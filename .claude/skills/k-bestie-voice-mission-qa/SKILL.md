# k-bestie-voice-mission-qa

**목적: 음성 미션 "기능"만의 QA가 아니라, 아이와 AI 친구 간 실제 대화 경험을
검증하는 E2E 서비스 QA다.** 내친구 케이(K-Bestie-v3) 음성 미션의 QA·E2E·회귀
테스트·완료 판정을 수행하기 전에 반드시 이 스킬을 적용한다. 코드만 보고
실동작을 추측하지 않는다 — 모든 판정은 실제 실행 증거(로그·DB 조회·라이브
API 응답·화면 변화)를 근거로 한다.

## QA 기본 원칙 (반드시 먼저 적용, 2026-07-25 v2 강화)

이전 회귀 QA에서 "케이의 응답은 자연스럽고 API도 200을 반환하지만, 실제로는
`mission_question_history`/`mission_progress`가 전혀 갱신되지 않아 미션이
영원히 완료되지 않는" 결함을 뒤늦게 발견한 사례가 있었다(자동화 스크립트가
"문항이 PRIMARY로 배정됨"처럼 항상 참인 정적 사실을 "승격 성공"으로 오인해
과거 PASS를 잘못 보고했었다). 이 재발을 막기 위한 원칙:

- **API 성공 응답이나 로그 정상만으로 PASS 판정 금지.** `res.ok === true`,
  200 응답, 정상적인 콘솔 로그가 있어도 그 자체는 증거가 아니다.
- **"아이 행동 → K 응답 → 서비스 상태 변경 → 화면 변화"라는 전체 흐름이
  실제로 완결돼야만 PASS다.** 이 네 단계 중 하나라도 실제 DB 조회나 화면
  관찰로 확인하지 못했다면 그 시나리오는 PASS가 아니다.
- **자동 테스트 PASS와 실제 사용자 경험 PASS를 구분한다.** 자동화 스크립트가
  "에러 없이 끝남"을 PASS로 오인하지 않는다 — 서비스 상태(DB) 변화와 화면
  변화까지 직접 조회·관찰해야 진짜 PASS다.
- 문항 배정처럼 세션 시작 시점에 이미 고정되는 정적 사실(예: "1~10번
  selected_order는 항상 PRIMARY")을 답변 처리 이후의 동적 결과("승격됨",
  "진행됨")로 착각해 보고하지 않는다. 정적 사실과 동적 결과를 반드시 구분해서
  검증한다.

## 호출

```text
/k-bestie-voice-mission-qa
/k-bestie-voice-mission-qa requests/004-mission-reserve-live-e2e.md
```

인자로 요청서 경로를 주면 그 요청서의 요구사항과 아래 협의된 QA 기준을
결합해 테스트 매트릭스를 구성한다. 인자가 없으면 아래 기준만으로 현재
배포된 음성 미션 전반을 검증한다.

상세 턴별 테스트 매트릭스와 시나리오 A~G는 `references/voice-mission-test-matrix.md`
참고. 증거 기록·보고 형식은 `templates/qa-report.md` 참고.

## 음성 미션 E2E 검증 단계 (모든 시나리오 공통 뼈대)

모든 미션 테스트는 아래 4단계 순서를 기준으로 검증한다. 각 단계에서 실제
증거(로그/DB조회/화면관찰)를 확보하지 못하면 그 단계는 `확인 못 함`으로
남기고, 다음 단계를 임의로 PASS 처리하지 않는다.

1. **아이 행동**: K 질문 수신 → 아이 음성 답변 → STT 인식 결과 확인
2. **AI 처리**: 답변 분류 결과(VALID/REFUSAL/NO_RESPONSE) 확인 → K 응답 생성
   확인 → TTS 재생 상태 확인
3. **서비스 상태**(DB 직접 조회로 확인, 화면 관찰만으로 대체 금지):
   `valid_answer_count` 증가 여부 / mission progress 증가 여부 / session
   상태 유지 여부 / 다음 질문 선택 여부 / 미션 완료 조건 도달 여부
4. **화면**: 진행률 게이지 변화 / 상태 표시 변화 / 오류 메시지 노출 여부 /
   다음 질문 표시 여부

**3번(서비스 상태) 단계를 생략하고 1·2·4번만 확인한 채 PASS로 보고하는 것이
바로 이전 회귀에서 실제로 발생했던 오판정 원인이다** — 반드시 DB를 직접
조회해 `mission_question_history.answer_classification`/`progress_awarded`,
`mission_progress.valid_answer_count`가 실제로 변했는지 확인한다.

## QA 시작 전 정본 확인 (필수, 생략 불가)

1. 대상 요청서의 요구사항(인자로 주어진 경우)
2. 현재 미션 정책(이 문서의 협의된 기준)
3. 현재 배포 커밋(`git log -1 --format="%H %s"`)
4. 테스트할 Dev URL(`https://k-bestie-v3-dev.vercel.app`)
5. 테스트 계정(§테스트 계정 정책 참고)
6. 기존 미션 세션과 진행률(Dev DB 직접 조회)
7. 질문 20개 구성 상태(PRIMARY 10 + RESERVE 10, 실제 배정 수 확인)
8. 테스트 후 복구가 필요한 데이터(QA 계정에 남길 흔적이 있는지)

## 협의된 QA 기준

### 유효 답변

질문과 관련된 답변이면 다음도 유효 답변으로 인정한다.

- 짧은 답변("응", "좋아")
- 다소 애매하지만 질문과 관련된 답변("그냥 그랬어")
- 한두 단어로 된 답변

유효 답변 처리:
1. 케이가 답변 내용에 맞게 자연스럽게 반응
2. 미션 진행률 10% 증가
3. 다음 질문으로 이동

추가 설명을 강제로 요구하거나 같은 질문을 다시 묻지 않는다.

### 유효하지 않은 답변

다음은 유효 답변으로 인정하지 않는다.

- 질문과 완전히 관련 없는 답변
- 명시적인 답변 거부
- 침묵 또는 무응답
- 의미를 파악할 수 없는 답변

처리:
1. 같은 질문을 자연스럽게 한 번만 재질문
2. 재질문에도 유효 답변이 없으면 진행률을 올리지 않음
3. 다음 질문으로 이동

### 질문 순환 정책 (4단계)

미션은 유효 답변 10개를 받아야 완료된다. 순서:

1. 기본 질문 10개 진행
2. 유효 답변이 부족하면 예비 질문 10개 진행
3. 그래도 부족하면 기본·예비 질문 중 미답변 문항만 순서대로 1회 순환
4. 그래도 부족하면 다음 최종 안내 전달 후, 남은 미답변 문항을 마지막으로
   1회 더 순환

```text
더 이상 준비된 질문지가 없어서 미션을 완료할 수 없어요. 다시 한번 질문을
진행할게요. 이번에도 답변 못하면 미션은 실패됩니다.
```

마지막 순환 후에도 유효 답변이 10개 미만이면 미션 실패. 유효 답변이 10개가
되는 즉시 남은 질문 수와 관계없이 완료한다.

### 진행률 규칙

```text
유효 답변 0개 = 0%   ...   유효 답변 9개 = 90%   유효 답변 10개 = 100%(완료)
```

무효 답변에서는 진행률 증가 금지. 같은 답변 중복 제출로 진행률이 두 번
증가하면 안 된다.

### 음성 처리 상태 표시

한 턴의 전체 흐름: 아이 발화 → 음성 입력 종료 → STT → LLM 응답 생성 →
TTS 생성 → 실제 음성 재생 → 다음 질문 대기.

`components/VoiceConversationStateBadge.tsx` 기준 필수 상태 5종(코드에 정의된
실제 상태값을 우선 확인 후 적용 — 아래는 참고 기준, 임의로 새 상태명을
추측하지 않는다):

| 상태 문구 | 표시 조건 | 해제 조건 |
|---|---|---|
| 연결 중 | 세션/소켓 연결 수립 중 | 연결 완료 |
| 듣는 중 | 마이크 입력을 실제로 받는 중 | 발화 종료 |
| 생각하는 중 | 발화 종료 후 STT·LLM·TTS 처리 중 | 음성 재생 시작 |
| 말하는 중 | 실제 오디오 재생 시작 | 실제 오디오 재생 종료 |
| 오류 상태 | 실제 파이프라인 단계 실패 시 | 복구 또는 재시도 |

검증: 실제 pipeline stage와 UI 표시 일치 / 상태 순서가 뒤바뀌지 않음 / 영구
고정되지 않음 / 실패 후에도 잘못된 상태가 남지 않음 / 다음 턴에서 다시
"듣는 중"으로 복귀 / 정상 대화 중 불필요한 오류 표시 없음.

### 응답 시간 측정 (성능 검증)

각 턴마다 다음을 실제로 측정·기록한다: 아이 발화 종료 시각 / STT 완료 /
LLM 응답 생성 완료 / TTS 생성(시작) 시각 / 케이 음성 재생 시작 / 케이 음성
재생 종료. 파생 지표: 아이 발화 종료→K 응답 시작 latency, K 응답 생성 시간,
TTS 시작 시간, 전체 turn latency.

핵심 지표: **아이 발화 종료 → 케이 음성 재생 시작**. 판정 기준은 이 스킬이
임의로 정하지 않는다 — 코드에 정의된 실제 타임아웃/기준값(예: watchdog
타이머, `apiTimeoutRef` 등)을 먼저 확인한 뒤 그 값을 기준으로 적용하고,
추측하지 않는다. 측정값은 초 단위로 기록하고 지연 발생 단계를 구분해
보고한다.

### 연결 경고 검증

정상 대화 중 상단에 "연결 불안정"/"연결 다소 불안정"이 불필요하게 표시되면
안 된다. 단순 시간 경과만으로 경고를 표시하면 결함이다. 다음 근거를
구분해 기록한다: 실제 단계 실패 / API 오류 / timeout / 오디오 재생 실패 /
단순 응답 지연 / UI 상태 판단 오류. 대화가 정상적으로 계속되는데 경고가
나오면 이 항목은 `FAIL`이다.

### 결과 판정

각 시나리오는 `PASS` / `FAIL` / `BLOCKED` / `NOT TESTED` 중 하나로만
판정한다. 실행하지 않은 시나리오를 PASS로 처리하지 않는다. 필수 시나리오에
`FAIL`·`BLOCKED`·`NOT TESTED`가 하나라도 있으면 전체 QA를 PASS로 보고하지
않는다.

### 테스트 계정 정책

자동 QA는 전용 QA 계정만 사용한다: 부모 `QA테스트`, 자녀 `QA테스트(5학년)`.
비밀번호는 환경변수(`QA_TEST_PASSWORD`)로만 받고 코드나 로그에 하드코딩하지
않는다.

절대 금지: 김서아·김서현 자동 로그인, 비밀번호 변경, 세션 삭제, 프로필
변경, 황금열쇠 변경, 미션 데이터 초기화. 실제 가족 계정은 대표님 수동
확인용으로만 남긴다.

QA 진행 중 QA 계정 데이터를 변경했다면(예: `given_name` 임시 설정, 세션
생성) 검증 종료 후 반드시 원상 복구하고 생성된 테스트 세션을 정리한다.

### 대표님 확인 항목 (자동 QA 완료 후)

최대 5개 항목만, 다음 형식으로 전달한다 — 장문의 내부 로그를 그대로
붙이지 않는다.

```text
[대표님 확인 필요]
1. 접속 위치
2. 사용할 계정
3. 말할 내용
4. 정상적으로 보여야 할 결과
5. 문제가 생기면 캡처할 화면
```

## 작업 방식

1차 조사·실행은 agy 또는 메인 Claude Code가 수행할 수 있다. **이 스킬은
QA 전용이다 — 코드 수정은 절대 하지 않는다.** 버그를 발견해도 이 스킬
실행 중에는 고치지 않고, 원인·재현 조건·영향 범위를 보고서에 기록해
대표님 결정 또는 별도 개발 지시를 기다린다(코드 수정이 필요하면 §하드룰1의
별도 트랙으로 넘긴다).

실행 순서:
1. dry run 실행(코드·DB를 변경하지 않는 읽기 전용 확인 — 정본 확인 8항목,
   기존 세션/문항 배정 상태 등).
2. 실제 데이터 변경이 필요한 시나리오(세션 생성, `given_name` 임시 설정 등)는
   QA 계정에서만 수행.
3. 검증 종료 후 변경 파일 목록을 출력(이 스킬 실행 중 앱 코드 파일이 단 하나도
   바뀌지 않았음을 `git status`/`git diff`로 직접 확인해 보고에 포함).
4. 커밋 전 결과 보고 — QA 보고서를 커밋하기 전에 반드시 요약 결과를 먼저
   보고한다.

메인 Claude Code가 (이 QA 스킬과 무관하게) 직접 코드를 수정한 경우는 별도
`claude-review` 인스턴스가 읽기 전용 검증한다 — 이 규칙은 QA 스킬 자체의
동작에는 적용되지 않는다(QA 스킬은 애초에 코드를 수정하지 않으므로).
