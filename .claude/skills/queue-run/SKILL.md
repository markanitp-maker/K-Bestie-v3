# 큐 실행 규칙

## 큐 감시 규칙

### 큐 정의

- `requests/` 폴더가 작업 지시서 큐다.
- `_done/`, `_failed/`에 없는 `.md` 파일이 처리 대상이다. (`_TEMPLATE.md`, `_log.md`, `_blocked.md`, `_dashboard.md`는 제외)
- 처리 순서는 파일명 오름차순이다.

### 절대 원칙

- 한 지시서를 끝낼 때마다 **반드시 `requests/`를 다시 나열(ls)한다.** 기억이나 캐시에 의존하지 않는다.
- 처리 대기 파일이 하나라도 남아 있으면 **턴을 종료하지 않는다.** 큐가 빌 때까지 계속 진행한다.
- **큐가 비면 폴링하지 말고 턴을 종료한다.** 대기 상태에서 Claude가 주기적으로 큐를 다시 여는 것은 토큰 낭비이므로 금지한다. 신규 지시서 감지는 OS 크론(`/failure-handling` §14-G)이 담당하며, 크론이 새 파일을 발견하면 새 세션을 기동한다.

### 처리 절차

1. `requests/`를 나열하고 처리 대상을 확정한다.
2. 가장 앞선 파일을 읽고, 그 내용을 **`/gate-route` 표준 작업 흐름**에 투입한다.
3. **2단 게이트 통과 후** 해당 파일을 `requests/_done/`으로 이동하고 `_log.md`에 [일시 / 파일명 / 개발주체(모델·effort) / 정적리뷰주체 / QA주체 / 변경파일 / 결과]를 기록한다. **단, 해당 건이 Production 배포 대상(대표님이 Production 배포를 명시 승인한 경우)이면 2단 게이트 통과·Dev 배포만으로는 `_done`으로 옮기지 않는다 — 실제 Production 배포 완료를 확인한 뒤에만 이동한다.** Production 배포 승인이 없는 지시서는 게이트 통과 직후 바로 `_done`으로 이동한다.
4. **지시서 전체를 이번 턴에 완료할 수 없는 특이사항**(대표님 결정 필요, 또는 기술적 이슈·의존성 충돌·정보 부족 등 스스로 판단·해결 불가)이 발생하면 `_done`·`_failed` 어디로도 옮기지 않고 아래 "특이사항 대시보드" 절차에 따라 `requests/_dashboard.md`에 기록한 뒤, 해당 건은 건너뛰고 다음 큐로 진행한다.
5. `/failure-handling` §12-D 기준으로 재시도를 모두 소진하고도 기술적으로 실패가 확정되면 `requests/_failed/`로 이동하고 `_log.md`에 사유를 기록한다.
6. 1번으로 돌아간다. 작업 중 새로 생성된 파일도 이 시점에 발견되어 처리된다.
7. 큐가 비면 CLAUDE.md §9 김비서 보고를 실행한 뒤 **종료한다.** `_dashboard.md`에 항목이 하나라도 있으면 이 보고에 대표님 확인·결정 필요 사항으로 반드시 포함한다.

### 큐 항목의 병렬 처리

- 파일 범위가 겹치지 않는 지시서가 2개 이상 대기 중이면 **여러 agy 구현 위임을 동시 실행**한다. 상한과 격리 조건은 아래 「병렬 실행」을 따른다.
- 공유 파일(라우터 인덱스 / 공통 타입 / 설정파일 / package.json)을 건드리는 지시서는 단독으로 순차 처리한다.
- 판단이 애매하면 병렬로 묶지 말고 순차로 처리한다.
- 병렬로 처리했더라도 검증은 **묶음 단위로 한 번** 올린다(§2 기능 단위 게이트 원칙 유지).

### 작업 규칙

- 지시서 착수 전 `docs/conventions.md`(코드베이스 현황)와 AGENTS.md §6~§10(코딩 규약)을 확인하고 그에 따른다. **브리프에도 핵심 규약을 명시해 전달한다(`/delegate-run` 「위임 브리프 필수 포함 항목」).**
- 각 지시서는 `## 범위`에 명시된 경로 안에서만 파일을 생성·수정한다.
- 공유 파일은 지시서의 `## 공유파일 수정`에 명시된 경우에만 수정한다.
- 판단이 필요한 지점은 임의로 결정하지 않는다. 지시서의 **일부 세부 판단**만 보류해도 나머지로 정상 완료할 수 있으면 `requests/_blocked.md`에 [파일명 / 질문 / 보류 지점]을 기록하고 그 부분만 건너뛴 뒤 나머지를 완료한다. **지시서 전체**가 그 판단 없이는 진행 불가능하면 아래 "특이사항 대시보드"를 따른다.

### 특이사항 대시보드 (`_dashboard.md`)

- **대상**: 지시서 전체를 이번 턴에 완료할 수 없는 경우 — 대표님 결정 필요, 또는 기술적 이슈·의존성 충돌·정보 부족으로 스스로 판단·해결 불가.
- **`_failed/`와의 구분**: `/failure-handling` §12-D는 실제로 시도했으나 소진 후 기술적 실패가 확정된 경우다. `_dashboard.md`는 그 이전 단계 — 진행 자체가 막혀 시도조차 못 하는 경우.
- 해당 지시서를 `_done/`으로 옮기지 말고 `requests/_dashboard.md`에 기록한다. 지시서 파일 자체는 `requests/`에 남고 처리 제외 목록에 포함되므로 무한 재처리되지 않는다.
- **`_dashboard.md`는 큐 루트에 있는 모든 지시서의 현재 상태를 `대기중`/`진행중`/`완료` 3단계 표로 항상 유지한다.** 상태가 바뀔 때마다(착수 시 `대기중`→`진행중`, 2단 게이트+배포 완료 시 `진행중`→`완료`) 갱신하고, 대표님이 "진행 상황 체크"를 요청하면 이 표를 최신화해 보여준다.
- 실제로 판단이 막힌 건에만 아래 3단 템플릿을 표 아래에 추가로 붙인다.

    ```markdown
    ## <지시서 파일명> (예: 003-결제연동.md)

    **사유**: 왜 완료하지 못했는지 구체적으로 작성

    **필요 조치**:
    - 대표님 결정 사항이면: 선택지 목록 + 결정할 항목
    - 기술 이슈면: 필요한 조치·정보
    ```

- **참조 대상 지시서가 `_done`이나 `_failed`로 이동하면 그 즉시 해당 행·항목을 삭제한다.** 완료된 작업의 후속 참고사항·잔여 리스크는 `_dashboard.md`가 아니라 `_log.md`에만 남긴다.
- 큐를 모두 순회한 뒤 `_done/` 이동 목록과 `_dashboard.md` 미완료 목록을 각각 요약해 보고한다.

### 긴급 요청 처리

- 채팅으로 새 지시가 들어오면 해당 지시를 최우선으로 처리한다.
- 완료 후 `requests/`를 다시 나열하고, 대기 파일이 있으면 이어서 진행한다.
- 중단되었던 지시서를 재개할 때는 처음부터 다시 하지 않는다. 대상 파일의 현재 상태를 먼저 읽고 이미 완료된 부분은 건너뛴다.

### 보고

- 각 지시서 처리 후 [파일명 / 개발주체 / 정적리뷰주체 / QA주체 / 변경 파일 목록 / 상태]를 한 줄로 출력한다.
- 큐가 비면 처리 결과 전체를 표로 출력하고, `_done/` 이동 목록과 `_dashboard.md` 미완료 건 목록을 각각 요약한 뒤 CLAUDE.md §9 김비서 보고를 실행한다.

## 큐 파일 구조와 지시서 템플릿

```
requests/
  001-<작업명>.md      ← 대표님이 생성하는 지시서
  002-<작업명>.md
  _TEMPLATE.md         ← 지시서 양식
  _done/               ← 완료된 지시서 보관
  _failed/             ← 실패한 지시서 보관
  _log.md              ← 처리 이력
  _blocked.md          ← 판단 보류 항목(지시서 일부만 보류, 나머지는 정상 완료)
  _dashboard.md        ← 큐 루트 지시서 상태표 + 특이사항(§1-A)
docs/
  conventions.md       ← 코드베이스 "현황" 단일 출처 (§9)
  plans/               ← Codex가 작성하는 구현 계획서
  ops/                 ← 운영 절차 상세 (§8)
```

## 병렬 실행

- 작업들이 서로 다른 파일 → 여러 위임을 동시 실행. **동시 실행 상한 10개**(2026-08-11 대표님 지시로 3→10 상향). 구현·잡무·QA를 모두 합산한다.
- **10개로 상향하면서 격리 워크트리 사용을 필수로 한다.** 2개만 같은 메인 작업 디렉토리(`cwd`)를 공유해도 빌드·파일 편집이 충돌한 사고(2026-08-11 실측 — 동시 `npm run build` 두 개가 서로의 `.next`를 밟음)가 있었다. 3개 초과로 동시 실행할 때는 **각 위임을 반드시 별도 git worktree**(`worktrees/<task>` 또는 기존 `req-XXX` 패턴)에서 실행해 파일·빌드 캐시 충돌을 원천 차단한다. 3개 이하로 돌릴 때도 격리 워크트리 사용을 권장한다.
- 파일이 겹치면 → 순차 실행(워크트리로 격리해도 같은 논리적 리소스, 예: 동일 마이그레이션 타임스탬프 대역이나 공유 파일을 건드리면 병합 시 충돌하므로 순차가 안전).
- 큐 지시서 간 병렬 판단 기준은 §1-A "큐 항목의 병렬 처리"를 따른다.
- **게이트 위임(Codex 정적리뷰 / agy QA)은 구현 슬롯과 별도로 센다.** 게이트 병렬은 최대 3개(정적 2 + QA 2 중 합계 3)로 유지한다 — 구현이 10개로 늘어도 리뷰 인프라 부하를 고려해 게이트 상한은 별도로 논의 전까지 그대로 둔다.
- **쿼터 소진 위험**: 동시 실행 수가 늘수록 한도 초과가 더 빨리 올 수 있다(과거 반복 이력 있음). **한도에 도달하면 Claude가 대신 하지 않는다** — 큐를 멈추고 CLAUDE.md §9로 보고한 뒤 대기한다(`/failure-handling` §12-E).

## 대표 확인과 보고 양식

개발 작업 진행 중 아래 상황이 발생하면 임의 판단으로 진행하지 말고 즉시 대표님에게 확인 요청 상태로 전환한다.

### 대표님 확인이 필요한 경우

1. 제품 방향 결정 필요 — 구현 방식이 여러 가지이고 사업 방향에 영향 / 데이터 구조·UX·서비스 정책 변경 / 기존 결정과 충돌 가능
2. 대표님 실사용 테스트 필요 — 실제 모바일/PC 확인 / 음성 품질·UX 체감 / 실사용자 관점 판단
3. 외부 작업·정보 입력 필요 — Vercel 환경변수 / 외부 API Key / 테스트 계정 충전 / 도메인·DNS / 제3자 권한 승인
4. 위험 작업 승인 필요 — DB migration / 기존 정상 기능 변경 / Production 배포 / 되돌리기 어려운 변경

### 보고 형식

무조건 한국어로만 답변한다.

```
[대표님 결정 필요]
항목:
현재 작업:
왜 멈췄는지:
선택 가능한 방향:
권장 방향:
대표님이 결정해야 하는 내용:
```

### 진행 가능한 작업은 자동 처리

코드 작성 / 테스트 코드 작성 / 빌드 오류 수정 / 타입 오류 수정 / 기존 구조 분석 / 영향 범위 분석 / Dev 환경 검증 / **Dev 환경 E2E QA** / 기존 기능 회귀 테스트. 이들은 대표님께 묻지 않고 자동 진행하되, 실행 주체는 §1 역할 분담을 따른다(코딩·QA는 agy, 분석·설계는 Codex, Claude는 게이트 명령만 직접 실행). 단, 기존 기능 변경이나 DB 구조 변경이 필요한 경우 먼저 확인한다.

### 작업 상태 관리

requests 항목 처리 중 대표님 입력이 필요하면 상태를 `대표님 결정 대기`로 변경한다. 완료 가능한 다른 요청은 계속 진행한다. 대기 중 임의 구현·추측 기반 정책 결정·기존 코드 삭제·새 DB 구조 생성 금지.
