# 성장정보 UX 개선 v2

## 0. 완료 시 기대 결과 / 대표님 테스트 정상 프로세스

### 완료 시 기대 결과

부모가 `우리 아이 성장정보`를 사용할 때 불필요한 스크롤, 과도한 동의 영역, 최초 설정 후 중복 입력, 생년월일 수정 진입점 부재를 한 번에 개선한다.

최종 UX는 다음과 같아야 한다.

1. 성장정보 상세 모달을 열면 최상단에서 바로 `새 기록 추가` 버튼을 사용할 수 있다.
2. 성장정보 수집·이용 동의 상세 설명은 기본 접힘 상태이며, 부모가 원할 때만 펼쳐본다.
3. 최초 성장정보 설정 시 생년월일 입력과 동의 후 바로 키·몸무게 첫 측정값까지 한 번에 입력한다.
4. 성장정보 상세 상단의 중복 아이 이름 표시는 제거한다.
5. 아이 이름 대신 `정보 변경 · 측정 당시 만 10세 6개월` 형태로 표시한다.
6. `정보 변경`을 누르면 생년월일 수정 UI가 열리고, 저장 후 월령·키/몸무게 백분위·BMI 백분위·성장곡선이 즉시 재계산된다.
7. 생년월일 수정 시 기존 키·몸무게 측정값 자체는 변경하지 않는다.
8. 기존 성장정보 계산, DB, RLS, 수동 기록 추가/수정/삭제 기능은 회귀하지 않는다.

### 대표님 테스트 정상 프로세스

#### 시나리오 A — 기존 성장정보 사용자의 새 기록 추가

1. 부모 홈에서 자녀의 `키/몸무게` 성장정보 카드를 클릭한다.
2. `우리 아이 성장정보` 상세 모달이 열린다.
3. 화면을 아래로 스크롤하지 않아도 최상단 헤더 우측에서 `새 기록 추가` 버튼이 보인다.
4. `새 기록 추가`를 누르면 기존 신규 측정기록 입력 UI가 열린다.
5. 키/몸무게/측정일을 입력하고 저장한다.
6. 최신 카드, 성장곡선, 측정 기록이 갱신된다.

PASS 기준:
- `새 기록 추가`가 모달 최초 진입 화면에서 즉시 보인다.
- 하단까지 스크롤해야 기록을 추가하는 불편이 제거된다.
- 중복된 `새 기록 추가` 버튼이 화면에 동시에 존재하지 않는다.
- 기존 저장 로직과 최신값 계산이 정상이다.

#### 시나리오 B — 성장정보 최초 설정 및 동의

1. 성장정보를 한 번도 설정하지 않은 자녀의 성장정보 카드를 클릭한다.
2. 생년월일 입력 및 성장정보 수집·이용 동의 화면이 열린다.
3. `성장정보 수집·이용 동의` 상세 설명 영역은 기본적으로 접혀 있다.
4. 체크박스, `나중에 하기`, `동의하고 시작하기` 버튼은 상세 설명을 펼치지 않아도 바로 보인다.
5. 부모가 `내용 확인`을 누르면 기존 상세 동의 문구 전체가 펼쳐진다.
6. 다시 누르면 접힌다.
7. 상세 내용을 펼치지 않은 상태에서도 체크 후 `동의하고 시작하기`가 가능하다.

PASS 기준:
- 기존 법적 동의 문구는 삭제/축약되지 않는다.
- 기본 화면 높이가 줄어든다.
- 동의 내용 확인은 선택적으로 가능하다.
- 동의 저장, 동의 버전, 동의 시각 등 기존 로직이 유지된다.

#### 시나리오 C — 최초 성장정보 설정 후 첫 기록 입력

1. 부모가 생년월일 입력과 성장정보 동의를 완료한다.
2. 빈 성장정보 상세 화면으로 먼저 이동하지 않는다.
3. 같은 최초 설정 플로우에서 바로 `첫 성장기록 입력` 단계가 표시된다.
4. 키(cm), 몸무게(kg), 측정일을 입력한다.
5. 저장하면 첫 `growth_measurements` 기록이 생성된다.
6. 이후 성장정보 상세 화면으로 진입한다.
7. 키/몸무게/BMI/백분위/성장곡선/측정기록이 첫 입력값 기준으로 정상 표시된다.

PASS 기준:
- `생년월일 입력 → 동의 → 빈 성장정보 화면 → 새 기록 추가 클릭`의 중복 흐름이 제거된다.
- 첫 성장기록 입력이 최초 설정 플로우 안에서 연속적으로 진행된다.
- 첫 기록이 `parent_manual` Source of Truth로 정상 저장된다.

#### 시나리오 D — 생년월일 정보 변경

1. 부모가 기존 성장정보 상세 모달을 연다.
2. 제목 아래 보조 정보 영역에는 아이 이름이 중복 표시되지 않는다.
3. 다음 형태로 표시된다.

```text
정보 변경 · 측정 당시 만 10세 6개월
```

4. 부모가 `정보 변경`을 누른다.
5. 기존에 저장된 생년월일을 수정할 수 있는 UI가 열린다.
6. 새 생년월일을 저장한다.
7. 기존 측정기록의 키·몸무게 값은 그대로 유지된다.
8. 생년월일 기준으로 측정 당시 월령과 성장지표가 즉시 재계산된다.

PASS 기준:
- 성장정보 모달 안에서 아이 이름 중복이 제거된다.
- `정보 변경`이 생년월일 수정 진입점으로 동작한다.
- 생년월일 저장 후 월령·키 백분위·몸무게 관련 기존 지표·BMI 백분위·성장곡선이 갱신된다.
- 기존 측정값 자체는 변경되지 않는다.

## 2. 목표

현재 성장정보 UX에는 다음 네 가지 불편이 있다.

### 문제 1 — 새 기록 추가 버튼 접근성

`새 기록 추가` 버튼이 `측정 기록` 영역 하단에 있어 부모가 성장정보를 열 때마다 아래까지 스크롤해야 한다.

변경 목표:

```text
AS-IS
성장정보 열기
→ 키/몸무게/BMI
→ 성장곡선
→ 측정기록
→ 새 기록 추가

TO-BE
성장정보 열기
→ 최상단 헤더에서 새 기록 추가
→ 나머지 성장정보 확인
```

### 문제 2 — 동의 상세 설명이 초기 화면을 과도하게 차지함

현재 성장정보 수집·이용 동의 상세 문구가 항상 펼쳐져 있어 최초 설정 화면의 대부분을 차지한다.

변경 목표:

```text
성장정보 수집·이용 동의   [내용 확인 ▼]
[ ] 위 성장정보 수집·이용에 동의합니다.

[나중에 하기] [동의하고 시작하기]
```

기본값은 상세 내용 접힘이다.

### 문제 3 — 최초 설정 후 첫 측정값을 다시 별도 입력해야 함

생년월일과 동의를 완료해도 키/몸무게 기록이 없으므로, 부모가 성장정보 화면에 진입한 뒤 다시 `새 기록 추가`를 눌러야 한다.

변경 목표:

```text
생년월일 확인
→ 수집·이용 동의
→ 첫 키/몸무게 측정값 입력
→ 저장
→ 성장정보 상세
```

최초 설정 자체가 첫 성장기록 생성까지 한 흐름으로 완료되어야 한다.

### 문제 4 — 생년월일 정보 변경 진입점 부재 및 아이 이름 중복

현재 성장정보 상세 제목 아래에 다음과 같이 표시된다.

```text
안서아 · 측정 당시 만 10세 6개월
```

하지만 앱 상단 우측에 이미 현재 선택된 아이 이름이 표시되므로 성장정보 모달 안에서 아이 이름을 다시 반복할 필요가 없다.

또한 생년월일을 잘못 입력했거나 변경해야 할 때 수정할 진입점이 없다.

변경 목표:

```text
정보 변경 · 측정 당시 만 10세 6개월
```

`정보 변경` 클릭 시 생년월일 수정 UI를 열고, 저장 후 모든 성장지표를 재계산한다.

## 3. 요구사항

### 3-1. `새 기록 추가` 버튼을 최상단으로 이동

`우리 아이 성장정보` 상세 모달의 헤더 영역에 `새 기록 추가` 버튼을 배치한다.

권장 위치:

```text
우리 아이 성장정보       [새 기록 추가] [X]
정보 변경 · 측정 당시 만 10세 6개월
```

요구사항:

- 모달 최초 진입 시 스크롤 없이 보일 것
- 닫기(X) 버튼과 충돌하지 않을 것
- 모바일/PWA에서 버튼이 잘리지 않을 것
- 기존 `새 기록 추가` 클릭 시 열리는 입력 UI/로직을 그대로 재사용할 것
- 하단 `측정 기록` 영역의 기존 `새 기록 추가` 버튼은 제거하여 중복 CTA를 만들지 않을 것
- 측정 기록 목록 자체는 그대로 유지할 것

### 3-2. 성장정보 동의 상세 영역 기본 접힘

현재 `성장정보 수집·이용 동의` 박스의 상세 내용은 삭제하지 않는다.

다만 기본 렌더링은 접힘 상태로 변경한다.

권장 구조:

```text
성장정보 수집·이용 동의                 [내용 확인 ▼]

[ ] 위 성장정보 수집·이용에 동의합니다.

[나중에 하기]        [동의하고 시작하기]
```

부모가 `내용 확인`을 누르면:

```text
성장정보 수집·이용 동의                 [내용 접기 ▲]

· 수집 항목: ...
· 이용 목적: ...
· 파생 정보: ...
· 열람 범위: ...
· 보유·파기: ...
· 동의하지 않아도 ...
· 참고 안내: ...
동의 버전: ...

[ ] 위 성장정보 수집·이용에 동의합니다.

[나중에 하기]        [동의하고 시작하기]
```

### 3-3. 동의 아코디언 동작

- 초기값: `collapsed`
- `내용 확인` 클릭: 펼침
- `내용 접기` 클릭: 접힘
- 상세 영역을 열지 않아도 동의 체크 가능
- 상세 영역을 열지 않아도 `동의하고 시작하기` 진행 가능
- 체크하지 않은 상태에서는 기존과 동일하게 동의 진행 차단
- `나중에 하기` 기존 동작 유지
- 기존 동의 문구, 동의 버전, 저장 방식은 변경하지 않음
- 단순 CSS 숨김으로 접근성을 깨지 말고 버튼의 `aria-expanded` 등 기본 접근성 속성을 적용할 것

### 3-4. 최초 설정 플로우에 첫 성장기록 입력 통합

성장정보를 아직 활성화하지 않은 부모가 `동의하고 시작하기`를 선택하면 곧바로 빈 성장정보 상세 모달을 보여주지 않는다.

대신 같은 흐름에서 첫 측정기록 입력 단계로 전환한다.

흐름:

```text
STEP 1
생년월일 확인
(+ gender가 NULL이면 성별 확인)

STEP 2
성장정보 수집·이용 동의

STEP 3
첫 성장기록 입력
- 측정일
- 키(cm)
- 몸무게(kg)

STEP 4
저장 후 우리 아이 성장정보 상세 표시
```

현재 생년월일 입력과 동의가 한 화면에 결합되어 있다면 기존 UI 구조를 억지로 여러 페이지로 나누지 말고, 현재 모달 안에서 자연스럽게 다음 단계로 전환해도 된다.

### 3-5. 첫 성장기록 입력 항목

최초 기록 입력 시 기존 `새 기록 추가`와 동일한 validation과 DB 저장 규칙을 사용한다.

필수 입력:

- 측정일
- 키(cm)
- 몸무게(kg)

기본값:

- 측정일: 오늘 날짜
- 부모가 실제 측정일로 수정 가능

저장:

```text
growth_measurements
source = parent_manual
```

기존 신규 기록 추가와 별도의 중복 저장 로직을 만들지 말고 가능한 한 동일 API/service/validation을 재사용한다.

### 3-6. 첫 기록 저장 후 즉시 성장정보 표시

첫 기록 저장이 성공하면 성장정보 상세를 다시 불러와 다음 값을 즉시 표시한다.

- 현재 키
- 현재 몸무게
- BMI
- 키 백분위
- 몸무게/체중 관련 기존 제공 정보
- BMI 백분위
- 성장곡선의 첫 측정점
- 측정 기록 1건

페이지/모달 전체 새로고침을 강제하지 말고 기존 데이터 refresh 패턴을 우선 재사용한다.

### 3-7. 최초 설정 중 저장 실패 처리

생년월일/동의는 성공했으나 첫 측정기록 저장이 실패할 수 있다.

이 경우:

- 동의와 생년월일 저장을 롤백하지 않는다.
- 오류를 명확히 표시한다.
- 첫 측정기록 입력값을 가능한 범위에서 유지한다.
- 재시도할 수 있게 한다.
- 오류 때문에 빈 화면으로 강제 이동하지 않는다.

### 3-8. 이미 성장정보를 사용하는 부모

기존 데이터가 있는 부모에게는 최초 설정 플로우를 다시 보여주지 않는다.

기존 사용자는:

```text
성장정보 카드 클릭
→ 상세 모달
→ 최상단 새 기록 추가
```

로 동작한다.

### 3-9. 성장정보 동의 이력이 있으나 측정기록이 0건인 경우

기존 이관 데이터 또는 중간 이탈 사용자처럼:

- 성장정보 동의 완료
- 생년월일 존재
- `growth_measurements = 0`

인 상태가 있을 수 있다.

이 경우 성장정보 진입 시 `첫 성장기록 입력`을 우선 안내한다.

최상단 CTA 역시 `새 기록 추가`로 사용할 수 있다.

### 3-10. 기존 하단 기록 영역 정리

`측정 기록` 섹션에서는:

- 기록 목록
- 편집
- 삭제

기능만 유지한다.

`새 기록 추가` CTA는 최상단으로 단일화한다.

버튼 삭제 후 불필요한 빈 margin/padding/고정 높이가 남지 않도록 함께 정리한다.

### 3-11. 성장정보 상세의 아이 이름 중복 제거

현재 상세 모달 상단 보조 문구에 표시되는 아이 이름을 제거한다.

AS-IS:

```text
안서아 · 측정 당시 만 10세 6개월
```

TO-BE:

```text
정보 변경 · 측정 당시 만 10세 6개월
```

이유:

- 앱 우측 상단에 현재 선택된 아이 이름이 이미 표시됨
- 동일 이름 반복은 정보 가치가 낮고 헤더 공간만 차지함

### 3-12. `정보 변경` 버튼/링크 추가

`정보 변경`은 생년월일 수정 진입점이다.

요구사항:

- 텍스트 링크 또는 compact button 형태
- 측정 당시 월령 정보와 한 줄 안에서 자연스럽게 배치
- 모바일에서 줄바꿈/겹침 최소화
- 클릭 시 현재 저장된 생년월일이 prefill된 수정 UI 오픈
- 저장/취소 가능
- 저장 중 중복 submit 방지

### 3-13. 생년월일 수정 저장

부모가 생년월일을 수정하면 기존 성장정보 프로필의 생년월일 Source of Truth를 갱신한다.

중요:

- 기존 키/몸무게 측정값 수정 금지
- 기존 `measured_at` 수정 금지
- 기존 측정기록 개수 유지
- 생년월일만 변경

저장 성공 후 다음 항목을 즉시 재계산/재조회한다.

- 각 측정기록의 측정 당시 월령
- 키 백분위
- 몸무게 관련 기존 지표
- BMI 백분위
- 성장곡선 위치
- 또래 중앙값/기준값 표시
- 현재 상세 상단 `측정 당시 만 X세 Y개월`

### 3-14. 생년월일 변경 시 사용자 안내

생년월일 수정은 성장도표 계산 결과를 바꿀 수 있다.

수정 UI 또는 저장 직전 다음 의미의 짧은 안내를 제공한다.

```text
생년월일을 변경하면 기존 측정기록은 유지되고, 성장도표와 백분위는 새 생년월일 기준으로 다시 계산됩니다.
```

과도한 경고 모달은 만들지 않는다.

### 3-15. 생년월일 저장 실패 처리

저장 실패 시:

- 기존 생년월일 유지
- 기존 성장지표 유지
- 오류 메시지 표시
- 재시도 가능
- 부분적으로 UI만 바뀐 상태가 남지 않도록 한다.

## 4. 기존 구조 확인

현재 성장정보 v1에서 확인된 주요 구조를 유지한다.

### 4-1. 성장정보 조회

기존 확인 흐름:

```text
GrowthCards.tsx
→ GET /api/parent/growth/[childId]
→ loadGrowthState()
→ growth_measurements
```

최신 측정값은 기존 기준대로 처리한다.

### 4-2. 성장정보 저장

기존 부모 수동 입력은 `growth_measurements`를 Source of Truth로 사용한다.

이번 첫 기록 입력도 별도 테이블을 만들지 않고 기존 부모 수동 입력 저장 경로를 재사용한다.

### 4-3. 생년월일/동의

기존 성장정보 최초 설정에서 사용하는 생년월일 및 성장정보 수집·이용 동의 저장 로직을 그대로 유지한다.

이번 변경은:

- 동의 UI 압축
- 첫 측정기록 입력을 같은 최초 설정 흐름에 추가
- 생년월일 수정 진입점 추가

하는 UX 변경이 핵심이다.

### 4-4. 구현 전 Claude Code 재확인

개발 전에 실제 현재 파일명을 기준으로 다음을 재확인한다.

- 성장정보 상세 모달 컴포넌트
- `GrowthCards.tsx`
- 신규 측정기록 입력 컴포넌트
- 최초 생년월일/동의 컴포넌트
- 생년월일 저장 API/service
- growth GET/POST/PATCH/DELETE API
- `loadGrowthState()` 및 저장 service
- `growth_measurements` validation
- 동의 버전/저장 위치

파일명이 점검 당시와 변경되어 있으면 현재 Source of Truth를 기준으로 수정한다.

## 5. 금지사항

1. 성장정보 동의 상세 문구를 삭제하거나 임의 축약하지 않는다.
2. 동의 체크 없이 성장정보를 활성화하지 않는다.
3. `나중에 하기` 기존 동작을 제거하지 않는다.
4. `새 기록 추가` 버튼을 상단과 하단에 중복 배치하지 않는다.
5. 첫 기록 입력을 위해 새로운 별도 Source of Truth를 만들지 않는다.
6. 첫 기록을 `growth_measurements` 외 임시 공식 기록으로 저장하지 않는다.
7. 첫 기록의 `source = parent_manual` 정책을 임의 변경하지 않는다.
8. 성장도표/BMI/백분위 계산 로직을 이번 UX 작업에서 변경하지 않는다.
9. 기존 측정기록 편집/삭제 기능을 제거하지 않는다.
10. 회원가입/아이 추가 단계에 생년월일을 추가하지 않는다.
11. 아이 화면에 성장정보를 새로 노출하지 않는다.
12. 케이 대화 기반 키/몸무게 후보 연동 기능을 이번 Request에 섞지 않는다.
13. Production 데이터를 테스트 목적으로 수동 수정하지 않는다.
14. UI 요소 제거 후 불필요한 빈 공간을 남기지 않는다.
15. 생년월일 수정 시 기존 키/몸무게 측정값을 변경하지 않는다.
16. 생년월일 수정 시 기존 측정일을 변경하지 않는다.
17. 앱 우측 상단에 이미 있는 아이 이름을 성장정보 모달 상단에 중복 표시하지 않는다.

## 6. 모호성 처리

### 6-1. 생년월일과 동의 UI가 현재 하나의 화면인 경우

현재 구조를 유지해도 된다.

중요한 것은 `동의하고 시작하기` 후 첫 성장기록 입력이 바로 이어지는 것이다.

### 6-2. 최초 측정값 입력 중 부모가 닫기(X)를 누르는 경우

이미 저장된 생년월일/동의는 유지한다.

다음 성장정보 진입 시 측정기록이 0건이면 첫 성장기록 입력을 다시 안내한다.

### 6-3. 키 또는 몸무게 한쪽만 알고 있는 경우

현재 기존 `새 기록 추가` validation을 Source of Truth로 따른다.

현재 API가 두 값을 모두 요구한다면 최초 입력도 동일하게 둘 다 요구한다.

현재 API가 부분 측정을 허용한다면 신규 임의 제한을 추가하지 않는다.

### 6-4. gender가 NULL인 기존 아이

기존 성장정보 v1 정책대로 최초 설정에서 성별을 함께 확인한다.

성장정보 UX 개선을 이유로 회원가입 단계로 되돌리지 않는다.

### 6-5. 생년월일 수정 UI 위치

기존 최초 설정 생년월일 입력 UI를 재사용할 수 있다면 우선 재사용한다.

단, 수정 용도에서는 동의 절차를 다시 요구하지 않는다.

이미 동의가 유효한 사용자가 생년월일만 수정하는 경우 성장정보 수집·이용 동의를 다시 받지 않는다.

### 6-6. 생년월일 변경 후 연령이 서비스 대상 범위를 벗어나는 경우

현재 성장정보 v1의 연령 validation 정책을 그대로 따른다.

새로운 임의 기준을 추가하지 않는다.

필요 시 기존 validation 메시지를 재사용한다.
