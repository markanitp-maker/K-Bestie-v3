# 케이 챗봇 문의·건의·버그 접수 기능

- 상태: TODO
- 유형: 신규 기능
- 우선순위: HIGH
- 대상: 아이 화면, 부모 화면, 관리자 화면
- 요청 파일: `requests/019-k-chatbot-feedback-intake.md`

## 목적

아이와 보호자가 내친구 케이 서비스를 이용하는 도중 어느 화면에서든 즉시 문의, 건의사항, 버그를 접수할 수 있도록 전역형 `케이 챗봇` 버튼과 접수 모달을 추가한다.

이 기능의 1차 버전은 Gemini 또는 다른 LLM과 실시간으로 대화하는 AI 챗봇이 아니라, 사용자 의견을 서비스 운영자에게 전달하는 문의 접수 기능이다. 불필요한 AI API 호출과 비용이 발생하지 않아야 한다.

## 핵심 사용자 관점

### 아이 관점

- 문제가 생기거나 새로운 생각이 떠올랐을 때 현재 화면을 벗어나지 않고 바로 케이에게 알릴 수 있어야 한다.
- 어려운 고객센터 용어 대신 아이가 이해할 수 있는 짧고 쉬운 표현을 사용한다.
- 입력 영역과 버튼은 모바일 터치가 편하도록 충분히 크게 제공한다.

### 부모 관점

- 서비스 이용 중 문의, 기능 건의, 오류를 별도의 이메일이나 외부 채널 없이 접수할 수 있어야 한다.
- 접수 완료 여부와 접수번호를 명확하게 확인할 수 있어야 한다.
- 아이가 접수한 내용과 부모가 접수한 내용을 관리자 화면에서 구분할 수 있어야 한다.

### 사업·운영 관점

- 베타 사용자의 문의와 불편사항을 한곳에서 수집한다.
- 문의, 기능 개선 의견, 버그를 유형별로 분리하여 제품 개선 우선순위를 판단할 수 있어야 한다.
- 어떤 사용자 화면과 환경에서 문제가 발생했는지 최소한의 기술 정보를 함께 확보한다.

## 1. 전역 케이 챗봇 버튼

### 1.1 적용 대상

다음 영역의 공통 최상위 레이아웃에 적용한다.

- 아이 화면 전체
- 부모 화면 전체
- 하위 메뉴 및 상세 페이지
- 미션 화면
- 자유대화 화면
- 놀이 진입 및 결과 화면
- 리포트 및 설정 화면
- 페이지 이동 후 새로 렌더링되는 모든 인증 사용자 화면

### 1.2 위치

- 화면 좌측 하단에 고정한다.
- CSS 기준 `position: fixed` 방식으로 구현한다.
- 모바일에서는 `safe-area-inset-bottom`을 반영한다.
- 기존 하단 내비게이션, 음성대화 컨트롤, 마스코트, 주요 실행 버튼과 겹치지 않아야 한다.
- 모바일과 PC 화면에서 위치를 각각 검증한다.
- 다른 콘텐츠보다 위에 표시되도록 적절한 z-index를 적용하되 기존 모달과 충돌하지 않아야 한다.

### 1.3 표시 형태

버튼 표시명:

`케이 챗봇`

권장 구성:

- 기존 확정 케이 마스코트 또는 서비스 내 사용 중인 케이 아이콘
- `케이 챗봇` 텍스트
- 모바일에서 지나치게 큰 영역을 차지하지 않는 플로팅 버튼 형태
- 새 로고나 새 마스코트 이미지를 임의 생성하지 않는다.

### 1.4 유지 조건

- 메뉴를 이동해도 버튼이 사라지지 않아야 한다.
- SPA 라우트 전환 후에도 다시 마운트되거나 중복 생성되지 않아야 한다.
- 스크롤 위치와 관계없이 항상 같은 위치에 표시되어야 한다.
- 로그인하지 않은 공개 화면과 데모 화면의 노출 여부는 기존 인증·데모 정책을 확인한 후 결정한다.
- 결제, 약관 동의 등 화면을 가리는 것이 위험한 특수 페이지가 있다면 숨기지 말고 충돌하지 않는 위치로 조정한다.

## 2. 케이 챗봇 모달

`케이 챗봇` 버튼을 클릭하면 현재 페이지에서 이동하지 않고 모달 팝업을 연다.

### 2.1 모달 기본 구성

모달 제목:

`케이에게 알려주세요`

아이 화면 안내 문구:

`궁금한 점이나 불편한 점, 케이에게 바라는 점을 알려줘!`

부모 화면 안내 문구:

`서비스 이용 중 문의사항, 건의사항 또는 오류를 남겨주세요.`

접수 유형:

1. 문의하기
2. 건의하기
3. 버그 신고하기

### 2.2 모달 공통 동작

- 모달 닫기 버튼 제공
- ESC 키로 닫기
- 모달 외부 배경 클릭 시 닫기
- 입력 중 내용이 존재할 때 닫으려 하면 작성 내용 삭제 확인
- 포커스 트랩 적용
- 모달이 열리면 첫 번째 입력 요소로 포커스 이동
- 모달 종료 후 케이 챗봇 버튼으로 포커스 복귀
- 모바일 가상 키보드가 입력창과 제출 버튼을 가리지 않도록 처리
- 배경 스크롤 방지
- 중복 모달 생성 방지
- WCAG 기준에 맞는 label, aria 속성, 키보드 접근성 적용

- 제목: 사용하지 않음

입력창 제목:

`무엇이 궁금한가요?`

`케이에게 궁금한 내용을 적어줘.`

- 최대 2,000자
- HTML 및 실행 가능한 스크립트 입력을 안전하게 처리
- 제출 전후 원문이 임의로 변경되지 않아야 함

## 6. 자동 수집 정보

사용자가 직접 입력하지 않아도 접수 처리와 버그 분석에 필요한 다음 정보를 자동으로 저장한다.

- 접수 유형
- 사용자 화면 구분: `child` 또는 `parent`
- 로그인 사용자 식별자
- 보호자 식별자
- 아이 식별자
- 현재 페이지 URL 또는 route
- 접수 시각
- 앱 버전
- 배포 환경: local, preview, development, production
- 브라우저 정보
- 운영체제 정보
- 모바일 또는 PC 기기 구분
- 접수 언어
- 생성된 접수번호

현재 인증 구조상 아이가 별도의 `auth.users` 계정을 사용하지 않는다면 임의로 아이 계정을 새로 만들지 말고, 기존 세션의 보호자·아이 식별 구조를 사용한다.

### 자동 수집 금지 정보

다음 정보는 자동으로 수집하거나 저장하지 않는다.

- 아이와 케이의 대화 원문
- 음성 녹음 데이터
- 액세스 토큰
- Refresh Token
- 쿠키 원문
- 비밀번호
- 환경변수
- API Key
- 콘솔 로그 전체
- 네트워크 요청 본문 전체
- 부모 리포트 원문
- 화면 캡처
- 입력 폼의 다른 개인정보

이번 작업 범위에는 파일 및 스크린샷 첨부 기능을 포함하지 않는다.

## 7. 데이터 저장

기존 문의, 고객지원, 피드백 관련 테이블이 존재하면 우선 재사용 가능성을 검토한다.

기존 구조가 없거나 재사용이 부적절한 경우 신규 테이블을 추가한다.

권장 테이블명:

`feedback_requests`

### 7.1 권장 필드

| 필드 | 유형 | 설명 |
|---|---|---|
| id | uuid | Primary Key |
| request_number | text | 사용자에게 표시할 접수번호 |
| request_type | text 또는 enum | inquiry, suggestion, bug |
| title | text nullable | 문의하기는 null 허용 |
| content | text | 접수 내용 |
| submitter_user_id | uuid nullable | 인증 사용자 식별자 |
| submitter_role | text | child, parent |
| guardian_id | uuid nullable | 보호자 식별자 |
| child_id | uuid nullable | 아이 식별자 |
| app_surface | text | child, parent |
| current_route | text | 접수한 화면 경로 |
| app_version | text nullable | 앱 버전 |
| environment | text | local, preview, development, production |
| device_info | jsonb nullable | 브라우저·OS·기기 정보 |
| status | text 또는 enum | received, reviewing, resolved, closed |
| admin_note | text nullable | 관리자 내부 처리 메모 |
| created_at | timestamptz | 접수 시각 |
| updated_at | timestamptz | 수정 시각 |
| resolved_at | timestamptz nullable | 처리 완료 시각 |
| resolved_by | uuid nullable | 처리 관리자 |

### 7.2 상태 기본값

신규 접수의 기본 상태:

`received`

관리자 처리 상태:

- `received`: 접수됨
- `reviewing`: 확인 중
- `resolved`: 처리 완료
- `closed`: 종료

## 8. 권한 및 보안

### 8.1 사용자 권한

- 인증된 아이 또는 보호자 세션만 접수 가능
- 사용자는 자신의 세션 정보로만 접수를 생성할 수 있음
- 클라이언트가 다른 사용자 ID, guardian_id, child_id를 임의 지정할 수 없어야 함
- 서버에서 현재 인증 및 세션 기준으로 사용자 정보를 확정해야 함

### 8.2 관리자 권한

- 관리자만 전체 접수 목록 조회 가능
- 관리자만 접수 상태 변경 가능
- 관리자만 내부 메모 작성 가능
- 일반 사용자는 다른 사용자의 접수 내용을 조회할 수 없음

### 8.3 RLS

Supabase를 사용하는 경우 RLS를 필수 적용한다.

정책 원칙:

- 일반 사용자: 본인 세션에 해당하는 접수 생성만 허용
- 일반 사용자: 타인의 접수 조회·수정·삭제 금지
- 관리자: 전체 조회 및 상태·관리 메모 수정 허용
- 삭제는 기본적으로 관리자 UI에서도 제공하지 않으며 필요한 경우 별도 정책으로 처리

Service Role Key를 브라우저에 노출하지 않는다.

## 9. 중복 및 비정상 제출 방지

- 제출 중에는 제출 버튼 비활성화
- 한 번 클릭으로 하나의 요청만 생성
- 네트워크 재시도 시 동일 요청이 중복 저장되지 않도록 idempotency 또는 중복 방지 처리
- 사용자별 단시간 연속 접수 제한
- 정상적인 베타 피드백 제출을 방해하지 않는 수준의 rate limit 적용
- 서버에서 입력 길이와 필수값을 다시 검증
- 클라이언트 검증만 신뢰하지 않음
- SQL Injection 및 XSS 방어
- 오류 발생 시 입력 내용이 즉시 사라지지 않도록 유지

## 10. 제출 결과

### 10.1 성공

제출 성공 시 다음 메시지를 표시한다.

아이 화면:

`케이에게 잘 전달했어! 접수번호는 {접수번호}야.`

부모 화면:

`정상적으로 접수되었습니다. 접수번호는 {접수번호}입니다.`

성공 처리 후:

- 접수번호 표시
- 사용자가 확인 버튼을 눌러 모달 종료
- 종료 후 입력값 초기화
- 동일 화면을 계속 이용할 수 있어야 함
- 페이지 새로고침 불필요

### 10.2 실패

실패 메시지:

`접수하지 못했습니다. 작성한 내용은 유지되니 잠시 후 다시 시도해 주세요.`

실패 시:

- 입력 내용 유지
- 중복 저장 여부 확인
- 다시 제출 가능
- 기술 오류 상세를 사용자 화면에 그대로 노출하지 않음

- 접수자 및 연결된 아이
- 접수 화면 route
- 브라우저·OS·기기 정보
- 앱 버전
- 배포 환경
- 접수 시각
- 현재 상태
- 관리자 내부 메모

### 11.4 관리자 처리

관리자는 다음 작업을 수행할 수 있어야 한다.

- 상태 변경
- 관리자 내부 메모 작성
- 수정 시각 및 처리 관리자 기록

이번 범위에는 사용자에게 답변을 발송하는 이메일·알림 기능을 포함하지 않는다.

## 12. 디자인 및 UX 기준

### 12.1 공통

- 기존 내친구 케이 디자인 시스템과 브랜드 자산 사용
- 확정 브랜드 컬러와 기존 버튼 스타일 활용
- 별도 디자인 체계 또는 신규 캐릭터를 만들지 않음
- 부모 화면과 아이 화면의 기능 구조는 동일하게 유지
- 문구와 터치 영역만 사용자 특성에 맞게 조정

### 12.2 아이 화면

- 쉬운 단어 사용
- 한 화면에 과도한 설명을 표시하지 않음
- 입력창과 버튼을 크게 제공
- 오류 문구가 아이를 탓하는 표현이 되지 않게 함
- 접수 완료 시 명확하고 긍정적인 피드백 제공

### 12.3 부모 화면

- 문의 유형과 입력 항목을 명확히 구분
- 접수번호를 쉽게 복사하거나 확인할 수 있게 함
- 모바일과 PC에서 동일한 기능 제공

## 16. 검증 시나리오

### 시나리오 1: 아이 문의하기

1. 아이 계정으로 로그인한다.
2. 아이 메인 화면에서 케이 챗봇 버튼을 클릭한다.
3. 문의하기를 선택한다.
4. 자유 형식 내용을 입력한다.
5. 제출한다.
6. 성공 메시지와 접수번호를 확인한다.
7. 관리자 화면에서 아이 접수로 구분되는지 확인한다.

### 시나리오 2: 부모 건의하기

1. 부모 계정으로 로그인한다.
2. 부모 리포트 상세 화면으로 이동한다.
3. 케이 챗봇 버튼이 유지되는지 확인한다.
4. 건의하기를 선택한다.
5. 제목과 내용을 입력한다.
6. 제출한다.
7. 관리자 화면에서 부모 접수와 현재 route가 정상 표시되는지 확인한다.

### 시나리오 3: 버그 신고

1. 아이 또는 부모 화면에서 버그 신고하기를 선택한다.
2. 제목과 내용을 입력한다.
3. 제출한다.
4. 앱 버전, 환경, 브라우저, OS, 기기 정보가 저장되는지 확인한다.
5. 대화 원문, 토큰, 쿠키, API Key가 저장되지 않았는지 확인한다.

### 시나리오 4: 메뉴 이동 유지

다음 화면들을 순차적으로 이동하며 좌측 하단 버튼 유지 여부를 확인한다.

- 아이 메인
- 미션
- 자유대화
- 놀이
- 부모 메인
- 리포트
- 설정

### 시나리오 5: 모바일 UI

1. iPhone Safari에서 확인한다.
2. Android Chrome에서 확인한다.
3. safe-area와 하단 내비게이션 겹침 여부를 확인한다.
4. 키보드가 입력창과 제출 버튼을 가리지 않는지 확인한다.

### 시나리오 6: 중복 제출

1. 제출 버튼을 빠르게 여러 번 클릭한다.
2. DB에 하나의 접수만 생성되는지 확인한다.
3. 네트워크 지연 또는 재시도 상황에서도 중복 생성되지 않는지 확인한다.

### 시나리오 7: 권한

1. 일반 사용자가 다른 사용자의 접수를 조회할 수 없는지 확인한다.
2. 일반 사용자가 접수 상태와 관리자 메모를 수정할 수 없는지 확인한다.
3. 관리자만 전체 목록과 상세 내용을 조회할 수 있는지 확인한다.
4. 관리자만 상태와 내부 메모를 변경할 수 있는지 확인한다.

### 시나리오 8: 회귀 테스트

1. 미션 음성대화를 실행한다.
2. 마이크 및 상태 UI 동작을 확인한다.
3. 케이 챗봇 버튼이 음성대화 컨트롤을 방해하지 않는지 확인한다.
4. 부모 리포트와 설정 화면이 기존과 동일하게 동작하는지 확인한다.

## 18. 작업 및 리뷰 방식

- 기존 구조를 먼저 조사한 후 구현한다.
- 관련 없는 리팩터링은 하지 않는다.
- 현재 요청 범위 밖 기능을 임의 추가하지 않는다.
- 기존 문의·피드백 구조가 있으면 재사용 여부와 근거를 보고한다.
- DB Migration과 RLS 정책은 코드 리뷰와 별도로 보안 집중 검토한다.
- UI 구현 후 모바일·PC 반응형 검토를 수행한다.
- Codex 사용이 가능하면 독립 리뷰를 수행한다.
- Codex 토큰 제한 또는 사용 불가 시 Claude가 별도 리뷰 컨텍스트에서 직접 독립 검증한다.
- BLOCKED, HIGH, MEDIUM 이슈가 남아 있으면 완료 처리하지 않는다.
- 검증이 완료되면 요청 파일을 `_done/`으로 이동하고 `_log.md`에 결과를 기록한다.
- 대표님의 결정이 필요한 문제가 발생하면 작업을 임의 확정하지 말고 `_blocked.md` 형식으로 기록한다.
