# 미션 기본 10개·예비 10개와 재도전 1회 라이브 E2E 검증

## 현재 처리 상태: 문항 콘텐츠 갭 해소 완료(2026-07-25) - 대표님 결정 대기 아님

**재조사 결과 정정**: 앞서 "학년별 활성 문항 13~17개뿐, 콘텐츠 자체 부족"이라고
결론 내렸던 것은 **불완전한 조사였다.** 대표님 지적대로 다시 확인한 결과,
`mission_questions`에는 `is_active=false`(`clinical_status='PENDING_REVIEW'`)
상태로 대표님이 이미 작성해 둔 문항 46개가 별도로 존재했다 - 콘텐츠 부족이
아니라 **활성화(검수 반영) 누락**이었다. 이 46개를 전수 검토(전부 정상 작성된
문항 확인) 후 활성화하고, 그래도 학년 1·2에 부족했던 태그(greeting/
future_dreams/school_life/study_concerns/digital_interests/peer_relations/
recurring_stories)에 신규 문항 11개만 최소 추가했다
(`supabase/migrations/20260742000000_mission_questions_activate_and_fill_gaps.sql`,
Dev 적용 완료).

**실제 검증 결과(코드 재구현이 아니라 실제 `selectFixedMissionQuestions()`
함수를 직접 호출)**: 1~6학년 전부 **PRIMARY 10 + RESERVE 10 = 정확히 20개**
확보 확인. 인접 학년 혼합·초기 질문 재사용·현재 상태 유지 없이, 학년별
고유 문항만으로 확정 정책을 충족한다.

Production에는 아직 미적용(이 세션의 표준 관행대로 Dev에서 먼저 검증) -
Production 반영은 별도 승인 필요.

## 현재 상태

- 장애 원인은 해당 미션 세션에 RESERVE 문항이 0개였던 것으로 분석됐다.
- 질문 소진 상태가 `서버 연결이 불안정해요`로 잘못 표시됐다.
- 커밋 `68bc467`에서 기본 10개·예비 10개와 보충 로직이 구현·Dev 배포됐다고 보고됐다.
- 독립 코드 리뷰는 PASS했으나 실제 STT·LLM·질문 진행을 포함한 라이브 E2E가 중단됐다.
- 동일 문항 재도전은 최대 1회라는 확정 스펙을 따라야 한다.
- 유효 답변 완료 기준은 10개이며 낮추면 안 된다.
- **[대표님 실기기 재현, 긴급 추가]** 김서현 계정에서 기존 미션을 9/10 상태로
  이어서 진행했을 때 "다음 질문을 준비하지 못했어요. 잠시 후 다시 해볼게요."가
  표시되고 더 이상 진행하지 못했다(대표님 캡처로 확인 - 재현 증거로만 사용,
  이 조사에서 김서현 실계정에 자동 접근하지 않는다).

  **[QA테스트로 재현·근본원인 확정 완료]** `/api/mission/answer`/`/api/mission/start`를
  QA테스트(5학년, childId `cde1b847-...`) 계정으로 직접 호출해 재현했다.
  - 1회 재도전 로직 자체는 정상 동작 확인: 문항의 첫 실패는 `answer_status=
    "skipped"`로 기록되고(재시도 허용), 같은 문항의 두 번째 실패에서만
    `"refused"`로 전환되며 예비 문항 승격을 시도한다 - 이 부분은 버그가 아니다.
  - **근본 원인은 문항 풀 자체의 절대량 부족이다.** Dev DB 실측:
    `mission_questions`(is_active=true) 전체 활성 문항 수는 **17개** 뿐이며,
    학년별로는 1학년=13, 2학년=13, 3학년=15, 4학년(김서현)=17, 5학년(QA테스트)=16,
    6학년=16개다. 세션 시작 시 PRIMARY 10개 + 가능한 만큼의 RESERVE를 배정하는데,
    이 학년별 전체 풀 크기 자체가 20에 못 미치므로 **세션 하나가 시작되는
    순간 그 학년의 활성 문항 전체가 이미 소진 상태로 배정된다.** 이 상태에서
    단 한 번이라도 "같은 문항 2회 연속 실패"(재도전 실패) 이벤트가 발생하면
    승격시킬 예비 후보가 세션 밖에도 전혀 남아있지 않아 즉시
    `MISSION_QUESTION_POOL_EXHAUSTED`가 뜬다(실측: 신선한 세션에서 문항 1개의
    2번째 실패만으로 즉시 재현됨).
  - 즉 "예비문항 보충 또는 남은 질문풀 재선정"은 코드상 정상 동작하지만,
    **재선정할 대상 자체가 DB에 존재하지 않는다** - 이건 코드 버그가 아니라
    콘텐츠(문항 데이터) 부족 문제다. 코드만으로는 존재하지 않는 문항을
    만들어낼 수 없다. 상세는 `requests/_blocked.md`의 004 항목 참고.

## 요구사항

1. 모든 지원 round type에서 세션 시작 시 다음을 보장한다.
   - PRIMARY 10개
   - RESERVE 10개

2. REFUSAL·NO_RESPONSE·회피 답변 처리:
   - 동일 질문 재도전 최대 1회
   - 두 번째에도 유효하지 않으면 해당 질문을 무효 처리
   - 즉시 RESERVE 질문으로 전환

3. 유효 답변 10개가 되기 전 RESERVE가 부족하면:
   - 남은 질문 풀에서 쿨다운과 중복 방지 규칙을 지키며 보충
   - 동일 질문 최근 반복 금지

4. 질문 풀 자체가 소진된 경우:
   - `MISSION_QUESTION_POOL_EXHAUSTED` 또는 기존 규약에 맞는 명시적 오류 기록
   - 세션과 진행률 보존
   - 네트워크 오류로 오해되는 문구 금지

5. `pickNextIndex=-1`에서 다음 상태를 구분한다.
   - 유효 답변 10개 완료
   - 비정상 질문 풀 소진
   - 동기화 지연 또는 데이터 오류

6. 최근 Dev 세션을 감사해 round type별 PRIMARY·RESERVE 배정 수를 확인한다.

7. 실제 E2E 검증이 끝나기 전 완료 처리하지 않는다.

## 검증 시나리오

2. 첫 질문에 REFUSAL
3. 같은 질문 1회 재시도 확인
4. 두 번째 REFUSAL 후 RESERVE 전환 확인

6. VALID 답변을 누적해 10개 완료 확인
7. 인위적으로 질문 풀 부족 조건을 구성해 중립 오류 확인
8. DB question history와 화면 순서 대조
9. HTTP 200 상태에서 연결불안 배너가 뜨지 않는지 확인
10. **(긴급 추가) QA테스트 계정으로 9/10 상태 + PRIMARY/RESERVE 모두 소진 상태를

    무효화해 RESERVE 승격을 유도하되, RESERVE 후보 자체를 사전에 고갈시켜
    둔 상태에서 진행) → 이 상태로 이어하기 시 정지·초기화 없이 실제로
    다음 질문이 준비되는지, 안 된다면 정확히 어느 코드 경로에서 막히는지
    확인한다.**
