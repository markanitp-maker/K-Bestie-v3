# 요청 제목

우리 아이 성장정보 v1 — 부모 전용 키·몸무게 기록 및 질병관리청 성장도표 비교

## 0. 완료 시 기대 결과 / 대표님 테스트 정상 프로세스

### 완료 시 기대 결과

- 기존 회원가입·아이 추가·온보딩에는 생년월일 입력을 추가하지 않는다.
- 부모가 부모 홈의 `키` 또는 `몸무게` 성장 카드를 처음 클릭할 때만 성장정보 초기 설정을 시작한다.
- 초기 설정에서 아이의 생년월일을 1회 입력받고, 기존 `child_profiles.gender`가 `NULL`인 아이만 성별도 함께 입력받는다.
- 생년월일·키·몸무게 수집 목적과 이용 범위를 명확히 고지하고 보호자 동의를 받은 뒤에만 성장정보를 저장한다.
- 부모는 측정일 기준으로 키와 몸무게를 직접 입력·수정·삭제할 수 있다.
- 측정일과 생년월일을 기준으로 아이의 정확한 연령/월령을 계산하고, 질병관리청 공식 `2017 소아청소년 성장도표` 기준으로 현재 위치를 비교한다.
- 부모 상세 화면에서 최소 다음 정보를 확인할 수 있다.
  - 측정 당시 만 나이/월령
  - 현재 키와 최신 측정일
  - 현재 몸무게와 최신 측정일
  - 동일 성별·연령 기준 키의 위치/백분위
  - 공식 기준에서 제공 가능한 또래 중앙값(50백분위) 키
  - 키와 몸무게가 동일 측정 기록에 함께 존재하는 경우 BMI 및 연령·성별 BMI 백분위
  - 공식 기준에서 제공 가능한 체중 관련 비교값
  - 과거 측정 기록과 성장 추세 그래프
  - 적용 성장도표 버전
- `정상/비정상`을 임의 판정하지 않고 공식 성장도표 기준의 객관적 위치와 중립적인 안내 문구를 제공한다.
- 성장정보 상세 화면과 데이터는 부모 역할만 조회·입력·수정·삭제할 수 있고 아이 역할에는 노출하지 않는다.
- 케이와 아이의 대화에서 키·몸무게를 자동 추출하거나 자동 저장하는 기능은 v1 범위에서 제외한다.
- 기존 부모 홈 `InsightGrid` 8개 대화 인사이트 카드, 미션, 자유대화, 리포트, 회원가입·온보딩에는 회귀가 없어야 한다.

### 대표님 테스트 정상 프로세스

1. 생년월일이 등록되지 않은 기존 부모 계정으로 로그인한다.
2. 부모 홈에서 새로 추가된 `키` 또는 `몸무게` 카드를 클릭한다.
3. 성장정보 최초 설정 모달이 열리고 생년월일 입력과 성장정보 수집·이용 안내가 표시되는지 확인한다.
4. 해당 아이의 `gender`가 `NULL`이면 성별 선택이 추가로 표시되고, 이미 성별이 있으면 다시 묻지 않는지 확인한다.
5. 동의하지 않은 상태에서는 생년월일·키·몸무게가 저장되지 않는지 확인한다.
6. 동의 후 생년월일을 저장하고 첫 측정일·키·몸무게를 입력한다.
7. 저장 후 부모 홈 카드에 최신 `키`, `몸무게` 값과 적절한 빈 상태/측정일 정보가 반영되는지 확인한다.
8. 성장 상세를 열어 측정 당시 연령/월령, 성장도표 비교, 백분위, 또래 중앙값, BMI/BMI 백분위, 적용 기준 버전이 표시되는지 확인한다.
9. 다른 날짜의 측정값을 2개 이상 추가하여 히스토리 목록과 성장곡선이 시간순으로 정상 표시되는지 확인한다.
10. 기존 기록을 수정·삭제했을 때 최신 카드 값과 그래프가 즉시 재계산되는지 확인한다.
11. 아이 계정으로 동일 아이의 성장정보 API/화면 접근을 시도하여 조회가 차단되는지 확인한다.
12. 신규 아이 추가/회원가입을 진행해 생년월일 필드가 추가되지 않았고 기존 플로우가 그대로 동작하는지 확인한다.

## 2. 목표

현재 내친구 케이에는 아이의 키·몸무게를 저장하거나 성장 흐름을 확인하는 기능이 없다. 부모가 필요할 때만 성장정보 기능을 선택적으로 시작하고, 아이의 생년월일·성별·측정일·키·몸무게를 기반으로 공식 성장도표와 비교하여 `우리 아이가 현재 어느 위치에 있고 시간에 따라 어떻게 성장하고 있는지`를 이해하기 쉽게 제공한다.

핵심 원칙은 다음과 같다.

```text
부모 홈 키/몸무게 카드 클릭
→ 최초 사용 여부 확인
→ 성장정보 수집·이용 안내 및 보호자 동의
→ 생년월일 1회 입력
→ gender NULL이면 성별 입력
→ 키/몸무게 + 측정일 입력
→ 측정 당시 연령/월령 계산
→ 공식 성장도표 기준 비교
→ 부모 전용 현재 상태 + 히스토리 + 성장곡선 표시
```

성장정보는 `아이를 평가하는 점수`가 아니라 부모가 공식 기준과 장기 추세를 참고하도록 돕는 정보다. 한 번의 측정값만으로 `정상/비정상`을 단정하지 않고, 백분위와 시간에 따른 성장 흐름을 중심으로 보여준다.

## 3. 요구사항

### 3-1. 부모 홈 키/몸무게 카드 신규 추가

- 현재 `app/parent/home/components/InsightGrid.tsx`의 8개 대화 기반 인사이트 카드는 유지한다.
- 기존 InsightGrid를 키/몸무게 카드로 대체하거나 축소하지 않는다.
- 부모 홈의 아이 기본정보/요약 영역에 `키`, `몸무게` compact card를 신규 추가한다.
- 초기 미등록 상태:
  - 키: `기록 없음`
  - 몸무게: `기록 없음`
- 등록 후:
  - 키: 최신 non-null 측정값 `NNN.N cm`
  - 몸무게: 최신 non-null 측정값 `NN.N kg`
- 카드 클릭 시 동일한 `우리 아이 성장정보` 상세 모달/화면으로 진입한다.
- 키와 몸무게가 서로 다른 날짜에 입력된 경우 각 카드의 최신값은 각각 가장 최근의 non-null 값으로 표시한다.

### 3-2. 최초 성장정보 설정 플로우

- 회원가입·아이 추가·기존 온보딩에는 생년월일 필드를 절대 추가하지 않는다.
- 성장 카드를 처음 클릭한 부모에게만 최초 설정 플로우를 표시한다.
- 필수 입력:
  - 생년월일
  - 성장정보 수집·이용 동의
- 조건부 입력:
  - `child_profiles.gender IS NULL`인 경우에만 `male` / `female` 성별 선택
- 이미 `gender`가 존재하면 최초 성장정보 설정에서 성별을 다시 묻지 않는다.
- 생년월일은 미래 날짜를 허용하지 않는다.
- 아이 연령 범위와 공식 성장도표 지원 범위를 검증하고 지원 범위를 벗어난 경우 임의 계산하지 않고 안내한다.
- 취소 시 어떠한 성장정보도 생성/저장하지 않고 기존 부모 홈으로 복귀한다.

### 3-3. 성장정보 전용 데이터 모델

부모 전용 접근 정책을 명확히 유지하기 위해 `birth_date`를 기존 `child_profiles`에 직접 추가하지 않고, 성장정보 전용 프로필을 별도 Source of Truth로 둔다.

#### 신규 `child_growth_profiles`

최소 권장 필드:

```text
id uuid PK
child_id uuid UNIQUE NOT NULL FK -> child_profiles.id ON DELETE CASCADE
birth_date date NOT NULL
growth_consent_version text NOT NULL
growth_consent_at timestamptz NOT NULL
created_at timestamptz NOT NULL
updated_at timestamptz NOT NULL
```

- 생년월일 Source of Truth는 `child_growth_profiles.birth_date`로 한다.
- 성별 Source of Truth는 기존 `child_profiles.gender`를 계속 사용하고 중복 저장하지 않는다.
- 별도 성장 프로필을 사용하는 이유:
  - 기존 `child_profiles_select`는 동일 가족 구성원 조회를 허용하므로 `child_profiles.birth_date` 추가 시 아이 역할에서도 컬럼이 노출될 수 있음.
  - 이번 정책은 성장정보를 부모 전용으로 확정했으므로 생년월일도 성장정보 경계 안에서 parent-only RLS로 보호한다.

#### 신규 `growth_measurements`

최소 권장 필드:

```text
id uuid PK
child_id uuid NOT NULL FK -> child_profiles.id ON DELETE CASCADE
measured_at date NOT NULL
height_cm numeric nullable
weight_kg numeric nullable
source text NOT NULL DEFAULT 'parent_manual'
standard_version text NOT NULL DEFAULT 'KDCA_2017'
created_at timestamptz NOT NULL
updated_at timestamptz NOT NULL
UNIQUE(child_id, measured_at)
CHECK(height_cm IS NOT NULL OR weight_kg IS NOT NULL)
```

- 같은 아이·같은 측정일은 하나의 measurement row를 Source of Truth로 사용한다.
- 같은 날짜에 키만 먼저 입력하고 이후 몸무게를 입력하면 새 row를 만들지 말고 기존 row를 update/upsert한다.
- 키·몸무게의 현재값을 `child_profiles` 등에 별도 중복 저장하지 않는다.
- 현재값은 `growth_measurements`에서 측정일 기준 최신 non-null 값을 조회하여 파생한다.
- `source`는 v1에서 `parent_manual`만 허용한다. 향후 `k_conversation_confirmed` 등의 확장을 고려하되 현재 구현하지 않는다.

### 3-4. 키·몸무게 입력/수정/삭제

- 부모는 성장 상세 화면에서 `새 기록 추가`를 통해 측정일·키·몸무게를 입력한다.
- 측정일 기본값은 오늘(KST)이지만 사용자가 과거 날짜로 변경할 수 있다.
- 키 단위: cm
- 몸무게 단위: kg
- UI는 소수 입력을 허용한다.
- 저장 시 서버에서도 숫자형·허용 범위·날짜를 재검증한다.
- 허용 범위는 하드코딩된 임의 값으로 아이 성장 여부를 판단하는 데 사용하지 말고, 명백한 입력 실수 방지를 위한 넓은 validation 범위로만 사용한다.
- 키 또는 몸무게 하나만 입력할 수 있다.
- BMI는 동일 measurement row에 키와 몸무게가 모두 있을 때만 계산한다.
- 서로 다른 날짜의 키와 몸무게를 임의 결합하여 BMI를 계산하지 않는다.
- 기존 기록은 부모가 수정·삭제할 수 있다.
- 삭제 후 최신값이 바뀌면 홈 카드와 상세 분석을 즉시 다시 계산한다.

### 3-5. 연령/월령 계산

- 계산 기준은 `birth_date`와 각 `measured_at`이다.
- 현재 날짜가 아니라 반드시 `측정 당시 나이`를 사용한다.
- 월령은 30일을 1개월로 나누는 근사 계산을 금지한다.
- 공식 질병관리청 성장도표 데이터에서 요구하는 연령/월령 정의와 binning 규칙을 확인한 뒤 동일하게 구현한다.
- 월말, 윤년, 생일 전후, 월령 경계에서 오류가 발생하지 않도록 테스트를 추가한다.
- UI에는 부모가 이해하기 쉬운 `만 N세 N개월` 형태를 우선 표시하고 필요 시 내부 계산 월령을 함께 사용한다.

### 3-6. 공식 성장도표 데이터 및 계산 엔진

- 기준 Source of Truth: 질병관리청·대한소아청소년과학회 `2017 소아청소년 성장도표` 공식 데이터.
- 2026-08 기준 질병관리청이 공식적으로 제공하는 성장도표와 성장상태 측정계산기를 기준으로 구현한다.
- 성장도표 데이터는 임의 블로그/커뮤니티/상업 사이트 값을 사용하지 않는다.
- 공식 다운로드 원본 데이터의 출처·버전·가공 방법을 코드 주석 또는 문서에 남긴다.
- 런타임 외부 API 호출에 의존하지 않고 프로젝트 내부의 versioned static standard data로 동작하도록 한다.
- 권장 경로 예:

```text
lib/growth/
  age.ts
  bmi.ts
  percentile.ts
  assessment.ts
  standards/
    kdca-2017/
      ...official normalized data
```

- `GROWTH_STANDARD_VERSION` 또는 동등한 단일 상수로 적용 기준을 명확히 관리한다.
- 향후 `2027 소아청소년 성장도표` 공표 후 기준 교체가 가능하도록 2017 데이터와 계산 로직을 강결합하지 않는다.
- LMS 계수를 공식 자료에서 제공하는 경우 공식 정의대로 계산한다.
- 공식 데이터가 특정 지표에 LMS가 아닌 다른 방식/표를 사용한다면 임의 LMS 변환이나 추정 계산을 하지 말고 공식 자료·공식 계산기 동작을 따른다.
- 공식 기준에서 지원되지 않는 연령/지표는 값을 추정 생성하지 않고 `해당 기준에서 제공되지 않음`으로 처리한다.

### 3-7. 부모 성장 상세 화면

성장 상세 화면에는 현재 기록이 있을 때 최소 다음을 제공한다.

#### 기본 정보

- 아이 이름
- 측정 당시 `만 N세 N개월`
- 최근 측정일
- 적용 성장도표: `2017 소아청소년 성장도표`

#### 키

- 최신 키
- 동일 성별·연령 기준 위치/백분위
- 공식 데이터에서 산출 가능한 경우 50백분위 값을 `또래 중앙값`으로 표시
- `평균보다 작다/크다`만 강조하는 UI를 피하고 현재 백분위와 추세를 함께 표시

#### 몸무게

- 최신 몸무게
- 공식 성장도표에서 해당 연령에 직접 제공되는 체중 비교 지표가 있을 때만 공식 기준으로 표시
- 단순 몸무게 숫자 하나만으로 비만/정상 여부를 판정하지 않는다.
- 체중 평가가 키와 결합된 공식 지표를 요구하면 해당 공식 기준을 따른다.

#### BMI

- 동일 측정일에 키와 몸무게가 모두 있는 경우만 계산
- BMI = kg / m² 기본 산식 적용
- 연령·성별 BMI 성장도표에 따라 백분위 및 공식 분류를 계산
- 공식 분류를 표시하는 경우 질병관리청 기준과 표현을 그대로 따르고 임의 임계값을 만들지 않는다.

#### 히스토리/성장 추세

- 과거 측정 기록을 최신순/시간순으로 확인 가능
- `recharts ^3.9.2`를 재사용하여 성장 추세 그래프 구현 가능
- 최소 키/몸무게 추세를 날짜축으로 표시
- 공식 백분위 곡선을 함께 표시하는 경우 공식 원본 데이터에 근거해 렌더링하고 임의 선을 생성하지 않는다.
- 기록이 1개뿐이면 `추세`를 단정하지 않는다.

### 3-8. 표현 정책 / 아동 신체 이미지 보호

- 부모 전용 화면이더라도 다음 표현은 금지한다.
  - `비정상입니다`
  - `문제가 있습니다`를 단일 측정값만으로 확정
  - `살쪘습니다`, `뚱뚱합니다`, `너무 말랐습니다` 등 가치판단 표현
  - 다이어트, 칼로리 제한, 체중 감량 목표 등 의료·영양 처방
  - 최종 키 예측 또는 성장 가능성 보장
- 우선 표현:
  - `같은 성별·연령 성장도표에서 약 N백분위에 있어요.`
  - `또래 중앙값은 약 Ncm예요.`
  - `한 번의 측정값보다 성장 흐름을 함께 확인하는 것이 중요해요.`
  - 공식 기준상 확인이 필요한 구간일 때 `성장도표상 낮은/높은 구간에 있어요. 이전 기록과 함께 확인해 주세요.`
- 의료적 판단이 필요한 상황을 앱이 확정 진단하지 않는다.
- 공식 기준상 상담 필요성을 안내할 근거가 있는 경우에만 `걱정되는 변화가 지속되면 소아청소년과 등 전문가와 상의해 주세요.` 정도의 참고 문구를 제공한다.

### 3-9. 부모 전용 접근 및 RLS

`child_growth_profiles`와 `growth_measurements`는 모두 RLS를 활성화한다.

- SELECT: 해당 아이 가족의 `owner_parent`, `parent`만 허용
- INSERT: 해당 아이 가족의 `owner_parent`, `parent`만 허용
- UPDATE: 해당 아이 가족의 `owner_parent`, `parent`만 허용
- DELETE: 해당 아이 가족의 `owner_parent`, `parent`만 허용
- 아이 역할은 SELECT 포함 전부 거부
- 다른 가족의 부모는 접근 거부
- service role은 서버 운영에 필요한 기존 프로젝트 규칙을 따르되 브라우저에 노출하지 않는다.
- RLS만 믿지 말고 부모 전용 API/route에서도 child-family-role 관계를 서버에서 검증한다.
- `GRANT`와 RLS 작성은 프로젝트 `AGENTS.md` 및 기존 migration 규칙을 따른다.

### 3-10. 개인정보 수집 동의 및 법적 문서 현행화

Antigravity 점검 결과 현재 법적 문서에는 아이 생년월일을 `수집하지 않는다`고 명시되어 있으므로 성장정보 기능 배포 전에 반드시 현행화한다.

대상:

- `lib/legal/documents/privacyPolicy.ts`
- `lib/legal/documents/childPrivacyConsent.ts`

현재 확인된 내용:

- 개인정보처리방침: 아이의 생년월일을 현재 수집하지 않는다고 명시
- 아이 개인정보 수집·이용 동의서: 아이의 생년월일을 현재 수집하지 않는다고 명시
- 키·몸무게·신체정보 수집 항목은 현재 별도 명시 없음

요구사항:

- 성장 기능에서 수집하는 항목을 명확히 추가한다.
  - 생년월일
  - 키
  - 몸무게
  - 측정일
  - 위 데이터로 계산되는 성장정보/BMI/백분위 등 파생값의 이용 목적
- 수집 목적을 `부모에게 아이의 성장 기록과 공식 성장도표 기반 비교 정보를 제공하기 위함`으로 한정한다.
- 성장 기능 최초 진입에서 별도 동의 UI를 제공한다.
- 동의 시 `growth_consent_version`, `growth_consent_at`을 저장해 감사 가능하게 한다.
- 동의하지 않은 사용자는 기존 서비스 전체를 그대로 사용할 수 있어야 한다.
- 성장정보 사용 중지/삭제 경로를 부모에게 제공하고, 삭제 요청 시 성장 측정 기록과 성장 전용 생년월일/동의 상태의 처리 정책을 일관되게 구현한다.
- 약관/동의 버전 변경이 기존 guardian consent를 임의로 덮어쓰지 않도록 현재 법적 문서 버전 관리 구조를 확인해 적용한다.

### 3-11. API / Source of Truth

구현 전 기존 API naming convention을 확인하여 최종 경로를 정하되 기능 책임은 다음처럼 분리한다.

- 성장 프로필 조회/생성/수정
- 측정 기록 조회/추가/수정/삭제
- 현재 요약 조회
- 성장도표 계산은 서버와 클라이언트에 서로 다른 구현을 중복 생성하지 않는다.

Source of Truth:

```text
성별                    = child_profiles.gender
성장기능 생년월일        = child_growth_profiles.birth_date
성장정보 동의            = child_growth_profiles.growth_consent_*
키/몸무게 원본 기록       = growth_measurements
현재 키/몸무게            = growth_measurements의 최신 non-null 값에서 파생
연령/월령                 = birth_date + measured_at에서 파생
BMI/백분위/평가            = 원본 측정값 + versioned 공식 성장도표에서 계산
성장도표 기준             = lib/growth/standards/<version>
```

- 동일 결과를 여러 테이블에 중복 저장하지 않는다.
- 계산값 캐시가 필요하다고 판단되더라도 원본 측정값을 최종 Source of Truth로 유지한다.

### 3-12. 기존 성별 NULL 아이 처리

Antigravity 실제 DB 집계:

- Production: 전체 44명 중 `gender IS NULL` 2명
- Dev: 전체 8명 중 `gender IS NULL` 3명

처리:

- 성장기능 최초 설정 시 gender NULL이면 보호자에게 성별을 함께 확인받는다.
- 저장 값은 기존 규격 `male` / `female`을 그대로 사용한다.
- 성장 기능을 사용하지 않는 기존 gender NULL 아이에게 강제 입력을 요구하지 않는다.

### 3-13. v1 이후 확장 경계

다음은 데이터 모델에서 확장 가능성만 고려하고 v1에서는 구현하지 않는다.

- 케이가 아이와 대화 중 `나 145cm 됐어`와 같은 발화를 감지하는 기능
- 케이가 성장정보를 자동 저장하는 기능
- 아이에게 키·몸무게·BMI·백분위·성장도표를 보여주는 기능
- 학교 건강검진 데이터 자동 연동
- 외부 의료기관/건강앱 연동
- 성장 예측 AI

향후 케이 대화 연동을 구현하더라도 아이 발화만으로 확정 저장하지 않고 별도 보호자 확인 정책을 선행한다.

- `lib/legal/documents/childPrivacyConsent.ts`

Antigravity 실제 점검 기준 관련 child profile schema는 Dev/Production 100% 동일하다.

- Dev 아이 8명 / gender NULL 3명

Production에는 직접 수동 데이터 보정이나 테이블 생성 없이 migration으로만 반영한다.

## 5. 금지사항

- 회원가입/아이 추가 단계에 생년월일 필드를 추가하지 않는다.
- 성장정보를 아이 화면에 노출하지 않는다.
- 아이 role에 성장정보 SELECT 권한을 부여하지 않는다.
- `child_profiles`에 키/몸무게 최신값을 중복 저장하지 않는다.
- parent-only 정책을 무시하고 `child_profiles.birth_date`를 단순 추가하지 않는다.
- 같은 날짜의 중복 measurement row를 무제한 생성하지 않는다.
- 서로 다른 날짜의 키와 몸무게를 결합하여 BMI를 만들지 않는다.
- 공식 근거가 없는 평균 키/몸무게 표를 직접 작성하지 않는다.
- 인터넷 블로그/커뮤니티 표를 성장 기준 데이터로 사용하지 않는다.
- 공식 데이터 범위 밖 값을 임의 보간·외삽하여 건강 판정을 생성하지 않는다.
- `정상/비정상`을 단순 평균 비교만으로 판정하지 않는다.
- 케이가 아이에게 몸무게를 먼저 묻거나 자동 저장하는 기능을 이번 Request에 포함하지 않는다.
- 의료 진단·치료·다이어트 조언을 생성하지 않는다.
- Production DB를 수동 ALTER/INSERT/UPDATE/DELETE하여 맞추지 않는다.
- 기존 InsightGrid, 미션, 자유대화, 리포트 구조를 성장 기능 때문에 불필요하게 리팩터링하지 않는다.

## 6. 모호성 처리

개발 중 아래 사항이 공식 자료나 현재 코드만으로 확정되지 않으면 추정 구현하지 않는다.

1. 특정 연령에서 사용할 공식 체중 비교 지표가 불명확한 경우
2. 공식 2017 성장도표의 월령 binning/LMS/percentile 산출 규칙이 불명확한 경우
3. 공식 계산기와 자체 계산 결과가 의미 있게 다른 경우
4. 법적 문서 버전 처리 또는 기존 사용자 재동의 범위가 현재 코드에서 불명확한 경우
5. parent-only RLS를 기존 family helper로 안전하게 표현할 방법이 불명확한 경우

이 경우 해당 부분을 `BLOCKED`로 표시하고 근거와 선택지를 보고한 뒤 임의 구현하지 않는다. 나머지 확정 범위까지 멋대로 확대하지 않는다.

- 동의 체크 전 저장 시도
- 미래 생년월일
- 오늘 측정
- 과거 측정
- 키만 입력
- 몸무게만 입력
- 키+몸무게 동시 입력
- 같은 날짜 재입력 → 중복 row가 아니라 update/upsert
- 측정값 수정
- 최신 기록 삭제 후 이전 기록으로 카드 fallback
- 모든 기록 삭제 후 `기록 없음` 복귀

### 7-2. 연령/성장도표 계산 QA

공식 질병관리청 성장상태 측정계산기를 기준 Oracle로 사용해 대표 fixture를 검증한다.

최소 포함:

- 남아/여아 각각
- 초등 저학년/중학년/고학년 연령대
- 생일 직전/당일/직후
- 월령 경계
- 윤년 생일 케이스
- 키 50백분위 부근
- 키 낮은/높은 백분위 구간
- BMI 50백분위 부근
- BMI 85/95백분위 경계 전후
- 공식 기준에서 지표가 제공되지 않는 케이스

PASS:

- 연령/월령 mapping 동일
- 공식 분류 동일
- 백분위 결과는 공식 계산기와 동일한 계산 규칙을 사용하며 표시 반올림 차이 외 의미 있는 차이 없음
- 차이가 있으면 허용오차를 임의 확대하지 말고 원인을 해결

### 7-3. BMI QA

- 동일 row에 키/몸무게 모두 존재 → BMI 계산
- 키만 존재 → BMI 미표시
- 몸무게만 존재 → BMI 미표시
- 키와 몸무게 최신 날짜가 서로 다름 → 서로 조합하여 BMI 계산 금지
- 0/음수/NaN/문자 입력 차단
- 단위 cm→m 변환 정확성 검증

### 7-4. RLS / 보안 QA

역할별 실제 Supabase 접근을 검증한다.

- owner_parent: 자신의 가족 아이 SELECT/INSERT/UPDATE/DELETE PASS
- parent: 자신의 가족 아이 SELECT/INSERT/UPDATE/DELETE PASS
- child: SELECT/INSERT/UPDATE/DELETE 모두 DENY
- 다른 가족 parent: 모두 DENY
- anon: 모두 DENY
- API에 다른 child_id 직접 주입 → DENY
- 브라우저에서 service role key 노출 0건

`child_growth_profiles`의 생년월일까지 아이 role이 직접 조회할 수 없는지 반드시 확인한다.

### 7-5. 동의 / 개인정보 QA

- 동의하지 않으면 growth profile 생성 0건
- 동의 후 consent version/time 저장
- 기존 서비스 사용에는 성장정보 동의가 강제되지 않음
- 개인정보처리방침에서 `생년월일 미수집`이라는 기존 문구가 새 정책과 충돌하지 않도록 현행화
- 아이 개인정보 수집·이용 동의서 현행화
- 성장정보 삭제 시 측정기록 및 성장 전용 프로필 처리 확인
- 일반 guardian consent와 growth consent가 서로 잘못 덮어쓰지 않음

### 7-6. UI/UX QA

- 모바일 PWA 기준 카드 크기/텍스트 잘림 없음
- PC 부모 홈 정상
- 키/몸무게 미등록 empty state
- 1건/다건 history
- 소수점 표시 일관성
- 긴 아이 이름 대응
- 그래프 overflow/축 잘림 없음
- 모달 열기/닫기/뒤로가기 정상
- 저장 중 중복 클릭 방지
- 오류 발생 시 입력값 유실 최소화
- `비정상`, 외모 평가, 체중 낙인 표현 미노출

### 7-7. 회귀 QA

반드시 확인:

- 회원가입 정상
- 신규 아이 추가 정상
- 아이 성별 입력 정상
- 기존 아이 설정 수정 정상
- 부모 홈 기존 InsightGrid 8개 정상
- 일일/주간 리포트 정상
- 미션 정상
- 자유대화 정상
- 부모/아이 role 전환 정상
- 기존 RLS 회귀 없음

### 7-8. Dev / Production 배포 QA

1. 신규 migration을 Dev에 먼저 적용
2. Dev schema 확인
3. Dev E2E/계산/RLS QA PASS
4. Production 적용 전 migration forward/rollback 영향 검토
5. 대표님 승인 후 Production 정식 migration 적용
6. Production schema가 Dev와 동일한지 read-only 검증
7. Production 실제 사용자 데이터에 수동 backfill하지 않음
8. 기존 사용자는 성장기능을 직접 시작하기 전 growth profile이 생성되지 않아야 함

## 10. 공식 기준 및 구현 시 재확인 사항

- 기준 기관: 질병관리청 / 대한소아청소년과학회
- 현재 적용 기준: `2017 소아청소년 성장도표`
- 질병관리청은 2017 성장도표용 성장상태 측정계산기와 산출프로그램을 제공하고 있다.
- 질병관리청은 `2027 소아청소년 성장도표` 개정·공표를 준비 중이므로 데이터/계산 모듈을 버전 교체 가능하게 설계한다.
- 구현 시작 시 공식 성장도표 다운로드 자료와 공식 측정계산기의 최신 제공 상태를 다시 확인하고, 공식 자료가 변경된 경우 변경 사실을 보고한 뒤 기준 버전을 확정한다.
