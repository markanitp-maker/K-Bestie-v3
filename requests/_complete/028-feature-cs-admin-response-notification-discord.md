# REQUEST #028 — CS 시스템 고도화: 관리자 답변·처리상태·사용자 알림·Discord 연동

- 상태: TODO
- 유형: 기능 고도화
- 우선순위: HIGH
- 대상: 아이 화면 / 부모 화면 / 관리자 화면 / Discord 운영 채널
- 핵심 방향: 기존 CS 시스템 재사용 및 운영 처리 기능 고도화

## 0. 완료 시 기대 결과 / 대표님 테스트 정상 프로세스

### 완료 시 기대 결과

기존 문의·건의·버그 접수가 단순 접수 기능에서 실제 운영 가능한 CS 처리 흐름으로 확장된다.

최종 흐름:

`사용자 접수 → Discord 신규 접수 알림 → 관리자 상태 변경/답변 → 사용자 알림 → 사용자가 상태·답변 확인 → 처리 완료`

정상 완료되면:

- 신규 접수를 Discord에서 빠르게 인지할 수 있다.
- 관리자가 접수 상태를 변경할 수 있다.
- 관리자가 사용자에게 공식 답변을 남길 수 있다.
- 아이와 부모는 자신의 접수 상태와 답변을 확인할 수 있다.
- 주요 상태 변경과 답변 등록 시 사용자 알림이 발생한다.
- Discord에는 개인정보나 문의 원문 전체가 노출되지 않는다.
- 기존 문의·건의·버그 시스템은 그대로 유지된다.

### 대표님 테스트 정상 프로세스

1. Dev 부모 앱 또는 아이 앱에서 문의·건의·버그 중 하나를 접수한다.
2. Discord 운영 채널에 신규 접수 알림이 1건 오는지 확인한다.
3. Discord 메시지에서 접수 유형, 접수번호, 출처와 관리자 바로가기를 확인한다.
4. 관리자 화면에서 해당 접수를 연다.
5. 상태를 `확인 중` 또는 `처리 중`으로 변경한다.
6. `사용자에게 보내는 답변`을 작성해 저장한다.
7. 사용자 계정으로 돌아가 앱 내 알림을 확인한다.
8. 알림을 눌러 해당 접수 상세로 이동한다.
9. 변경된 상태와 관리자 답변이 표시되는지 확인한다.
10. 관리자 내부 메모가 사용자 화면에 보이지 않는지 확인한다.
11. 관리자가 상태를 `처리 완료`로 변경한다.
12. 사용자에게 완료 상태와 알림이 정상 반영되는지 확인한다.

정상이라면:

- Discord 신규 접수 알림 정상
- 관리자 상태 변경 정상
- 관리자 공식 답변 정상
- 사용자 상태/답변 확인 정상
- 알림 클릭 시 해당 접수로 이동
- 아이/부모는 자신의 접수만 조회 가능
- 관리자 내부 메모 미노출
- Discord 개인정보 미노출
- 기존 CS 접수 기능 정상 유지

## 1. 목표

기존 문의·건의·버그 접수 시스템을 별도 시스템으로 재구축하지 않고, 다음 운영 기능을 추가한다.

- 신규 접수 Discord 운영 알림
- 관리자 처리 상태 관리
- 관리자 공식 사용자 답변
- 아이/부모의 내 접수 상태·답변 확인
- 주요 상태 변경 및 답변 알림
- 기존 Push 구조가 있을 경우 Push 연동
- 상태 변경 및 답변 감사 추적

Discord는 **신규 접수를 운영자가 인지하기 위한 단방향 알림 수단**으로만 사용한다.

## 2. 요구사항

### 접수 유형

기존 3개 유형을 그대로 유지한다.

```text
inquiry
suggestion
bug
```

사용자 표시:

```text
문의
건의
버그
```

신규 접수 유형은 추가하지 않는다.

### 처리 상태

기존 상태값이 있으면 재사용한다.

기본 정책:

```text
received
reviewing
in_progress
resolved
closed
```

아이 화면은 운영 용어 대신 쉬운 문구를 사용한다.

```text
received     → 접수됐어
reviewing    → 확인하고 있어
in_progress  → 처리하고 있어
resolved     → 처리가 끝났어
closed       → 확인이 끝났어
```

부모 화면은 일반적인 CS 상태 문구를 사용한다.

기존 상태 enum이 있으면 중복 생성하지 않는다.

### 관리자 상태 관리

관리자 접수 상세에서 상태 변경이 가능해야 한다.

상태 변경 시 최소 다음을 추적한다.

- 이전 상태
- 새 상태
- 변경 관리자
- 변경 시각

기존 audit/history 구조가 있으면 재사용한다.

### 관리자 공식 답변

관리자 상세에서 다음 두 영역을 명확히 분리한다.

```text
관리자 내부 메모
→ 운영자만 확인

사용자 답변
→ 해당 사용자에게 공개
```

사용자 답변에는 최소 다음 정보를 관리한다.

- 답변 내용
- 답변 관리자
- 답변 시각

답변 저장 시 사용자 알림을 생성한다.

관리자 내부 메모는 사용자에게 절대 노출하지 않는다.

### 사용자 내 접수 확인

아이와 부모는 **본인이 작성한 접수만** 조회할 수 있어야 한다.

목록에서 최소 확인:

- 접수 유형
- 제목 또는 식별 가능한 내용
- 접수일
- 현재 상태
- 관리자 답변 여부

상세에서 최소 확인:

- 접수번호
- 유형
- 제목
- 내용
- 첨부 이미지
- 접수일
- 현재 상태
- 관리자 답변
- 답변 등록일

아이 화면의 관리자 답변 제목:

`케이팀에서 답장이 왔어`

부모 화면:

`관리자 답변`

### 사용자 알림

다음 이벤트에서 사용자 알림을 생성한다.

1. 관리자 공식 답변 등록
2. 상태가 `in_progress`로 변경
3. 상태가 `resolved`로 변경

모든 상태 변경마다 반복 알림을 발생시키지 않는다.

기존 앱 내 알림 시스템을 우선 재사용하며, 알림 클릭 시 해당 접수 상세로 이동한다.

기존 PWA Push 또는 앱 Push 구조가 실제 사용 중이면 동일 이벤트에 연결한다.

Push가 없거나 권한이 없는 환경에서도:

- 앱 내 알림
- 내 접수 확인

은 독립적으로 정상 동작해야 한다.

### Discord 신규 접수 알림

문의·건의·버그 접수가 DB에 성공적으로 저장된 후 Discord webhook을 호출한다.

```text
사용자 접수
→ DB 저장 성공
→ Discord 알림
```

Discord 실패가 사용자 접수 성공을 rollback하거나 차단하면 안 된다.

Discord에는 최소 정보만 전달한다.

허용:

- 접수 유형
- 접수번호
- 제목 또는 짧은 요약
- 접수 출처
- 접수 시각
- 관리자 상세 바로가기

금지:

- 문의 원문 전체
- 이메일/전화번호
- 아이/부모 이름
- user_id / child_id / guardian_id
- 이미지 및 이미지 URL
- 관리자 내부 메모
- 인증 정보
- IP
- fingerprint

문의에 별도 제목이 없으면 내용 일부를 짧게 잘라 식별용 제목으로 사용할 수 있으나 민감정보 노출을 방지한다.

유형은 Discord에서 쉽게 구분 가능해야 한다.

```text
🔵 새로운 문의
🟠 새로운 건의
🔴 새로운 버그 신고
```

Discord 관리자 바로가기는 실제 관리자 route를 사용하며 관리자 인증을 거쳐야 한다.

### Discord Secret / 장애 처리

Webhook URL은 server-side 환경변수로만 관리한다.

예:

`DISCORD_SUPPORT_WEBHOOK_URL`

금지:

- 코드 하드코딩
- `NEXT_PUBLIC_`
- 클라이언트 bundle 노출
- Git 저장
- Secret 로그 출력

Webhook 실패 시:

- 사용자 접수 성공 유지
- 운영 흐름 blocking 금지
- Secret 없는 안전한 실패 로그만 기록
- 기존 retry infrastructure가 있으면 재사용

이번 기능을 위해 별도 복잡한 queue 시스템은 구축하지 않는다.

### 랜딩 문의

랜딩페이지 문의가 동일 CS 시스템을 사용하는 경우 Discord 알림도 동일하게 적용한다.

출처는 기존 구조를 기준으로 다음을 구분 가능해야 한다.

```text
landing
parent_app
child_app
```

랜딩 비로그인 사용자는 앱 알림/Push 대상이 아닐 수 있으므로 이 경우:

`랜딩 문의 → Discord 알림 → 관리자 처리`

까지 정상 동작하면 된다.

랜딩 문의 자동 이메일 답변 기능은 이번 범위에서 새로 만들지 않는다.

### 권한

일반 사용자:

허용:
- 본인 접수 목록/상세 조회
- 본인 접수 상태 조회
- 본인에게 공개된 관리자 답변 조회

금지:
- 다른 사용자 접수 조회
- 다른 사용자 답변 조회
- 상태 변경
- 관리자 내부 메모 조회

관리자는 기존 관리자 권한 체계를 사용하여:

- 전체 접수 조회
- 상태 변경
- 사용자 답변 작성
- 관리자 내부 메모 작성
- 첨부 이미지 조회

가 가능해야 한다.

클라이언트 필터만으로 ownership을 보장하지 않는다.

## 3. 기존 구조 확인

구현에 직접 필요한 범위만 확인하고 기존 구조를 우선 재사용한다.

확인 대상:

- `support_requests` 또는 동일 목적 구조
- 문의/건의/버그 type 구조
- 기존 status 구조
- 관리자 CS 목록/상세
- 관리자 내부 메모
- 사용자 `내 접수 확인`
- 이미지 첨부/Storage
- 앱 내 알림
- 기존 PWA Push 또는 Push
- server-side notification utility
- Discord webhook 관련 기존 코드
- 아이/부모 인증 및 ownership
- child/guardian 관계
- RLS
- 관리자 audit/history
- 환경변수 관리 방식

코드에서 확인 가능한 내용은 추측하지 않는다.

기존 구조가 있으면 재사용하고 관련 없는 영역까지 조사 범위를 확대하지 않는다.

## 5. 모호성 처리

Request와 현재 코드만으로 판단 가능하면 기존 구조에 맞춰 진행한다.

다음 상황에서는 관련 코드와 필요한 Skill/Reference만 추가 확인한다.

- 기존 상태/audit 구조가 여러 방식으로 존재
- 관리자 공식 답변 저장 구조가 이미 존재하는지 불명확
- 아이/부모 알림 대상 결정 방식이 불명확
- Push 코드가 존재하지만 실제 활성 구조인지 불명확
- RLS와 server ownership 검증이 여러 경로로 존재
- Discord 관련 기존 utility 재사용 가능 여부가 불명확
- 랜딩 문의의 비로그인 ownership 처리와 기존 구조가 충돌

Reference까지 확인해도 다음 위험이 남으면 임의 구현하지 않는다.

- 다른 사용자 데이터 노출 가능성
- 관리자 내부 메모 노출 가능성
- 기존 CS 데이터 또는 상태 호환성 문제
- 알림 중복 가능성
- Push 대상 사용자 판단 오류
- 개인정보가 Discord로 전송될 가능성

이 경우 다음만 보고한다.

1. 불명확한 지점
2. 가능한 선택지
3. 선택지별 실제 차이
4. 기존 구조 기준 권장 방향

## 6. QA

`qa-scope` Skill을 적용하여 실제 최종 diff 위험도에 맞는 최소 충분 QA만 수행한다.

이번 Request의 필수 Gate:

- 문의/건의/버그 신규 접수 시 Discord 알림 정상
- 동일 신규 접수에 불필요한 Discord 중복 알림 없음
- Discord 금지 개인정보/이미지 정보 0건
- Discord 실패 시 사용자 접수 및 DB 저장 정상 유지
- 관리자 상태 변경 정상
- 상태 변경 이력 추적 정상
- 관리자 공식 답변 저장 정상
- 관리자 내부 메모와 사용자 답변 분리
- 본인 접수 상태/답변 조회 정상
- 다른 사용자 request ID 직접 접근 차단
- 관리자 답변 알림 정상
- `in_progress` / `resolved` 알림 정상
- 알림 클릭 시 해당 접수 상세 이동
- 기존 Push 구조를 사용한 경우 Push/deep-link 정상
- RLS/ownership 변경이 있으면 해당 권한 검증 필수
- 기존 CS 흐름을 직접 변경한 경우 영향받은 범위만 회귀 검증

## 7. 완료 조건

- 관리자가 접수 상태 변경 가능
- 상태 변경 주체/시각/이전·신규 상태 추적 가능
- 관리자 공식 사용자 답변 작성 가능
- 관리자 내부 메모와 공개 답변 완전 분리
- 아이/부모가 본인 접수 상태 확인 가능
- 아이/부모가 관리자 답변 확인 가능
- 주요 상태 변경/답변 등록 시 사용자 알림
- 알림에서 해당 접수 상세 이동
- 기존 Push 구조가 있으면 Push 연동
- Push 미지원 환경에서도 CS 조회 정상
- 문의/건의/버그 신규 접수 Discord 알림
- Discord 장애가 사용자 접수에 영향 없음
- Discord 개인정보 및 Secret 노출 없음
- 타 사용자 접수/답변 접근 차단
- 랜딩 문의가 기존 CS에 연결되어 있다면 동일 Discord 운영 알림 적용
- 기존 CS 및 관련 기능 보존
- 중복 CS 시스템 생성 없음

위 조건과 필수 Gate가 충족되면 작업을 종료한다.

요구사항을 넘어선 추가 기능은 구현하지 않는다.
