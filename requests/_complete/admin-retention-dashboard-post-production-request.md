# 관리자 사용자 리텐션 데이터 감사 및 대시보드 후속 구현

## 1. 작업 목적

프로덕션 배포 일정은 유지하되, 출시 첫날부터 사용자 행동과 리텐션을 계산할 수 있는 원천 데이터가 누락되지 않도록 사전 감사한다.

전체 리텐션 대시보드 신규 개발은 프로덕션 배포 이후 별도 단계로 진행한다.

본 작업은 신규 요구사항이 아니라 기존에 확정된 관리자 사용자 리텐션 기능의 누락 사항을 복구하는 작업이다.

---

## 2. 최우선 원칙

1. 현재 진행 중인 프로덕션 배포와 최종 검증을 우선 완료한다.
2. 전체 리텐션 대시보드 개발을 현재 프로덕션 배포 범위에 끼워 넣지 않는다.
3. 단, 프로덕션 배포 전에 출시 첫날부터 필요한 리텐션 원천 데이터를 기존 DB에서 산출할 수 있는지 반드시 읽기 전용으로 감사한다.
4. 기존 데이터만으로 필수 지표 산출이 불가능한 경우에만 최소 이벤트 로그 수집을 추가한다.
5. 최소 로그 보완이 필요하더라도 관리자 화면, 차트, 코호트 UI는 배포 후 구현한다.
6. 프로덕션 배포 이후 본 문서의 대시보드 구현 단계로 즉시 전환한다.
7. 기존 인증, 미션, 자유대화, 리포트, 놀이, 황금열쇠, 관리자 기능의 동작을 변경하거나 회귀시키지 않는다.

---

## 3. 작업 단계

### Phase 1. 프로덕션 배포 전 원천 데이터 감사

코드와 DB를 읽기 전용으로 조사하여 다음 사용자 행동을 사용자·아이·세션·발생 시각 기준으로 산출할 수 있는지 확인한다.

#### 필수 행동 데이터

- 부모 회원가입
- 부모 로그인 및 실제 방문
- 아이 로그인 또는 아이 프로필 기준 실제 사용
- 미션 시작
- 미션 유효 답변 발생
- 미션 완료
- 자유대화 시작
- 자유대화 종료
- 자유대화 실제 사용 시간
- 일일 리포트 조회
- 주간 리포트 조회
- 월간 리포트 조회
- 놀이 시작
- 놀이 이어하기
- 놀이 완료
- 황금열쇠 획득
- 황금열쇠 사용
- 마지막 활동 시각
- 활동일 기준 연속 접속일

#### 감사 기준

각 행동마다 아래 항목을 표로 정리한다.

| 항목 | 내용 |
|---|---|
| 행동명 | 측정할 사용자 행동 |
| 현재 데이터 소스 | 테이블, 뷰, RPC, 로그 또는 API |
| 사용자 식별자 | parent user_id 등 |
| 아이 식별자 | child_id |
| 세션 식별자 | mission/session/play attempt ID 등 |
| 발생 시각 | created_at, started_at, completed_at 등 |
| 중복 제거 기준 | 동일 세션·동일 이벤트 중복 처리 방식 |
| 현재 산출 가능 여부 | 가능 / 부분 가능 / 불가능 |
| 누락 위험 | 리텐션 계산에 미치는 영향 |
| 보완 필요 여부 | 없음 / 최소 로그 필요 |

#### 필수 확인 사항

- 로그인 성공 로그만으로 실제 서비스 사용자를 과대 계산하지 않는지 확인한다.
- 단순 페이지 새로고침이 방문 횟수로 중복 집계되지 않도록 기준을 정한다.
- 부모와 아이 활동을 구분할 수 있는지 확인한다.
- 하나의 부모 계정에 여러 아이가 연결된 경우 아이별 활동이 분리되는지 확인한다.
- Dev, Preview, Production 데이터가 섞이지 않는지 확인한다.
- 관리자, 개발자, QA, 자동화 테스트 계정이 실제 베타 사용자 지표에 포함되지 않도록 식별할 수 있는지 확인한다.
- 타임존은 모든 관리자 지표에서 `Asia/Seoul` 기준 날짜로 계산한다.
- soft delete, 가족 연결 해제, 아이 삭제가 과거 리텐션 데이터에 미치는 영향을 확인한다.
- 원시 대화 데이터 7일 파기 정책과 무관하게 행동 지표는 대화 내용 없이 유지할 수 있는 구조인지 확인한다.
- 대화 원문, 보정 원문, 민감한 아이 발화 내용은 리텐션 이벤트에 저장하지 않는다.

### Phase 1-A. 최소 이벤트 로그 보완 조건

기존 DB만으로 필수 행동을 정확히 계산할 수 없는 경우에만 최소 이벤트 로그를 추가한다.

#### 권장 이벤트 구조

기존 이벤트 테이블이 있으면 재사용하고, 신규 생성이 필요한 경우 프로젝트의 기존 네이밍 규칙을 따른다.

최소 필드:

- `id`
- `event_name`
- `user_id`
- `child_id`
- `session_id`
- `event_date`
- `occurred_at`
- `environment`
- `metadata`
- `created_at`

#### 이벤트 설계 원칙

- `event_name`은 허용된 값만 사용한다.
- 동일 행동의 이벤트명이 화면이나 API마다 달라지지 않도록 중앙 상수로 관리한다.
- `metadata`에는 리텐션 계산에 필요한 최소 정보만 저장한다.
- 대화 원문, 음성, 이미지, 리포트 본문, 부모 질문 내용은 저장하지 않는다.
- 서버에서 확정 가능한 이벤트는 클라이언트가 아니라 서버에서 기록한다.
- 클라이언트 이벤트는 중복 전송을 고려하여 idempotency 기준을 둔다.
- 이벤트 기록 실패가 핵심 사용자 기능 실패로 이어지지 않도록 비차단 방식으로 처리하되, 실패 로그는 남긴다.
- RLS 또는 서버 전용 쓰기 권한을 적용하여 사용자가 다른 사용자의 이벤트를 읽거나 조작하지 못하게 한다.
- 서비스 역할 키를 클라이언트에 노출하지 않는다.

#### 배포 전 최소 완료 기준

- 필수 행동 데이터 산출 가능 여부 감사 완료
- 치명적인 데이터 누락 항목만 최소 로그로 보완
- 타입 검사 통과
- 빌드 통과
- 관련 핵심 플로우 회귀 테스트 통과
- 프로덕션 배포 차단 요소가 없다는 결론 문서화

## 6. 리텐션 정의

### 6.1 가입 코호트 기준

- 코호트 시작일은 부모의 승인 완료일 또는 실제 서비스 최초 사용일 중 제품 분석에 적합한 기준을 선택한다.
- 어떤 기준을 선택했는지 UI 도움말과 코드 주석에 명확히 기록한다.
- 승인 대기 기간이 길어 가입일 기준 리텐션이 왜곡되지 않도록 한다.
- 기본 권장 기준은 `승인 후 최초 핵심 행동 발생일`이다.

### 6.2 활성 사용자 정의

단순 로그인 성공만으로 활성 사용자로 계산하지 않는다.

다음 핵심 행동 중 하나 이상 발생한 경우 해당 날짜의 활성 사용자로 계산한다.

#### 아이 활성 행동

- 미션 시작
- 미션 유효 답변
- 미션 완료
- 자유대화 시작
- 자유대화 실제 진행
- 놀이 시작
- 놀이 완료

#### 부모 활성 행동

- 관리자 승인이 아닌 일반 사용자 로그인 후 부모 홈 진입
- 일일·주간·월간 리포트 조회
- 오늘의 대화거리 조회
- 아이 정보 또는 보호자 설정의 실제 저장
- 서비스 사용과 직접 관련된 부모 행동

### 6.3 D1·D3·D7·D14

- Day 0: 코호트 시작일
- D1: Day 1에 활성 행동이 한 번 이상 발생한 사용자
- D3: Day 3에 활성 행동이 한 번 이상 발생한 사용자
- D7: Day 7에 활성 행동이 한 번 이상 발생한 사용자
- D14: Day 14에 활성 행동이 한 번 이상 발생한 사용자
- 부모와 아이 리텐션을 별도로 계산한다.
- 아이 리텐션은 child_id 기준으로 계산한다.
- 부모 리텐션은 user_id 기준으로 계산한다.

### 6.4 2주 지속률

베타 핵심 KPI 확인을 위해 다음 지표를 제공한다.

- 최초 사용 후 14일 이내 최소 7개 활동일을 기록한 아이 수와 비율
- 최초 사용 후 2주차에도 핵심 행동이 발생한 아이 수와 비율
- 두 정의를 혼합하지 말고 별도 지표로 표시한다.

- 민감한 아이 감정, 사건, 친구 관계, 리포트 본문은 이 화면에서 노출하지 않는다.

## 10. 데이터 집계 및 성능

- 관리자 화면 진입 때마다 전체 원시 테이블을 클라이언트에서 직접 집계하지 않는다.
- 서버 전용 API, SQL 뷰, RPC 또는 사전 집계 테이블을 사용한다.
- 초기 베타 규모에서는 정확성을 우선하되, 데이터 증가를 고려해 인덱스를 설계한다.
- `user_id`, `child_id`, `event_name`, `event_date`, `occurred_at`, `environment` 기준 인덱스를 검토한다.
- 동일 필터 요청에 대한 불필요한 반복 쿼리를 줄인다.
- 관리자 API 응답에 개인정보가 과도하게 포함되지 않도록 필요한 필드만 반환한다.
- 모든 집계 쿼리는 `Asia/Seoul` 날짜 경계를 일관되게 적용한다.
- 일별 집계와 상세 합계가 불일치하지 않도록 하나의 공통 정의를 재사용한다.

## 11. 권한 및 보안

- 관리자 권한이 없는 사용자는 페이지와 API 모두 접근할 수 없어야 한다.
- 클라이언트에서 메뉴를 숨기는 것만으로 권한을 처리하지 않는다.
- 관리자 API에서 서버 측 권한 검증을 수행한다.
- RLS를 우회해야 하는 집계는 서버 전용 경로에서만 실행한다.
- 서비스 역할 키와 DB 비밀번호를 브라우저 번들에 포함하지 않는다.
- 관리자 조회 행위는 필요 시 감사 로그에 남길 수 있도록 구조를 고려한다.
- 외부 분석 서비스로 아동 사용자 행동 데이터를 전송하지 않는다.
- 신규 외부 분석 SDK를 임의 도입하지 않는다.

## 12. UI/UX 요구사항

- 기존 관리자 페이지 디자인 시스템을 재사용한다.
- 상단에 핵심 KPI 카드를 배치한다.
- 카드 아래에 활성 사용자 추이, 코호트 리텐션, 핵심 행동 퍼널을 배치한다.
- 사용자별 목록에서 행을 클릭하면 상세 패널 또는 상세 페이지로 이동한다.
- 수치는 천 단위 구분을 적용한다.
- 퍼센트는 소수점 첫째 자리까지 표시하되, 표본이 작으면 실제 인원을 더 강조한다.
- 지표명 옆 도움말에서 계산 기준을 확인할 수 있게 한다.
- 로딩, 데이터 없음, 오류 상태를 명확히 분리한다.
- 오류 발생 시 빈 화면으로 보이지 않도록 원인과 재시도 버튼을 제공한다.
- 작은 표본의 급격한 비율 변화를 과도하게 강조하지 않는다.

## 13. 테스트 시나리오

### 13.1 데이터 정확성

1. 신규 부모와 아이를 생성한다.
2. 최초 핵심 행동일을 Day 0으로 기록한다.
3. Day 1, Day 3, Day 7, Day 14 활동 데이터를 테스트 데이터로 구성한다.
4. 각 D 리텐션 분자와 분모가 예상값과 일치하는지 확인한다.
5. 부모와 아이 수치가 섞이지 않는지 확인한다.
6. 한 부모에게 두 아이가 있을 때 아이별로 정확히 계산되는지 확인한다.
7. 동일 세션 이벤트가 중복 기록되어도 한 번만 계산되는지 확인한다.
8. 자정 전후 활동이 KST 기준 날짜로 정확히 분리되는지 확인한다.
9. 내부 계정 제외 전후 수치가 정확히 변하는지 확인한다.
10. 탈퇴 또는 연결 해제 후에도 과거 집계가 정책대로 유지되는지 확인한다.

## 16. 작업 금지 사항

- 현재 프로덕션 배포 전에 전체 대시보드를 무리하게 끼워 넣지 않는다.
- 데이터 확인 없이 완료로 보고하지 않는다.
- 비율만 표시하고 실제 인원을 생략하지 않는다.
- 로그인 성공만으로 활성 사용자를 정의하지 않는다.
- 부모와 아이 리텐션을 하나로 합쳐서만 표시하지 않는다.
- 관리자·QA·자동화 계정을 실제 베타 사용자 지표에 포함하지 않는다.
- UTC 날짜를 그대로 사용하여 한국 날짜를 왜곡하지 않는다.
- 대화 원문이나 민감한 아이 정보를 이벤트 로그에 저장하지 않는다.
- 외부 분석 SDK를 임의 도입하지 않는다.
- 서비스 역할 키를 클라이언트에 노출하지 않는다.
- 기존 데이터나 테이블을 근거 없이 삭제하거나 초기화하지 않는다.
- 프로덕션 데이터에 테스트 이벤트를 남긴 채 완료하지 않는다.
- 차트와 상세 표의 수치가 서로 다른 정의를 사용하지 않는다.
- Phase 1 감사만 수행하고 Phase 2 후속 작업을 누락하지 않는다.
