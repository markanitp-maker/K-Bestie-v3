# Request: 관리자 문의·건의·버그 접수 메뉴 분리

## 1. 작업 목적

현재 관리자 사이드바의 `문의·건의·버그 접수` 메뉴 하나에서 문의, 건의, 버그 데이터가 모두 함께 표시되고 있다.

운영자가 유형별 접수 건을 더 빠르게 확인하고 처리할 수 있도록 관리자 사이드바와 각 목록 화면을 아래 3개 메뉴로 분리한다.

- 문의 접수
- 건의 접수
- 버그 접수

기존 데이터와 DB 구조는 유지하고, 접수 유형(type) 기준으로 화면과 API 조회 범위만 분리한다.

---

## 2. 현재 문제

현재 화면에서는 다음 문제가 있다.

- 문의·건의·버그가 한 화면에 함께 표시됨
- 유형 필터를 매번 선택해야 함
- 운영자가 처리 대상 유형을 즉시 구분하기 어려움
- 사이드바 메뉴만 보고는 유형별 미처리 건수를 알기 어려움
- 삭제·상태 변경·검색 시 다른 유형 데이터가 함께 노출될 수 있음

---

## 3. 변경 후 사이드바 구조

기존 메뉴:

```text
문의·건의·버그 접수
```

기존 통합 메뉴는 제거하고 아래 메뉴 3개를 추가한다.

```text
문의 접수
건의 접수
버그 접수
```

권장 순서:

```text
운영
├─ 문의 접수
├─ 건의 접수
├─ 버그 접수
├─ 리포팅 수동 실행
├─ 이벤트 현황
└─ ...
```

기존 관리자 레이아웃, 모바일 드로어, 현재 선택 메뉴 강조 스타일을 그대로 사용한다.

---

## 4. 라우트 요구사항

프로젝트의 현재 라우팅 구조를 먼저 확인한 뒤 아래와 같은 독립 라우트로 분리한다.

권장 예시:

```text
/admin/inquiries
/admin/suggestions
/admin/bugs
```

기존 통합 라우트가 존재한다면 다음 중 한 방식으로 처리한다.

1. `/admin/requests` 등 기존 통합 라우트는 `/admin/inquiries`로 리다이렉트
2. 내부 링크가 남아 있다면 새 라우트로 모두 교체
3. 외부 북마크 호환이 필요하면 기존 라우트에서 유형 선택 화면을 제공

임의로 새 테이블을 만들거나 기존 접수 데이터의 type 값을 변경하지 않는다.

---

## 5. 유형별 조회 기준

기존 접수 테이블과 API를 유지하고, 저장된 유형 값 기준으로 분리한다.

프로젝트에서 실제 사용하는 type 값과 enum을 먼저 확인한다.

예시:

```text
문의: inquiry
건의: suggestion
버그: bug
```

또는 기존 한글 값:

```text
문의
건의
버그
```

실제 Production DB의 값을 확인해 현재 값과 정확히 일치시키며, 추측 enum을 새로 만들지 않는다.

### 문의 접수 화면

문의 유형 데이터만 조회한다.

```text
type = 문의 유형
deleted_at is null
```

### 건의 접수 화면

건의 유형 데이터만 조회한다.

```text
type = 건의 유형
deleted_at is null
```

### 버그 접수 화면

버그 유형 데이터만 조회한다.

```text
type = 버그 유형
deleted_at is null
```

각 화면에서 다른 유형 데이터가 섞이면 실패로 처리한다.

---

## 6. 목록 화면 공통 기능

세 화면은 동일한 공통 목록 컴포넌트 또는 공통 서비스 레이어를 사용하되, 고정된 접수 유형만 다르게 전달한다.

각 화면에서 아래 기능을 유지한다.

- 검색
- 상태 필터
- 접수자 필터
- 접수번호 표시
- 접수자 이름과 계정 유형 표시
- 제목 또는 내용 요약
- 접수일 표시
- 처리 상태 표시
- 상세 보기
- 상태 변경
- 개별 삭제
- 다중 선택
- 선택 삭제
- 페이지네이션
- CSV/XLSX 다운로드 기능이 있다면 유형별 분리
- 모바일 반응형 동작

기존 통합 화면의 `모든 유형` 드롭다운은 각 분리 화면에서 제거한다.

각 화면의 유형은 고정값이며 사용자가 다른 유형으로 변경할 수 없게 한다.

---

## 7. 화면 제목과 문구

### 문의 접수

```text
문의 접수 목록
```

설명 예시:

```text
사용자가 접수한 문의를 확인하고 처리합니다.
```

### 건의 접수

```text
건의 접수 목록
```

설명 예시:

```text
서비스 개선을 위해 접수된 건의를 확인하고 처리합니다.
```

### 버그 접수

```text
버그 접수 목록
```

설명 예시:

```text
서비스 오류 및 기능 장애 신고를 확인하고 처리합니다.
```

기존 목록 컬럼은 유지한다.

권장 컬럼:

```text
선택
접수번호
접수자
제목/내용 요약
접수일
상태
액션
```

유형이 고정된 화면에서는 `유형` 컬럼을 제거해도 된다.

단, 공통 컴포넌트 구조상 유지가 더 안전하면 표시해도 되지만 각 화면의 고정 유형만 보여야 한다.

---

## 8. 상태 및 처리 기능

기존 상태 값과 상태 변경 로직을 그대로 유지한다.

예시:

```text
확인 중
처리 중
처리 완료
종료
```

새 상태 enum을 임의로 추가하거나 기존 상태를 일괄 변경하지 않는다.

상태 변경 시:

- 기존 API와 감사 로그 유지
- 접수 유형이 현재 화면 유형과 일치하는지 서버에서 재검증
- 다른 유형 ID를 조작해 변경하지 못하도록 차단
- 성공 후 현재 목록만 갱신

---

## 9. 삭제 기능 연동

이번 메뉴 분리 작업은 기존에 확정한 관리자 운영 요청 데이터 소프트 삭제 정책과 연결한다.

각 화면의 삭제 버튼은 아래 규칙을 따른다.

- 물리 삭제 금지
- `deleted_at` 기록
- `deleted_by` 기록
- `delete_reason` 기록
- 일반 목록에서 즉시 숨김
- 휴지통에서 30일 이내 복구 가능
- 삭제·복구 감사 로그 기록
- 30일 후 자동 영구 삭제 정책 유지

개별 삭제 및 선택 삭제 모두 현재 화면의 고정 유형에 해당하는 데이터만 처리해야 한다.

다른 유형의 ID가 요청에 섞이면 서버에서 차단한다.

---

## 10. 휴지통 연동

기존 관리자 휴지통이 있다면 유형 필터에서 아래 3개 유형을 독립적으로 선택할 수 있게 한다.

```text
문의
건의
버그
```

복구 후 데이터는 원래 유형의 메뉴로 돌아가야 한다.

예시:

- 문의 복구 → 문의 접수 목록
- 건의 복구 → 건의 접수 목록
- 버그 복구 → 버그 접수 목록

기존 통합 휴지통 구조는 유지해도 된다.

---

## 11. 미처리 건수 배지

가능하면 각 사이드바 메뉴에 미처리 건수 배지를 표시한다.

예시:

```text
문의 접수  3
건의 접수  1
버그 접수  2
```

배지 기준은 프로젝트의 기존 미처리 상태 정의를 그대로 사용한다.

예:

```text
status not in ('처리 완료', '종료')
and deleted_at is null
```

실제 상태 enum을 확인한 뒤 적용한다.

배지 조회가 메뉴 렌더링 성능을 저하시키지 않도록 기존 관리자 요약 API 또는 단일 집계 쿼리를 활용한다.

---

## 12. API 및 서비스 레이어

기존 API를 재사용할 수 있으면 공통 API에 고정 type 파라미터를 서버에서 주입한다.

가능한 구조 예시:

```text
GET /api/admin/inquiries
GET /api/admin/suggestions
GET /api/admin/bugs
```

또는 공통 내부 서비스:

```ts
getAdminRequests({
  type: "inquiry",
  status,
  assignee,
  search,
  page,
  pageSize,
  includeDeleted: false,
})
```

주의사항:

- 클라이언트 query string의 type만 신뢰하지 않는다.
- 라우트별 허용 type을 서버에서 고정한다.
- 관리자 인증과 권한 검사를 유지한다.
- Production Service Role Key를 클라이언트에 노출하지 않는다.
- 기존 RLS와 관리자 접근 정책을 확인한다.
- 다른 유형 데이터가 API 응답에 포함되지 않게 한다.

---

## 13. 데이터 보존 및 마이그레이션 정책

이번 작업에서는 기존 접수 데이터를 변경하지 않는다.

금지사항:

- 기존 문의·건의·버그 데이터 삭제 금지
- 접수번호 변경 금지
- 접수자 변경 금지
- 접수일 변경 금지
- 상태 변경 금지
- 유형 값 일괄 변경 금지
- 새 테이블로 데이터 강제 이전 금지
- 기존 Production 데이터 초기화 금지

DB migration이 필요한 경우는 소프트 삭제 컬럼 또는 인덱스가 아직 없는 경우로 제한한다.

기존 pending migration 전체를 일괄 적용하지 않는다.

---

## 14. 성능 및 인덱스

접수 데이터가 증가해도 유형별 목록이 느려지지 않게 실제 테이블 구조를 확인한다.

필요한 경우 아래 조건을 고려한 인덱스를 추가한다.

```text
type
status
created_at
deleted_at
```

예시:

```sql
create index if not exists idx_requests_type_deleted_created
on <actual_table_name> (type, deleted_at, created_at desc);
```

실제 테이블명과 컬럼명을 확인한 뒤 작성하며 추측 SQL을 Production에 적용하지 않는다.

---

## 15. 모바일 및 반응형

모바일 관리자 화면에서도 3개 메뉴가 각각 독립적으로 표시되어야 한다.

확인 항목:

- 모바일 드로어 메뉴 노출
- 선택 메뉴 강조
- 목록 가로 스크롤 또는 카드형 변환
- 삭제 모달 정상 표시
- 다중 선택 정상 동작
- 필터 영역 줄바꿈
- 긴 제목/내용 요약 말줄임
- 상태 배지 깨짐 없음

---

## 16. 테스트 요구사항

### 16.1 데이터 분리 검증

Development와 Production의 기존 데이터를 기준으로 유형별 건수를 먼저 확인한다.

각 메뉴에서 다음을 검증한다.

#### 문의 접수

- 문의만 표시
- 건의 0건
- 버그 0건

#### 건의 접수

- 건의만 표시
- 문의 0건
- 버그 0건

#### 버그 접수

- 버그만 표시
- 문의 0건
- 건의 0건

### 16.2 검색·필터 검증

각 화면에서 아래를 확인한다.

- 접수번호 검색
- 제목/내용 검색
- 상태 필터
- 접수자 필터
- 페이지네이션
- 정렬
- 빈 결과 화면
- 로딩 화면
- API 오류 화면

### 16.3 삭제·복구 검증

각 유형별 QA 데이터 최소 1건으로 확인한다.

1. 목록 표시 확인
2. 삭제 실행
3. 해당 메뉴에서 사라짐 확인
4. 다른 유형 메뉴에 나타나지 않음 확인
5. 휴지통 표시 확인
6. 복구 실행
7. 원래 유형 메뉴에 다시 나타남 확인

### 16.4 링크 검증

- 사이드바 3개 메뉴 링크 정상
- 새로고침 정상
- 브라우저 뒤로가기 정상
- 기존 통합 URL 처리 정상
- 상세 화면에서 목록 돌아가기 시 원래 유형 메뉴 유지
