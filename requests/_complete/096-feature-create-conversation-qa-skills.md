
# 자유대화·끝말잇기·초성게임 QA SKILL 생성

## 상태
- 작업 유형: Feature / QA Infrastructure
- 우선순위: HIGH
- 대상: Claude Code
- 목적: 반복 QA 절차를 기능별 Claude Code QA SKILL로 표준화

---

# 0. 완료 시 기대 결과 / 대표님 테스트 정상 프로세스

## 완료 시 기대 결과

대표님이 앞으로 자유대화 관련 기능을 QA할 때 매번 테스트 방법을 설명하지 않아도 된다.

Claude Code에 해당 QA SKILL을 실행하도록 요청하면 각 SKILL이 스스로:

1. 현재 구현 구조를 확인하고
2. 실제 QA용 아이 계정/세션을 사용해
3. 여러 턴의 실제 대화를 진행하고
4. 올바른 Skill/Router가 호출됐는지 확인하고
5. 케이의 실제 응답이 정상인지 확인하고
6. 세션/게임 상태가 정상 유지되는지 확인하고
7. DB에 실제 데이터가 정상 저장됐는지 확인하고
8. PASS/FAIL 및 근거를 보고해야 한다.

이번 작업에서 최소 다음 3개의 독립 QA SKILL을 실제 생성한다.

- `free-chat-qa`
- `word-chain-qa`
- `chosung-game-qa`

각 SKILL은 `.claude/skills/` 하위의 프로젝트 Skill로 생성한다.

예상 구조:

```text
.claude/
└─ skills/
   ├─ free-chat-qa/
   │  └─ SKILL.md
   ├─ word-chain-qa/
   │  └─ SKILL.md
   └─ chosung-game-qa/
      └─ SKILL.md
```

단, 작업 시작 전에 현재 프로젝트의 `.claude/skills` 구조와 기존 SKILL 작성 규칙을 먼저 읽고, 이미 사용 중인 구조·frontmatter·파일명이 있으면 그것을 우선한다.

존재하지 않는 Claude Code SKILL 문법을 추측해서 만들지 않는다.

## 대표님 테스트 정상 프로세스

### 자유대화

대표님이 Claude Code에 자유대화 QA SKILL 실행을 지시한다.

정상이라면 Claude Code가:

`자유대화 진입 → 실제 대화 여러 턴 → 응답 확인 → DB 확인 → 결과 보고`

순서로 진행한다.

최종 보고에서 다음이 한 번에 보여야 한다.

- 자유대화 응답 PASS/FAIL
- 문맥 유지 PASS/FAIL
- DB 저장 PASS/FAIL
- 실제 근거

---

### 끝말잇기

대표님이 끝말잇기 QA SKILL 실행을 지시한다.

정상이라면:

`자유대화 → "끝말잇기 하자" → 끝말잇기 Skill 진입 → 최소 10턴 게임 → DB 확인 → 결과 보고`

가 자동으로 진행된다.

PASS 결과에서는:

- 실제 끝말잇기 Skill/Router 사용
- 끝글자 규칙 정상
- 적절한 단어 난이도
- 게임 상태 유지
- DB 저장 정상

이 모두 확인되어야 한다.

---

### 초성게임

대표님이 초성게임 QA SKILL 실행을 지시한다.

정상이라면:

`자유대화 → "초성게임 하자" → 초성게임 Skill 진입 → 문제 → 오답 → 힌트1 → 오답 → 힌트2 → 오답 → 힌트3 → 정답 → 다음 문제 → DB 확인`

전체 흐름을 자동 검증한다.

PASS 결과에서는 위 단계가 실제로 모두 정상 수행됐다는 근거가 보여야 한다.

# 3. 공통 QA SKILL 작성 원칙

3개 SKILL 모두 아래 원칙을 따른다.

## 3.1 실제 동작을 검증한다

코드만 읽고 "정상으로 보인다"라고 PASS 처리하면 안 된다.

가능한 범위에서 실제 실행 결과를 확인한다.

최소한:

- 실제 입력
- 실제 반환값
- 실제 로그
- 실제 DB record

중 검증 가능한 근거를 확보한다.

---

## 3.2 멀티턴 QA를 수행한다

1회 요청/1회 응답만 테스트하지 않는다.

자유대화 및 게임 특성상 반드시 여러 턴을 진행해 state와 context가 유지되는지 검증한다.

---

## 3.3 DB까지 검증한다

화면이나 응답이 정상이어도 DB가 잘못 저장되면 PASS가 아니다.

각 Skill은 실제 구현에 맞춰 다음을 검증한다.

- child 식별
- session 식별
- 아이 발화
- 케이 응답
- 순서
- timestamp
- 대화/게임 유형
- 게임 state
- 중복 저장
- 누락

DB 구조가 별도 게임 테이블이 아니라 message metadata 기반이면 실제 구현 방식을 따른다.

---

## 3.4 QA 중 임의 수정 금지

QA SKILL 실행 중 발견한 문제를 자동으로 수정하지 않는다.

SKILL의 기본 책임은:

`재현 → 검증 → 증거 확보 → PASS/FAIL → 원인 후보 보고`

까지다.

수정은 별도 개발 작업에서 수행한다.

---

## 3.5 Production 데이터 보호

QA를 위해 Production 실제 사용자 데이터에 임의 쓰기를 하지 않는다.

프로젝트에 존재하는 QA/Test 계정이나 Dev 환경을 우선 사용한다.

Production DB를 확인해야 한다면 특별한 지시가 없는 한 읽기 전용으로 제한한다.

API key, service role key, token, password 등의 비밀정보를:

- 코드에 하드코딩
- 콘솔 출력
- 보고서 출력
- 임시파일 저장

하지 않는다.

기존 환경변수 또는 Secret 관리 방식을 사용한다.

# 4. SKILL 1 — free-chat-qa

생성 위치:

```text
.claude/skills/free-chat-qa/SKILL.md
```

현재 프로젝트 convention이 다르면 기존 convention을 따른다.

---

## 목적

케이와 아이의 일반 자유대화가 정상적으로 이어지고, 아이가 이야기한 내용을 케이가 제대로 받아서 반응하며, 모든 발화와 응답이 DB에 정상 저장되는지 검증한다.

---

## 필수 시나리오

최소 5턴 이상의 연속 대화를 진행한다.

예시 의미:

1. 아이가 오늘 있었던 일을 이야기
2. 친구 이야기를 추가
3. 감정 표현
4. 구체적인 사건 추가
5. 앞에서 이야기한 내용을 다시 언급

QA 문구를 항상 똑같이 하드코딩할 필요는 없지만 동일 검증 목적을 충족해야 한다.

---

## 확인 항목

### Routing

- 자유대화 기본 처리 경로를 사용한다.
- 불필요한 게임 Skill로 잘못 routing되지 않는다.

### Conversation

- 아이 발화의 의미를 정상적으로 이해한다.
- 아이가 방금 말한 내용을 자연스럽게 받아서 반응한다.
- 엉뚱한 주제로 전환하지 않는다.
- 아이가 말하지 않은 사실을 생성하지 않는다.
- 현재 자유대화 응답 정책을 준수한다.
- 장황한 설명이나 훈계가 나오지 않는다.

### Context

최소 1회 앞선 발화를 다시 참조하는 테스트를 수행한다.

예:

```text
아까 내가 누구랑 놀았다고 했지?
```

- 같은 세션의 앞선 대화를 적절하게 참조
- 다른 아이 정보 혼입 없음
- 존재하지 않는 기억 생성 없음

### Persistence

실제 DB에서:

- 아이 발화 저장
- 케이 응답 저장
- child 연결
- session 연결
- speaker 구분
- 턴 순서
- timestamp
- 중복 여부
- 누락 여부

를 확인한다.

# 5. SKILL 2 — word-chain-qa

생성 위치:

```text
.claude/skills/word-chain-qa/SKILL.md
```

---

## 목적

자유대화 중 아이가 끝말잇기를 요청했을 때 실제 끝말잇기 Skill이 선택되고, 게임 규칙과 상태가 정상적으로 유지되며, 관련 데이터가 DB에 정상 저장되는지 검증한다.

---

## Skill Routing

실제 사용자 발화로 시작한다.

예:

```text
케이야 끝말잇기 하자
```

반드시 확인:

- 실제 끝말잇기 Skill/Router 선택
- Skill 진입 근거 확보
- 일반 LLM이 끝말잇기를 흉내만 낸 것이 아님
- 게임 state 생성 또는 활성화

Skill이 실제 호출되지 않았다면 응답 내용이 우연히 정상이어도 FAIL이다.

---

## 게임 진행

최소 10턴 이상 진행한다.

각 턴에서:

- 직전 단어의 마지막 글자 확인
- 다음 단어 첫 글자 확인
- 아이 입력 유효성 처리
- 케이 입력 유효성 처리
- 게임 state 유지

를 확인한다.

---

## 난이도 검증

케이가 초등학생과 진행하는 게임이라는 현재 서비스 맥락에 맞는 단어를 사용하는지 확인한다.

다음 문제를 검출한다.

- 지나치게 희귀한 단어
- 전문용어
- 사전에 없는 억지 단어
- 정상적인 쉬운 단어가 있는데 불필요하게 어려운 단어 사용
- 게임을 인위적으로 막는 단어 선택

단, "어려운 단어" 여부를 단순 주관으로 판정하지 말고 현재 구현된 단어 bank, validation 정책 또는 프로젝트 기준이 있으면 이를 우선한다.

---

## DB 검증

실제 구현 구조를 기준으로 확인:

- 끝말잇기 Skill 사용 기록
- child/session
- 게임 식별 정보
- 아이 단어
- 케이 단어
- 턴 번호
- 게임 state
- 사용 단어 history
- 종료 상태
- 중복
- 누락

# 6. SKILL 3 — chosung-game-qa

생성 위치:

```text
.claude/skills/chosung-game-qa/SKILL.md
```

---

## 목적

아이가 초성게임을 요청했을 때 실제 초성게임 Skill을 사용하고, 문제부터 힌트 단계와 정답까지 정의된 게임 흐름이 정상 작동하는지 검증한다.

```text
초성게임 하자
```

- 실제 초성게임 Skill 호출

- 문제 state 생성
- 일반 LLM이 임의로 문제를 만들어내지 않음

Skill 호출 근거가 없으면 FAIL이다.

# 7. 초성게임 필수 Full Scenario

최소 한 문제에 대해 아래 전체 흐름을 실제로 통과한다.

```text
문제 출제
↓
오답
↓
힌트 1
↓
오답
↓
힌트 2
↓
오답
↓
힌트 3
↓
정답
↓
정답 처리
↓
다음 문제
```

---

## 7.1 문제 출제

확인:

- 실제 문제 bank 사용
- 초성 정상
- 정답과 초성 일치
- 정답 사전 노출 없음
- 문제 state 정상

---

## 7.2 힌트 1

첫 번째 의도적 오답을 전달한다.

확인:

- 바로 정답 공개하지 않음
- 힌트 1 정상 제공
- 같은 문제가 유지됨
- hint state 정상 증가

---

## 7.3 힌트 2

두 번째 의도적 오답 입력.

확인:

- 힌트 2 정상 제공
- 힌트 1과 동일 내용 단순 반복 아님
- 동일 문제 유지
- 정답 변경 없음

---

## 7.4 힌트 3

세 번째 의도적 오답 입력.

확인:

- 힌트 3 정상 제공
- hint 단계 정상 증가
- 문제/정답 mapping 유지

---

## 7.5 정답

실제 정답을 입력한다.

확인:

- 정상 정답 판정
- 성공 응답
- 해당 문제 완료
- 다음 문제로 정상 전환

---

# 8. 초성게임 DB 검증

실제 스키마를 기준으로 가능한 모든 항목을 확인한다.

최소:

- 초성게임 Skill 사용 여부
- child/session
- 문제 식별자
- 초성
- 정답
- 아이 입력
- 정답/오답 판정
- hint 단계
- 힌트 진행 상태
- 완료 상태
- 다음 문제 상태

QA를 위해 임의의 신규 DB 컬럼이나 테이블을 만들지 않는다.

# 9. 복합 전환 검증

각 독립 SKILL의 기본 QA 구현 후, 현재 구조에서 가능하다면 다음 시나리오도 검증 가능하도록 SKILL 내부에 회귀 항목으로 포함한다.

```text
일반 자유대화
→ 끝말잇기 진입
→ 끝말잇기 진행
→ 종료
→ 일반 자유대화 복귀
→ 초성게임 진입
→ 초성게임 진행
→ 종료
→ 일반 자유대화 복귀
```

확인:

- 자유대화 → 끝말잇기 routing
- 끝말잇기 → 자유대화 복귀
- 자유대화 → 초성게임 routing
- 초성게임 → 자유대화 복귀
- 이전 게임 state 잔존 없음
- 서로 다른 Skill state 혼입 없음
- 세션 데이터 정상
- DB 데이터 정상

---

# 10. 각 QA SKILL의 공통 판정 구조

각 SKILL은 최소 아래 4개 Layer로 결과를 판정한다.

## Layer 1 — Routing

올바른 Skill / Router가 실제 선택됐는가?

## Layer 2 — Conversation

케이의 실제 응답이 현재 정책 및 게임 규칙에 맞는가?

## Layer 3 — State

대화 문맥, 턴, 문제, hint, 게임 상태가 정상 유지되는가?

## Layer 4 — Persistence

DB에 필요한 데이터가 정상적으로 저장됐는가?

4개 중 하나라도 FAIL이면 해당 QA 전체를 PASS 처리하지 않는다.

---

# 11. QA 결과 출력 형식

모든 SKILL의 마지막 출력 형식을 가능한 한 통일한다.

예:

```text
[QA RESULT]

Skill: word-chain-qa
Environment: Dev
Child/Test Account: <masked identifier>

Routing: PASS
Conversation: PASS
State: PASS
Persistence: FAIL

Overall: FAIL
```

세부 결과:

```text
QA-01 PASS — 실제 끝말잇기 Skill 호출 확인
근거: <file/log/event>

QA-02 PASS — 10턴 정상 진행
근거: <actual turn summary>

QA-03 FAIL — 7번째 아이 발화 DB 누락
근거: <query/result>
```

FAIL 시 반드시 아래를 포함한다.

- 증상
- 재현 절차
- 기대 결과
- 실제 결과
- 관련 로그
- 관련 DB record
- 관련 코드 위치 또는 원인 후보

비밀값은 마스킹한다.

# 12. SKILL 자체 품질 검증

SKILL 파일 생성만 하고 작업 완료 처리하지 않는다.

각 SKILL에 대해 다음을 확인한다.

- Claude Code가 Skill로 인식 가능한 구조인가
- frontmatter가 현재 프로젝트 convention에 맞는가
- Skill 이름이 충돌하지 않는가
- 실행 지침이 모호하지 않은가
- 존재하지 않는 파일/API/테이블을 하드코딩하지 않았는가
- 실제 프로젝트 구조를 기준으로 검증하도록 작성됐는가
- QA 중 자동 수정하지 않도록 명시됐는가
- 보안정보 출력 금지가 포함됐는가
- PASS/FAIL 근거가 반드시 남도록 되어 있는가

가능하면 생성된 Skill을 실제 호출하여 dry-run 또는 Dev QA를 수행하고 Skill 자체가 정상 실행되는지 확인한다.
