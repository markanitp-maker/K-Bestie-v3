# REQUEST 024 — 부모 대화 실마리와 부모용 추천 질문 분리 구현

## 1. 작업 목적

부모 리포트 상세 모달의 `추천 가이드` 탭에서 다음 두 영역이 사실상 동일한 내용으로 표시되고 있다.

- 부모 대화 실마리
- 부모용 추천 질문

현재 Production 진단 결과, 두 데이터가 독립적으로 생성·저장되는 구조가 아니라 단일 `parent_guide` 문자열만 존재하며, UI가 이 문자열을 그대로 한 번 표시하고 다시 정규식으로 분할하여 추천 질문처럼 렌더링하고 있다.

이번 작업에서는 두 항목을 생성 단계부터 완전히 분리한다.

```text
부모 대화 실마리
→ 아이의 상황과 부모의 접근 방향을 설명하는 짧은 조언

부모용 추천 질문
→ 부모가 아이에게 그대로 말할 수 있는 실제 의문문 2~3개
```

---

## 2. 확정 원인

읽기 전용 진단에서 다음이 확인됐다.

### 2.1 데이터 모델 문제

`daily_reports`에는 다음 독립 필드가 없다.

- `parent_conversation_clue`
- `recommended_questions`

현재는 `parent_guide` 문자열 하나만 존재한다.

### 2.2 프롬프트·Schema 문제

리포트 생성 프롬프트는 부모용 질문 배열을 생성하도록 정의되어 있지 않다.

LLM은 다음 두 역할을 구분하지 않고 단일 조언 문장만 생성한다.

- 대화 맥락 및 접근 방향
- 실제로 아이에게 물을 질문

### 2.3 UI 문제

`app/parent/report/[id]/page.tsx` 또는 실제 상세 모달 컴포넌트가 단일 `parent_guide`를 다음처럼 중복 사용한다.

1. 전체 문장을 `부모 대화 실마리`로 표시
2. 동일 문장을 `?`, `요`, `까` 등의 정규식으로 분할
3. 분할 결과를 `부모용 추천 질문`처럼 표시

이 방식 때문에 질문이 아닌 조언 문장이 질문 영역에 반복된다.

---

## 3. 확정 결과 구조

리포트 생성 결과를 다음 두 필드로 분리한다.

```ts
type ParentGuideOutput = {
  parentConversationClue: string | null;
  recommendedQuestions: string[];
};
```

DB 또는 JSON 저장 구조는 기존 네이밍 규칙에 맞춰 다음 목적을 충족해야 한다.

```text
parent_conversation_clue
recommended_questions
```

### 역할 구분

| 항목 | 역할 | 형식 |
|---|---|---|
| 부모 대화 실마리 | 아이의 현재 상황과 부모의 접근 방향 설명 | 문자열 1개 |
| 부모용 추천 질문 | 아이에게 바로 건넬 자연스러운 질문 | 문자열 배열 2~3개 |

두 항목은 같은 문장을 재사용하거나 일부만 바꿔 복제하면 안 된다.

---

## 4. 부모 대화 실마리 생성 기준

`parent_conversation_clue`는 부모가 아이와 대화를 시작하기 전에 알아야 할 맥락과 태도를 설명한다.

### 필수 기준

- 아이의 실제 대화와 리포트 근거 사용
- 부모가 어떤 태도로 접근하면 좋은지 설명
- 2~4문장 이내
- 질문문을 포함하지 않음
- 훈계나 진단 표현 금지
- 아이가 말하지 않은 감정·사실 추가 금지
- 부모에게 아이를 추궁하도록 유도하지 않음

### 허용 예시

```text
아이는 친구들과 스케이트를 타며 즐거움을 느꼈지만,
과제를 시작해야 한다는 부담도 조금 남아 있습니다.
놀이 경험을 먼저 공감한 뒤 과제 이야기를 가볍게 꺼내는 방식이 좋습니다.
```

### 금지 예시

```text
왜 과제를 아직 시작하지 않았어?
```

질문은 `recommended_questions`에만 생성한다.

## 5. 부모용 추천 질문 생성 기준

`recommended_questions`는 부모가 아이에게 그대로 말할 수 있는 자연스러운 의문문 2~3개다.

### 필수 기준

- 배열 형태
- 2개 이상 3개 이하
- 각 항목은 완전한 의문문
- 물음표로 끝남
- 아이의 실제 대화 근거 사용
- 짧고 일상적인 말투
- 한 질문에 한 가지 내용만 포함
- 정답을 유도하지 않음
- 추궁·검증·심문처럼 느껴지지 않음
- 부모 대화 실마리 문장을 복사하지 않음

### 허용 예시

```json
[
  "스케이트를 탈 때 어떤 순간이 제일 재미있었어?",
  "오늘 과제는 언제 시작하면 마음이 편할 것 같아?",
  "다음에도 친구들과 같이 타고 싶어?"
]
```

### 금지 예시

```json
[
  "공부 걱정을 내려놓고 자유롭게 놀 수 있도록 다정하게 격려해 주세요."
]
```

이 문장은 질문이 아니라 부모 행동 지침이다.

### 금지 질문 유형

- `왜 아직 안 했어?`
- `친구랑 싸운 거 아니야?`
- `엄마 말이 맞지?`
- `다음에는 공부부터 해야 하는 거 알지?`
- 한 항목에 두 개 이상의 질문을 결합한 문장

## 6. LLM 프롬프트 변경

일일·주간 리포트 생성 프롬프트에 두 필드의 역할을 명확히 분리한다.

### 구조화 출력 예시

```json
{
  "parent_conversation_clue": "아이는 친구들과 스케이트를 타며 즐거움을 느꼈지만 과제를 시작해야 한다는 부담도 조금 남아 있습니다. 놀이 경험을 먼저 공감한 뒤 과제 이야기를 가볍게 꺼내는 방식이 좋습니다.",
  "recommended_questions": [
    "스케이트를 탈 때 어떤 순간이 제일 재미있었어?",
    "오늘 과제는 언제 시작하면 마음이 편할 것 같아?",
    "다음에도 친구들과 같이 타고 싶어?"
  ]
}
```

### 프롬프트 필수 명령

- 두 필드는 서로 다른 목적을 가진다.
- `parent_conversation_clue`에는 질문을 작성하지 않는다.
- `recommended_questions`에는 설명이나 부모 행동 지침을 작성하지 않는다.
- `recommended_questions`는 반드시 2~3개의 의문문 배열이다.
- 두 필드의 문장을 서로 복사하지 않는다.
- 실제 대화 근거가 부족하면 추측하지 않는다.

## 7. 출력 검증

LLM 결과는 DB 저장 전에 서버에서 검증한다.

### 부모 대화 실마리 검증

- 문자열 또는 `null`
- 빈 문자열 금지
- 물음표 포함 여부 확인
- 추천 질문과 완전 일치 또는 높은 중복 여부 확인
- 데이터 부족 placeholder 여부 확인

### 부모용 추천 질문 검증

- 배열 여부
- 길이 2~3
- 각 항목 문자열 여부
- 공백 제거 후 빈 문자열 금지
- 각 항목이 `?`로 끝나는지
- 질문끼리 중복되지 않는지
- 부모 대화 실마리와 동일하거나 거의 같은 문장이 아닌지
- 조언문·명령문이 질문 배열에 들어오지 않았는지

### 검증 실패 처리

1. 생성 결과 검증
2. 실패한 필드만 한 번 재생성
3. 재검증
4. 여전히 실패하면 해당 필드를 `null` 또는 빈 배열로 저장
5. 잘못된 값을 정상값처럼 UI에 표시하지 않음
6. 오류 코드와 생성 버전을 로그에 기록

## 8. DB 및 마이그레이션

현재 `daily_reports.parent_guide`는 기존 과거 데이터 호환을 위해 즉시 삭제하지 않는다.

다음 독립 필드 또는 동일 목적의 JSON 경로를 추가한다.

```sql
parent_conversation_clue text
recommended_questions jsonb
```

실제 프로젝트의 기존 스키마와 네이밍 규칙을 우선 확인한다.

### 권장 조건

- `recommended_questions`는 JSON 배열만 허용
- 동일 리포트 upsert 시 두 필드를 모두 갱신
- 일일·주간 리포트 모두 지원
- 자동 배치·관리자 수동 생성이 같은 저장 함수를 사용
- 기존 `parent_guide`를 신규 필드에 자동 복제하지 않음

기존 `parent_guide` 문자열을 질문 배열로 변환하여 마이그레이션하지 않는다.

## 9. TypeScript 타입·파서·저장 매핑

다음 전체 경로에서 독립 필드를 유지한다.

```text
LLM JSON Schema
→ 응답 파서
→ 내부 TypeScript 타입
→ 일일·주간 리포트 생성 결과
→ DB insert/upsert
→ 부모 상세 API DTO
→ 추천 가이드 UI
```

각 단계에서 다음 오류를 방지한다.

- 두 필드가 같은 변수에 매핑됨
- `recommended_questions` 누락 시 `parent_conversation_clue`를 fallback으로 사용
- 배열 파싱 실패 시 `parent_guide`를 정규식 분할
- 자동 배치와 수동 생성 경로의 필드명이 다름
- 일일과 주간 리포트가 서로 다른 Schema 사용
- 신규 필드가 upsert 대상에서 빠짐

## 10. 부모 리포트 API

상세 모달 API는 두 값을 서로 다른 필드로 반환한다.

### 응답 예시

```json
{
  "guide": {
    "parentConversationClue": "아이는 친구들과 즐겁게 놀았지만 과제를 시작해야 한다는 부담도 조금 남아 있습니다.",
    "recommendedQuestions": [
      "오늘 가장 재미있었던 순간은 뭐였어?",
      "과제는 언제 시작하면 마음이 편할 것 같아?",
      "다음에도 친구들과 같이 놀고 싶어?"
    ]
  }
}
```

### 금지 처리

- `recommendedQuestions`가 없을 때 clue를 복사
- 문자열을 정규식으로 분할하여 질문 배열 생성
- 질문 배열을 하나의 긴 문자열로 합침
- 다른 날짜 또는 다른 아이의 캐시 재사용

캐시 키에는 최소한 다음 값을 포함한다.

```text
childId + reportType + reportId
```

## 11. 추천 가이드 UI 수정

현재 단일 `parent_guide`를 두 카드에서 재사용하는 로직을 제거한다.

### 부모 대화 실마리 카드

사용 데이터:

```text
guide.parentConversationClue
```

표시 방식:

- 일반 문단
- 질문 목록 아이콘 사용 금지
- 값이 없으면 카드 전체 숨김

### 부모용 추천 질문 카드

사용 데이터:

```text
guide.recommendedQuestions
```

표시 방식:

- 질문별 별도 항목
- 2~3개 리스트
- 각 질문 앞 체크 또는 질문 아이콘
- 하나의 긴 문단으로 합치지 않음
- 값이 없으면 카드 전체 숨김

### 완전 제거 대상

- `parent_guide` 정규식 분할
- `?`, `요`, `까` 기준 문자열 자르기
- clue를 질문 영역에 fallback
- 동일 prop을 두 카드에 전달하는 코드
- 질문이 아닌 조언문을 질문으로 표시하는 코드

## 12. 과거 리포트 호환성

기존 과거 리포트에는 신규 두 필드가 없을 수 있다.

### 처리 원칙

- 기존 `parent_guide`는 부모 대화 실마리로만 표시할 수 있다.
- 기존 `parent_guide`에서 질문을 임의 추출하지 않는다.
- `recommended_questions`가 없는 과거 리포트는 질문 카드 전체를 숨긴다.
- `질문 정보가 부족해요` 같은 빈 카드 안내를 표시하지 않는다.
- 과거 전체 리포트를 자동 재생성하지 않는다.
- 필요한 특정 리포트만 관리자 수동 생성으로 갱신할 수 있게 한다.

---

## 13. 일일·주간 리포트 공통 적용

다음 모든 생성·조회 경로에 적용한다.

- 새벽 일일 리포트 자동 배치
- 주간 리포트 자동 배치
- 관리자 특정 아이 즉시 리포트 생성
- 관리자 전체 아이 리포트 생성
- 수집 후 리포트 즉시 생성
- 실패 아이 재생성
- 일일 목록 카드 상세 모달
- 주간 목록 카드 상세 모달
- 지난 이력보기 달력 진입

자동·수동·일일·주간 경로에서 서로 다른 필드 생성 규칙을 사용하지 않는다.

## 14. Production 환경 확인 원칙

이전 진단 일부 명령에서 `.env.local`이 사용됐으므로, 실제 Production 적용 전 다음을 다시 확인한다.

- Production Vercel 배포 커밋
- Production Supabase 프로젝트
- Production Edge Function 배포본
- Production DB Schema
- Production API 응답

Production 검증에서는 `.env.production` 또는 실제 Production Secret만 사용한다.

Development와 Production 데이터를 혼합하지 않는다.

비밀키 값은 로그·보고서·명령 출력에 노출하지 않는다.

## 15. 필수 테스트 시나리오

### 시나리오 A — 정상 일일 리포트

예상 결과:

- 부모 대화 실마리 1개 생성
- 추천 질문 2~3개 생성
- 두 내용이 서로 다름
- 추천 질문이 모두 의문문
- DB·API·UI 값 일치

### 시나리오 B — 정상 주간 리포트

예상 결과:

- 주간 맥락을 반영한 실마리
- 주간 리포트용 추천 질문 2~3개
- 일일 리포트 데이터와 혼합되지 않음

### 시나리오 C — 추천 질문 생성 실패

예상 결과:

- 부모 대화 실마리는 정상 표시
- 추천 질문 카드는 숨김
- clue를 질문으로 복사하지 않음
- 전체 모달 오류 없음

### 시나리오 D — 과거 리포트

조건:

- `parent_guide`만 존재
- 신규 필드 없음

예상 결과:

- 기존 조언은 부모 대화 실마리로 표시 가능
- 추천 질문 카드 숨김
- 정규식 질문 생성 없음

### 시나리오 E — 중복 검증

예상 결과:

- clue와 질문의 문장 중복 없음
- 질문끼리 중복 없음
- 같은 조언이 여러 카드에 반복되지 않음

### 시나리오 F — 다자녀

예상 결과:

- 선택한 아이의 질문만 표시
- 다른 아이의 캐시 또는 추천 질문 혼합 없음

### 시나리오 G — 관리자 수동 생성

예상 결과:

- 자동 배치와 동일한 두 필드 생성
- 기존 리포트 갱신 시 두 필드 모두 upsert
- 재실행 시 중복 레코드 없음

### 시나리오 H — 모바일 모달

예상 결과:

- 질문 2~3개가 각각 별도 줄로 표시
- 긴 조언과 질문이 레이아웃을 깨뜨리지 않음
- 상단 탭 고정과 내부 스크롤 정상

## 16. 완료 기준

- [ ] LLM이 부모 대화 실마리와 추천 질문을 별도 생성한다.
- [ ] 부모 대화 실마리는 문자열 1개다.
- [ ] 추천 질문은 문자열 배열 2~3개다.
- [ ] 추천 질문은 모두 실제 의문문이다.
- [ ] 두 항목의 문장이 서로 중복되지 않는다.
- [ ] 질문 배열에 부모 행동 지침이 들어가지 않는다.
- [ ] DB에 두 필드가 별도로 저장된다.
- [ ] 일일·주간 리포트 모두 적용된다.
- [ ] 자동·수동 생성 경로가 동일 로직을 사용한다.
- [ ] API가 두 값을 별도 필드로 반환한다.
- [ ] UI가 두 값을 별도 데이터로 렌더링한다.
- [ ] `parent_guide` 정규식 분할 로직이 제거된다.
- [ ] 추천 질문이 없으면 카드 전체를 숨긴다.
- [ ] 기존 과거 리포트에서 임의 질문을 생성하지 않는다.
- [ ] DB→API→UI 값이 일치한다.
- [ ] 다자녀·날짜·리포트 유형 혼선이 없다.
- [ ] Development 일일·주간 E2E가 완료된다.
- [ ] Production 배포 및 실제 화면 검증이 완료된다.
- [ ] BLOCKER 및 HIGH 문제가 0건이다.
