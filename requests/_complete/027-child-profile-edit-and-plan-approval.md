
# 027 — 자녀 프로필 수정 오류 개선 및 요금제 변경 승인 워크플로우 구축

## 1. 작업 목적

부모 화면의 `자녀 프로필 수정` 기능에서 발생하는 다음 문제를 수정한다.

1. 기존에 저장된 자녀의 성과 이름이 수정 화면에 자동으로 표시되지 않는 문제
2. 필수값 누락 또는 저장 실패 시 아무런 안내 없이 저장되지 않는 문제
3. 부모가 자녀 요금제를 선택하면 즉시 변경하지 않고 관리자 승인 요청으로 접수하는 기능 부재
4. 관리자가 부모의 요금제 변경 요청을 승인하거나 거절할 수 있는 운영 화면 부재

이번 작업은 자녀 기본정보 수정과 요금제 변경 요청을 명확하게 분리하고, 모든 상태를 사용자와 관리자에게 투명하게 보여주는 것을 목표로 한다.

---

# 2. 현재 문제

## 문제 1 — 성과 이름이 빈 값으로 표시됨

현재 `자녀 프로필 수정` 화면을 열면 기존에 등록된 자녀임에도 다음 필드가 비어 있다.

- 성
- 이름

부모가 성과 이름을 다시 입력하지 않으면 저장되지 않는다.

## 문제 2 — 저장 실패 안내가 없음

필수값이 없거나 검증에 실패한 경우 다음 문제가 있다.

- 어느 항목이 비어 있는지 표시되지 않음
- 저장 버튼을 눌러도 아무 반응이 없는 것처럼 보임
- 입력란 아래 오류 문구가 없음
- 첫 번째 오류 위치로 이동하거나 포커스하지 않음
- 서버 저장 오류와 입력값 오류를 구분할 수 없음

## 문제 3 — 요금제 선택 후 처리 흐름이 없음

현재 화면에서 다음 요금제를 선택할 수 있다.

- 케어 스타트
- 케어 인사이트
- 케어 프리미엄

하지만 요금제 선택 후 결제 또는 변경 요청 흐름이 연결되어 있지 않다.

이번 단계에서는 실제 결제를 구현하지 않는다.

부모가 요금제를 선택하면 관리자 승인 요청을 생성하고, 관리자가 승인해야 실제 요금제가 적용되도록 한다.

- 요청 상태 표시

- 요금제 변경 요청 메뉴
- 요청 목록
- 요청 상세 정보
- 승인

- 처리 이력
- 중복 처리 및 충돌 방지

## 서버 및 데이터

- 요금제 변경 요청 저장 구조

- 권한 검증
- 원자적 상태 변경
- 감사 이력

# 4. 선행 조사

코드 수정 전에 다음을 확인한다.

1. 자녀 프로필 수정 화면의 실제 route와 컴포넌트
2. 성과 이름을 최초 등록할 때 사용하는 필드명
3. 자녀 목록과 홈 화면에서 이름을 표시할 때 사용하는 데이터 원본
4. 자녀 정보를 조회하는 API, Server Action, Supabase query 또는 store
5. 자녀 정보를 수정하는 기존 API 또는 RPC
6. 현재 요금제의 정본 데이터 위치
7. 부모와 자녀의 관계를 검증하는 기존 권한 로직
8. 관리자 판별 방식
9. 관리자 페이지의 메뉴와 공통 테이블 구조
10. 현재 미커밋 변경

성과 이름 필드명을 추정해서 새 필드를 만들지 말고, 최초 등록과 현재 화면 표시에서 사용하는 정본 필드를 확인한 뒤 동일한 필드를 사용한다.

기존 스키마에 성과 이름이 분리되어 있는데 조회 매핑만 빠진 경우 DB 스키마를 변경하지 않는다.

# 5. 자녀 성·이름 자동 불러오기

## 기본 동작

부모가 `자녀 프로필 수정`을 누르면 선택한 자녀의 현재 저장 정보를 조회해 다음 필드에 표시한다.

- 성
- 이름
- 학년
- 관심사
- 현재 요금제

성과 이름은 빈 문자열로 초기화한 뒤 사용자 입력을 기다리는 방식으로 구현하지 않는다.

## 데이터 연결 기준

다음 우선순위를 따른다.

1. 기존 자녀 등록 시 저장한 성·이름 필드
2. 자녀 프로필 조회 API가 반환하는 성·이름 필드
3. 현재 자녀 이름을 표시하는 정본 child profile 데이터

전체 이름 문자열을 임의로 잘라 성과 이름으로 분리하지 않는다.

특히 한국 성씨는 한 글자 또는 두 글자일 수 있으므로 문자열 길이만으로 성을 추정하지 않는다.

정본 필드가 존재하지 않는 것이 확인될 때만 데이터 구조 변경안을 별도로 보고한다.

## 비동기 초기화

자녀 데이터가 비동기로 로드되는 경우 다음을 지킨다.

- 데이터 로딩 완료 후 form default value를 설정
- 모달을 열 때마다 선택된 자녀 기준으로 값을 갱신
- 다른 자녀로 전환하면 이전 자녀 값이 남지 않게 처리
- 사용자가 입력을 시작한 뒤 background refetch가 발생해도 입력값을 덮어쓰지 않음
- 로딩 중에는 빈 입력란을 정상 데이터처럼 노출하지 않음
- 필요하면 skeleton 또는 loading 상태 표시

## 표시 예시

기존 데이터가 다음과 같다면:

```text
성: 안
이름: 서아
```

수정 화면을 열었을 때 처음부터 다음과 같이 표시되어야 한다.

```text
[안] [서아]
```

# 6. 프로필 입력값 검증

## 필수 항목

최소한 다음 항목을 검증한다.

- 성
- 이름
- 학년

현재 서비스 정책상 관심사가 필수라면 기존 검증 정책을 유지한다.

요금제 선택은 프로필 저장 필수값으로 취급하지 않는다.

## 검증 시점

다음 시점에 검증한다.

- 저장 버튼 클릭
- 입력란을 수정한 뒤 포커스가 빠질 때
- 기존 오류가 있는 입력란을 다시 수정할 때

## 필드별 오류 문구

성 누락:

```text
성을 입력해 주세요.
```

이름 누락:

```text
이름을 입력해 주세요.
```

학년 누락:

```text
학년을 선택해 주세요.
```

관심사 필수 조건 미충족:

```text
관심사를 한 개 이상 선택해 주세요.
```

## 오류 표시 위치

- 해당 입력란 바로 아래에 오류 문구 표시
- 입력란 테두리를 오류 상태색으로 표시
- `aria-invalid="true"` 적용
- 오류 문구와 입력란을 `aria-describedby`로 연결
- 저장 버튼 클릭 후 첫 번째 오류 입력란으로 포커스 이동
- 모달 내부 스크롤이 필요한 경우 첫 번째 오류 위치가 보이도록 이동

## 상단 오류 요약

여러 항목이 비어 있는 경우 모달 상단 또는 저장 버튼 위에 다음 안내를 표시한다.

```text
입력하지 않은 항목이 있어요. 표시된 내용을 확인해 주세요.
```

필드별 오류 문구를 대체하지 말고 함께 사용한다.

## 저장 버튼 상태

- 입력값이 비어 있다는 이유로 저장 버튼을 아무 설명 없이 disabled 처리하지 않는다.
- 저장 버튼은 클릭 가능하게 두고 클릭 시 명확한 검증 메시지를 표시한다.
- 실제 저장 요청 중일 때만 중복 요청 방지를 위해 disabled 처리한다.
- 저장 중에는 `저장 중...` 상태를 표시한다.

# 7. 저장 성공·실패 처리

## 저장 성공

성공 시 다음을 수행한다.

1. 자녀 정보를 저장
2. 부모 화면의 child profile cache 또는 store 갱신
3. 화면에 즉시 변경된 이름 반영
4. 성공 안내 표시
5. 모달 닫기 또는 현재 UX 정책에 따른 유지

성공 문구:

```text
자녀 정보가 저장되었어요.
```

## 입력 검증 실패

- 서버 요청을 보내지 않음
- 모달을 닫지 않음
- 사용자가 입력한 값 유지
- 첫 번째 오류 항목으로 포커스 이동

## 서버 저장 실패

서버 오류 문구:

```text
자녀 정보를 저장하지 못했어요. 잠시 후 다시 시도해 주세요.
```

다음 정보를 구분한다.

- 입력값 오류
- 권한 오류
- 네트워크 오류
- 서버 오류
- 이미 삭제되거나 접근할 수 없는 자녀

권한 오류 예시:

```text
이 자녀의 정보를 수정할 권한이 없어요.
```

오류가 발생해도 사용자가 입력한 값은 초기화하지 않는다.

# 8. 프로필 저장과 요금제 변경 분리

자녀 기본정보 저장과 요금제 변경은 서로 다른 작업으로 처리한다.

## 프로필 저장에 포함되는 항목

- 성
- 이름
- 학년
- 관심사
- 기타 기존 자녀 프로필 필드

## 프로필 저장에 포함하지 않는 항목

- 요금제 즉시 변경
- 관리자 승인 상태 변경
- 결제 처리

일반 `저장` 버튼을 눌렀다는 이유로 선택한 요금제가 바로 적용되면 안 된다.

---

# 9. 요금제 선택 UI

## 표시할 요금제

- 케어 스타트
- 케어 인사이트
- 케어 프리미엄

실제 코드에서 사용하는 plan code와 표시명을 확인해 연결한다.

표시명으로 DB 값을 직접 저장하지 않는다.

## 현재 요금제

현재 적용 중인 요금제에는 다음 표시를 추가한다.

```text
현재 이용 중
```

현재 요금제 카드를 다시 선택해도 변경 요청을 만들지 않는다.

## 승인 대기 중인 요금제

이미 변경 요청이 진행 중이면 요청한 요금제 카드에 다음 표시를 한다.

```text
승인 대기 중
```

동일 자녀에 대해 여러 개의 대기 요청을 동시에 만들지 않는다.

## 다른 요금제 선택

현재 요금제와 다른 요금제를 선택하면 확인 다이얼로그를 표시한다.

예시:

```text
요금제 변경을 요청할까요?

현재 요금제: 케어 스타트
변경 요청: 케어 인사이트

관리자 승인 후 변경된 요금제가 적용됩니다.
```

버튼:

```text
취소
변경 요청
```

# 10. 프로필 수정 중 요금제를 선택하는 경우

프로필 입력값을 변경한 뒤 저장하지 않은 상태에서 요금제를 선택하면 입력값을 잃지 않도록 처리한다.

다음 다이얼로그를 표시한다.

```text
수정 중인 자녀 정보가 있어요.

자녀 정보를 먼저 저장한 뒤 요금제 변경을 진행해 주세요.
```

버튼:

```text
계속 수정
저장하고 진행
```

`저장하고 진행` 선택 시:

1. 프로필 필수값 검증
2. 프로필 저장
3. 저장 성공 확인
4. 요금제 변경 요청 생성
5. 요청 접수 화면으로 이동

프로필 저장에 실패하면 요금제 요청을 생성하지 않는다.

# 11. 요금제 변경 요청 생성

## 핵심 원칙

부모가 다른 요금제를 선택해도 현재 요금제를 즉시 변경하지 않는다.

처리 순서:

1. 부모·자녀 관계 검증
2. 현재 요금제 조회
3. 동일 자녀의 pending 요청 확인
4. 요금제 변경 요청 생성
5. 요청 접수 화면으로 이동
6. 관리자 승인 전까지 현재 요금제 유지

## 중복 요청 방지

자녀 한 명당 동시에 하나의 `pending` 요청만 존재할 수 있도록 한다.

동일한 요청을 여러 번 클릭한 경우 중복 레코드를 생성하지 않는다.

가능하면 DB unique constraint 또는 transaction으로 보장한다.

## 이미 대기 요청이 있는 경우

새 요청을 만들지 않고 기존 요청 상태 페이지로 이동한다.

안내:

```text
이미 확인 중인 요금제 변경 요청이 있어요.
```

# 12. 요금제 변경 요청 데이터

기존에 동일 목적의 테이블이나 workflow가 있으면 재사용한다.

없을 경우 최소한 다음 정보를 저장할 수 있는 구조를 만든다.

```text
id
parent_user_id
child_id
current_plan_code
requested_plan_code
status
requested_at
reviewed_at
reviewed_by
review_note
created_at
updated_at
```

## status

허용 상태:

```text
pending
approved
rejected
cancelled
```

임의 문자열 저장을 금지한다.

## 추가 권장 정보

필요한 경우 다음 정보를 포함한다.

```text
current_plan_snapshot
request_source
approved_plan_applied_at
rejection_reason
```

개인정보나 필요 없는 자녀 데이터를 snapshot으로 중복 저장하지 않는다.

# 13. 권한 및 RLS

## 부모

부모는 다음 작업만 가능해야 한다.

- 본인과 연결된 자녀의 변경 요청 생성
- 본인과 연결된 자녀의 요청 상태 조회
- 허용된 경우 본인의 pending 요청 취소

다른 부모 또는 다른 자녀의 요청을 조회하거나 수정할 수 없어야 한다.

## 아이 계정

아이 계정은 요금제 변경 요청을 생성하거나 승인할 수 없다.

## 관리자

관리자만 다음 작업을 할 수 있다.

- 전체 요청 조회
- 승인
- 거절
- 처리 이력 조회

클라이언트에서 admin 여부만 검사하는 방식으로 권한을 보장하지 않는다.

서버 또는 DB 정책에서 관리자 권한을 검증한다.

# 14. 요금제 변경 요청 접수 화면

실제 결제 기능이 연결되기 전까지 결제 입력 화면을 만들지 않는다.

요금제 변경 요청이 생성되면 별도의 요청 접수 페이지 또는 모달을 표시한다.

## 화면 제목

```text
요금제 변경 요청이 접수되었어요
```

## 안내 문구

```text
현재 관리자가 요청 내용을 확인하고 있습니다.
승인되면 선택한 요금제가 적용됩니다.
```

## 표시 정보

- 자녀 이름
- 현재 요금제
- 요청한 요금제
- 요청 일시
- 현재 상태

## 상태 표시

승인 대기:

```text
관리자 확인 중
```

승인:

```text
요금제 변경 완료
```

거절:

```text
변경 요청이 승인되지 않았어요
```

거절 사유가 있으면 함께 표시한다.

## 버튼

기본 버튼:

```text
확인
```

`확인`을 누르면 부모의 아이 정보 관리 화면 또는 기존 부모 홈으로 이동한다.

## 금지

- 카드번호 입력
- 결제 완료 문구
- 결제가 완료된 것처럼 보이는 표현
- 승인 전에 새 요금제가 적용된 것처럼 표시
- 실제 결제 API 호출

# 19. 관리자 승인

## 승인 전 확인

승인 버튼 클릭 시 확인 다이얼로그를 표시한다.

```text
요금제 변경을 승인할까요?

자녀: 안서아
현재 요금제: 케어 스타트
변경 요금제: 케어 인사이트
```

버튼:

```text
취소
승인
```

## 승인 처리

승인은 하나의 transaction 또는 동일한 원자적 서버 작업으로 처리한다.

처리 순서:

1. 요청이 아직 pending인지 확인
2. 현재 자녀 요금제가 요청 생성 당시 요금제와 동일한지 확인
3. 관리자 권한 확인
4. 자녀의 실제 요금제 변경
5. 요청 상태를 approved로 변경
6. reviewed_at과 reviewed_by 기록
7. 처리 결과 반환
8. 부모 화면에서 최신 상태가 조회되도록 cache 갱신

요금제 변경과 요청 상태 변경이 분리되어 한쪽만 성공하면 안 된다.

## 이미 처리된 요청

이미 승인 또는 거절된 요청을 다시 승인하지 않는다.

안내:

```text
이미 처리된 요청입니다.
```

---

# 20. 승인 충돌 처리

요청 생성 이후 다른 운영 작업으로 현재 요금제가 변경된 경우 자동 승인하지 않는다.

예시:

```text
요청 당시: 케어 스타트
현재 실제 요금제: 케어 프리미엄
요청 요금제: 케어 인사이트
```

이 경우 승인 버튼을 차단하고 다음 안내를 표시한다.

```text
요청 이후 현재 요금제가 변경되어 자동 승인할 수 없습니다.
현재 상태를 확인해 주세요.
```

관리자가 강제 덮어쓰기를 할 수 있는 기능은 이번 작업에서 임의로 추가하지 않는다.

# 21. 관리자 거절

## 거절 확인

거절 버튼 클릭 시 거절 사유 입력 영역을 표시한다.

예시:

```text
요금제 변경 요청을 거절할까요?
```

거절 사유는 관리자 운영에 필요한 범위에서 입력한다.

권장:

- 거절 사유 선택 또는 직접 입력
- 최대 글자 수 제한
- 입력 내용 trim 처리

## 거절 처리

- 현재 요금제를 변경하지 않음
- 요청 상태를 rejected로 변경
- reviewed_at 기록
- reviewed_by 기록
- review_note 또는 rejection_reason 기록

부모 화면에서 거절 상태와 공개 가능한 사유를 확인할 수 있도록 한다.
