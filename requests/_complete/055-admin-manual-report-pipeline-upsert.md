# 관리자 수동 수집·리포트 생성 파이프라인 및 일일 리포트 UPSERT 구현

## 1. 작업 목적

관리자 페이지에는 운영자가 이해하기 쉬운 다음 두 개의 핵심 기능만 제공한다.

1. 대화 수집
2. 리포트 생성

실제 백엔드에서는 각 버튼이 내부 파이프라인을 자동으로 순차 실행한다.

- 대화 수집:
  - Collection
  - Context Correction
- 리포트 생성:
  - Memory Batch
  - Daily Report
- 수집 후 리포트 생성:
  - Collection
  - Context Correction
  - Memory Batch
  - Daily Report

같은 아이·같은 날짜의 일일 리포트는 실행할 때마다 새 행을 추가하지 않고 최신 결과로 갱신한다.

수동 실행과 새벽 정기 실행은 동일한 파이프라인과 동일한 저장 규칙을 사용하며, 실행 출처만 구분한다.

---

## 2. 확정 정책

### 2.1 관리자 화면 정책

관리자 화면에는 다음 버튼을 유지한다.

- `즉시 대화 수집`
- `즉시 리포트 생성`
- `수집 후 리포트 즉시 생성`

관리자는 Collection, Context Correction, Memory Batch 같은 내부 용어를 직접 제어하지 않는다.

버튼별 실제 백엔드 동작은 다음과 같다.

| 관리자 버튼 | 백엔드 자동 실행 |
|---|---|
| 즉시 대화 수집 | Collection → Context Correction |
| 즉시 리포트 생성 | Memory Batch → Daily Report |
| 수집 후 리포트 즉시 생성 | Collection → Context Correction → Memory Batch → Daily Report |

### 2.2 리포트 재생성 정책

같은 날짜·같은 아이의 일일 리포트는 여러 번 생성할 수 있다.

예시:

1. 관리자가 낮에 수동 리포트 생성
2. 새벽 4시 정기 리포트 생성
3. 관리자가 정기 생성 이후 다시 수동 리포트 생성

위 세 실행 모두 정상 허용한다.

단, 부모 화면과 기본 리포트 조회 API에는 항상 가장 최근 정상 생성 결과 1건만 노출한다.

같은 날짜 리포트를 새 행으로 계속 추가하지 않는다.

고유 기준:

```text
child_id + report_date + report_type
```

저장은 INSERT-only가 아니라 UPSERT 방식으로 처리한다.

## 3. 전체 처리 흐름

### 3.1 즉시 대화 수집

```text
관리자 버튼 클릭
→ 관리자 권한 검증
→ 선택 날짜 및 대상 아이 확정
→ Collection 실행
→ Collection 성공 데이터 기준 Context Correction 실행
→ 단계별 결과 반환
```

완료 기준:

- Collection 성공
- Context Correction 성공 또는 처리할 데이터 없음
- 실패 및 건너뜀 사유가 관리자 화면에 명확히 표시됨

### 3.2 즉시 리포트 생성

```text
관리자 버튼 클릭
→ 관리자 권한 검증
→ 선택 날짜 및 대상 아이 확정
→ corrected_daily_conversations 또는 동등한 보정 데이터 존재 여부 확인
→ Memory Batch 실행
→ Daily Report 생성
→ 기존 같은 날짜 리포트 UPSERT
→ 단계별 결과 반환
```

중요:

- Memory Batch 실패가 Daily Report 생성을 무조건 차단하지 않는다.
- Daily Report가 Memory Batch 없이도 기존 메모리 또는 보정 데이터로 생성 가능한 구조라면 계속 실행한다.
- 리포트 생성에 필요한 보정 데이터 자체가 없으면 성공으로 위장하지 않는다.
- 보정 데이터가 없는 경우 `먼저 대화 수집을 실행해 주세요` 또는 동등한 명확한 상태를 반환한다.

### 3.3 수집 후 리포트 즉시 생성

```text
관리자 버튼 클릭
→ 관리자 권한 검증
→ 선택 날짜 및 대상 아이 확정
→ Collection
→ Context Correction
→ Memory Batch
→ Daily Report
→ 기존 같은 날짜 리포트 UPSERT
→ 단계별 결과 반환
```

각 단계는 앞 단계의 실제 완료 데이터를 기준으로 다음 단계로 진행한다.

## 4. 수동 실행과 정기 실행 통합

### 4.1 공통 파이프라인

수동 실행과 정기 실행이 서로 다른 비즈니스 로직을 사용하지 않도록 한다.

공통 서비스 계층 또는 공통 함수에서 다음을 처리한다.

- Collection
- Context Correction
- Memory Batch
- Daily Report
- UPSERT
- 상태 기록
- 중복 및 동시 실행 제어
- 오류 처리

실행 경로는 다음 값 또는 동등한 방식으로 구분한다.

```text
execution_source = manual | scheduled
```

클라이언트가 전달한 값만 신뢰하지 않는다.

관리자 수동 실행은 서버 측 관리자 권한 검증을 통과한 경우에만 `manual`로 실행한다.

정기 실행은 Cron 또는 서버 전용 인증 경로에서만 `scheduled`로 실행한다.

### 4.2 시간 제한 정책

자동 Cron 경로는 기존 스케줄과 시간 조건을 유지한다.

관리자 수동 실행은 자동 Cron의 시간 제한을 적용하지 않는다.

예시:

- 자동 Collection: 기존 17:55 / 23:55 KST 정책 유지
- 자동 리포트 생성: 새벽 4시 기존 정책 유지
- 관리자 수동 실행: 관리자 권한 검증 후 즉시 실행 가능

수동 실행에서 다음 오류가 발생하지 않도록 한다.

```text
Cannot run Phase II collection before the window begins
```

자동 경로 전용 시간 제한이 수동 경로에 적용되지 않도록 분리한다.

## 5. 일일 리포트 UPSERT 정책

### 5.1 고유키

일일 리포트 테이블에 다음 조합의 유일성을 보장한다.

```text
child_id
report_date
report_type
```

권장 DB 제약:

```sql
UNIQUE (child_id, report_date, report_type)
```

기존 스키마에 동등한 고유키가 있으면 재사용한다.

### 5.2 업데이트 대상 필드

재생성 성공 시 최소 다음 정보를 최신값으로 갱신한다.

- 리포트 본문
- 요약 데이터
- 기분
- 친구
- 학교
- 관심사
- 사건 키워드
- 변화 신호
- 오늘의 대화거리
- 전달 메시지
- `generated_at`
- `generation_source`
- `source_data_updated_at`
- `generation_version`
- `status`
- 모델 또는 프롬프트 버전이 있다면 해당 버전
- 마지막 성공 실행 ID

기존 테이블 필드명을 우선 사용한다.

스키마 변경이 필요한 경우 최소 변경으로 구현한다.

### 5.3 생성 출처

다음 값을 저장한다.

```text
generation_source = manual | scheduled
```

예시:

- 관리자가 낮에 생성: `manual`
- 새벽 4시 Cron 생성: `scheduled`
- 새벽 정기 생성 후 관리자가 다시 생성: 최종값은 `manual`

부모 화면에는 생성 출처를 노출하지 않아도 된다.

관리자 화면에는 최종 생성 시각과 생성 방식을 표시할 수 있다.

### 5.4 생성 버전

같은 리포트가 정상 재생성될 때마다 `generation_version`을 1 증가시킨다.

예시:

```text
최초 수동 생성: version 1
새벽 정기 생성: version 2
관리자 재생성: version 3
```

실패한 실행은 정상 리포트 버전을 증가시키지 않는다.

## 6. 최신 데이터 판정 기준

재생성 결과를 저장할 때 단순히 실행 종료 시각만 비교하지 않는다.

다음 기준을 함께 사용한다.

- `source_data_updated_at`
- 처리한 Collection 또는 corrected 데이터의 최신 시각
- 실행 ID
- generation started_at
- generation completed_at

목표:

- 더 오래된 원천 데이터로 생성된 작업이 늦게 끝났다는 이유만으로 최신 결과를 덮어쓰지 않게 한다.
- 더 최신 원천 데이터를 포함한 결과가 최종 리포트가 되게 한다.

권장 저장 조건:

1. 새 결과의 `source_data_updated_at`이 기존 결과보다 최신이면 업데이트
2. 동일한 데이터 시점이면 나중에 정상 완료된 실행으로 업데이트 가능
3. 새 결과의 데이터 시점이 기존보다 과거이면 기존 정상 리포트를 덮어쓰지 않음

## 7. 동시 실행 및 중복 방지

### 7.1 동시 실행 잠금

같은 대상에 대해 다음 키로 동시 실행을 제어한다.

```text
child_id + report_date + report_type
```

적용 대상:

- 수동과 수동
- 수동과 정기
- 정기와 정기
- 전체 아이 실행과 특정 아이 실행 충돌

가능한 구현 방식:

- DB advisory lock
- 실행 Job 고유키
- 원자적 claim RPC
- unique constraint + 상태 기반 잠금
- 기존 pipeline job 구조 재사용

한 번에 하나의 활성 실행만 허용한다.

### 7.2 전체 아이 실행

전체 아이 실행 시 각 아이를 독립 Job으로 처리한다.

한 아이 실패가 나머지 아이 처리를 중단하지 않게 한다.

최종 결과에 다음을 구분한다.

- 성공
- 실패
- 건너뜀
- 이미 실행 중
- 대상 데이터 없음

### 7.3 재실행 허용

리포트가 이미 존재하더라도 재실행을 허용한다.

다음 이유로 완료된 리포트 재생성을 막지 않는다.

- 수동 생성 후 정기 생성
- 정기 생성 후 수동 생성
- 새로운 대화 데이터 반영
- 보정 결과 변경
- 프롬프트 또는 모델 개선
- 운영자 수동 복구

단, 같은 실행 요청이 네트워크 재시도로 중복 전송된 경우에는 동일 idempotency key로 중복 실행을 방지한다.

## 8. 실패 처리

### 8.1 기존 정상 리포트 보호

새로운 재생성이 실패해도 기존 정상 리포트를 삭제하거나 빈 데이터로 덮어쓰지 않는다.

다음 경우 기존 리포트를 유지한다.

- Memory Batch 실패
- Daily Report LLM 호출 실패
- DB 저장 실패
- 타임아웃
- 권한 오류
- 입력 데이터 부족
- 부분 생성 결과
- 빈 본문 반환
- 스키마 검증 실패

### 8.2 단계별 실패 정책

#### Collection 실패

- 해당 아이의 Context Correction 실행하지 않음
- 해당 아이는 실패 처리
- 다른 아이는 계속 진행

#### Context Correction 실패

- 보정 데이터가 필수라면 후속 단계 차단
- 실패 이유 명확히 표시
- 다른 아이는 계속 진행

#### Memory Batch 실패

- Daily Report가 보정 데이터 또는 기존 메모리만으로 생성 가능하면 계속 진행
- 불가능하면 리포트 생성 실패로 표시
- Memory Batch 실패를 리포트 생성 성공으로 숨기지 않음

#### Daily Report 실패

- 기존 정상 리포트 유지
- generation history에 실패 기록
- 관리자 화면에 실패 사유 표시

## 9. 생성 이력 보존

부모용 리포트 본문은 같은 날짜 기준 1건만 유지한다.

다만 생성 이력은 별도 로그 또는 기존 Job 테이블에 누적 보존한다.

최소 이력 필드:

- 실행 ID
- child_id
- report_date
- report_type
- execution_source
- started_at
- completed_at
- source_data_updated_at
- status
- generation_version
- error_code
- error_message 요약
- 처리 모델 또는 버전
- 실행 사용자 또는 Cron 식별자
- 기존 리포트 업데이트 여부

비밀정보와 대화 원문은 이력에 저장하지 않는다.

## 10. 관리자 화면 결과 표시

관리자에게 단순히 `성공`만 표시하지 않는다.

버튼 실행 결과에 내부 단계 상태를 요약해서 보여준다.

### 10.1 대화 수집 결과 예시

```text
대화 수집 완료

- 원본 수집: 성공
- 대화 보정: 성공
- 대상 아이: 9명
- 성공: 7명
- 대화 없음: 2명
- 실패: 0명
```

### 10.2 리포트 생성 결과 예시

```text
리포트 생성 완료

- 메모리 업데이트: 성공 7명 / 실패 1명 / 건너뜀 1명
- 일일 리포트: 생성 8명 / 실패 1명
- 기존 리포트 업데이트: 5건
- 신규 리포트 생성: 3건
```

### 10.3 데이터 없음 예시

```text
리포트 생성 불가

선택한 날짜에 보정된 대화 데이터가 없습니다.
먼저 `즉시 대화 수집`을 실행해 주세요.
```

`요청 처리 성공`과 `실제 리포트 생성 성공`을 구분한다.

## 11. 관리자 화면 상태 표시

아이별 V3 처리 상태에 다음을 표시한다.

- 수집
- 수집 보정
- 메모리 배치
- 리포트 생성
- 최종 생성 시각
- 생성 방식
- 리포트 버전
- 마지막 오류

상태 예시:

```text
수집: 완료
수집 보정: 완료
메모리 배치: 완료
리포트 생성: 완료
최종 생성: 2026-08-03 04:07 KST
생성 방식: 정기 생성
버전: 2
```

## 12. 날짜 및 타임존

모든 날짜 기준은 `Asia/Seoul`로 통일한다.

다음 값이 일치해야 한다.

- 관리자 선택 날짜
- business_date
- report_date
- Collection 대상 날짜
- corrected 데이터 날짜
- Memory Batch 대상 날짜
- Daily Report 날짜

UTC 변환으로 날짜가 하루 밀리지 않도록 한다.

특히 다음 시간대를 테스트한다.

- 00:00 KST 직후
- 17:55 KST 전후
- 23:55 KST 전후
- 04:00 KST 정기 실행
- 월말 및 연말 경계

## 13. 특정 아이와 전체 아이 처리

### 특정 아이

- 선택 child_id만 처리
- 연결되지 않은 다른 아이 데이터 접근 금지
- 해당 아이의 단계별 결과 반환

### 전체 아이

- 활성 및 승인 기준에 맞는 대상 아이 목록 확정
- 아이별 독립 처리
- 한 아이 실패가 전체 중단으로 이어지지 않음
- 처리 대상과 제외 대상을 결과에 표시
- 관리자·QA·테스트 계정 포함 여부는 기존 관리자 정책을 따름

---

## 14. 보안

- 관리자 수동 실행 API는 서버에서 관리자 권한 검증
- 클라이언트가 `manual` 값을 넘겼다는 이유만으로 실행 허용 금지
- Cron 실행은 서버 전용 Secret 또는 기존 인증 방식 사용
- Service Role Key를 클라이언트에 노출하지 않음
- API 키, 비밀번호, 토큰을 코드에 하드코딩하지 않음
- 비밀정보를 로그, 결과 화면, 임시파일에 출력하지 않음
- 오류 메시지에 DB 접속 정보나 내부 비밀값 포함 금지
- 기존 환경변수, Vercel Secrets, Supabase Secrets를 런타임에 사용
- 값은 로그에서 마스킹

## 16. 구현 전 필수 감사

코드 수정 전에 다음을 확인하고 보고한다.

1. 현재 세 버튼이 실제 호출하는 API 또는 함수
2. Collection 이후 Context Correction 자동 enqueue 여부
3. 리포트 생성 시 Memory Batch와 Daily Report 연결 여부
4. 정기 04시 실행이 호출하는 실제 경로
5. 수동과 정기가 같은 저장 로직을 사용하는지 여부
6. 동일 날짜 리포트가 INSERT인지 UPSERT인지 여부
7. 현재 고유키 존재 여부
8. 현재 리포트 생성 이력 저장 위치
9. 완료 Job 재실행 차단 로직 존재 여부
10. 수동 실행 시간 제한이 자동 Cron 로직과 결합되어 있는지 여부

감사 결과를 기준으로 필요한 부분만 수정한다.

## 20. 작업 금지 사항

- 수동과 정기 파이프라인을 별도 비즈니스 로직으로 중복 구현하지 않는다.
- 같은 날짜 리포트를 매번 새 행으로 추가하지 않는다.
- 실패 결과로 기존 정상 리포트를 삭제하거나 빈값으로 덮어쓰지 않는다.
- 실행 요청 성공을 실제 리포트 생성 성공으로 표시하지 않는다.
- 보정 데이터가 없는데 `대화 없음`만 표시하고 원인을 숨기지 않는다.
- 수동 실행에 자동 Cron 시간 제한을 적용하지 않는다.
- 클라이언트 입력만 믿고 관리자 실행을 허용하지 않는다.
- 서비스 역할 키를 브라우저에 노출하지 않는다.
- 비밀정보를 로그 또는 임시파일에 저장하지 않는다.
- 원본 대화 내용을 생성 이력에 저장하지 않는다.
- 기존 정상 자동 Cron을 중단하거나 변경하지 않는다.
- Production에 직접 테스트 데이터를 생성하지 않는다.
- Dev 검증 없이 Production에 배포하지 않는다.
