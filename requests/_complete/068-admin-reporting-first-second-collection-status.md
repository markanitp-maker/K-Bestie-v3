# Request: 관리자 리포팅 수동 실행 화면 1차·2차 대화 수집 분리 및 수집 건수 표시

## 1. 작업 목적

현재 관리자 `리포팅 수동 실행` 화면은 대화 수집 상태가 하나의 `대화수집` 열로만 표시되어 있어, 하루 2회 실행되는 수집 작업의 회차별 성공·실패·수집 건수를 구분할 수 없다.

실제 운영 정책에 맞춰 관리자 표를 아래처럼 분리한다.

| 이름 | 세션(미션/자유) | 1차 수집 18:00 | 2차 수집 23:59:59 | 보정 | Memory Batch | 리포트 |
|---|---:|---|---|---|---|---|
| 안서아 | 2 / 0 | 완료 · 수집 건수 | 대기/완료 · 수집 건수 | 상태 | 상태 | 생성/버전 |

이번 작업은 기존 Collection 파이프라인을 새로 두 개 만드는 작업이 아니다. 이미 하루 2회 실행되는 수집 작업을 회차별로 구분해 저장·조회·표시하는 작업이다.

---

## 2. 확정 운영 시간

대화 수집 회차는 아래 기준으로 고정한다.

```text
1차 수집: 18:00
2차 수집: 23:59:59
기준 시간대: Asia/Seoul
```

관리자 화면의 대상 날짜는 반드시 `Asia/Seoul` 기준 business date로 해석한다.

---

## 3. 관리자 표 변경

현재 표의 단일 `대화수집` 열을 제거하고 아래 열로 교체한다.

```text
이름
세션(미션/자유)
1차 수집 18:00
2차 수집 23:59:59
보정
Memory Batch
리포트
```

기존 `N/8` 열이 실제 운영상 필요하지 않거나 역할이 불명확하면 제거한다. 다만 코드·DB에서 다른 기능이 의존하는지 먼저 확인하고, 의존성이 있으면 데이터는 유지하되 화면에서만 제거한다.

### 열 너비 권장

- 이름: 160px
- 세션(미션/자유): 150px
- 1차 수집 18:00: 190px
- 2차 수집 23:59:59: 190px
- 보정: 130px
- Memory Batch: 150px
- 리포트: 160px

화면 폭이 좁으면 가로 스크롤을 허용하고, 모바일에서는 각 아이별 카드형 표시로 전환해도 된다.

---

## 4. 1차·2차 수집 셀 표시 규칙

각 수집 셀에는 최소한 아래 정보를 표시한다.

```text
상태
신규 수집 건수
실제 실행 시각
```

상태 예시:

```text
대기
실행 중
완료
부분 성공
실패
건너뜀
```

표시 예시:

```text
완료 · 신규 18건
18:00:12
```

```text
완료 · 신규 0건
기존 18건 확인
23:59:58
```

```text
부분 성공 · 신규 7건
실패 1건
00:00:21
```

```text
실패
오류 상세 보기
```

셀에는 너무 많은 텍스트를 넣지 말고, 상세 수치는 툴팁·팝오버 또는 상세 모달로 제공한다.

---

## 5. 수집 건수 정의

관리자에서 표시하는 `수집 건수`는 반드시 아래 기준으로 정의한다.

### 신규 수집 건수

```text
해당 회차 실행으로 corrected/raw collection 영역에 새로 저장된 대화 메시지 또는 대화 턴 수
```

이미 수집된 데이터를 재실행한 경우에는 신규 수집 건수로 다시 계산하지 않는다.

예시:

```text
첫 실행: 신규 18건
재실행: 신규 0건 · 기존 18건 확인
```

### 함께 저장할 집계값

가능한 경우 아래 값을 회차별로 저장·표시한다.

```text
target_session_count
collected_session_count
new_message_count
existing_message_count
skipped_count
failed_count
started_at
completed_at
```

관리자 기본 표에는 `new_message_count`를 우선 표시하고, 나머지는 상세 보기에서 확인 가능하게 한다.

---

## 6. 회차 식별 기준

1차·2차 수집 결과는 아래 고유 기준으로 분리한다.

```text
child_id
target_date
collection_slot
```

`collection_slot` 값은 아래처럼 명확한 enum 또는 상수로 관리한다.

```text
FIRST
SECOND
```

또는 프로젝트의 기존 명명 규칙에 맞춰 다음과 같이 사용할 수 있다.

```text
COLLECTION_1800
COLLECTION_235959
```

추측 enum을 새로 만들기 전에 기존 DB, Edge Function, Cron, job log 구조를 먼저 확인한다.

권장 고유 제약:

```text
child_id + target_date + collection_slot
```

같은 회차를 수동 재실행해도 새 실행 이력은 별도 job log에 남기되, 관리자 요약 상태는 가장 최근 성공 결과 또는 가장 최근 실행 결과 기준으로 명확히 표시한다.

---

## 7. 데이터 소스 및 백엔드 점검

먼저 아래 항목을 읽기 전용으로 감사한다.

1. 18:00 Collection Cron 또는 Scheduled Function
2. 23:59:59 Collection Cron 또는 Scheduled Function
3. 수동 Collection 실행 API
4. Collection 결과 저장 테이블
5. raw_daily_conversations
6. corrected_daily_conversations
7. 기존 job/status/log 테이블
8. child_id, target_date, collection_slot 또는 source 정보 저장 여부
9. 멱등성 기준
10. 관리자 화면이 현재 어떤 상태값을 조회하는지

현재 하나의 상태만 저장하거나 가장 최근 실행 결과로 덮어쓰는 구조라면, 회차별 상태가 유지되도록 수정한다.

기존 수집 데이터는 삭제하거나 재생성하지 않는다.

---

## 8. 수동 실행 버튼 변경

현재 `대화 수집` 버튼 하나가 있다면 아래 방식으로 분리한다.

```text
1차 수집 실행
2차 수집 실행
전체 수집 실행
수집 후 리포트 생성
```

### 1차 수집 실행

- 선택한 대상 날짜
- 선택한 아이 또는 전체 아이
- `collection_slot = FIRST`
- 18:00 회차 기준 데이터만 수집

### 2차 수집 실행

- 선택한 대상 날짜
- 선택한 아이 또는 전체 아이
- `collection_slot = SECOND`
- 23:59:59 회차 기준 데이터만 수집

### 전체 수집 실행

- 1차 수집 실행
- 2차 수집 실행
- 각 회차 결과를 독립적으로 표시
- 하나가 실패해도 다른 하나의 성공 결과를 보존

### 수집 후 리포트 생성

권장 실행 순서:

```text
1차 수집
→ 2차 수집
→ Context Correction
→ Memory Batch
→ Daily Report UPSERT
```

단, 대상 날짜와 현재 시각에 따라 아직 2차 수집 시간이 도래하지 않은 경우 강제 실행 여부를 관리자에게 명확히 안내한다.

---

## 9. 보정 상태 표시

`보정` 열에는 Context Correction 상태를 표시한다.

표시 예시:

```text
대기
실행 중
완료 · 25건
부분 성공 · 24/25건
실패
건너뜀 · 수집 데이터 없음
```

보정 입력은 1차와 2차 수집 결과를 모두 포함하되, 중복 메시지는 멱등하게 제거한다.

보정 건수와 수집 건수가 다를 수 있으므로 두 수치를 혼동하지 않는다.

---

## 10. Memory Batch 상태 표시

`Memory Batch` 열에는 아래 상태를 표시한다.

```text
대기
실행 중
완료
건너뜀 · 보정 데이터 없음
실패
재시도 필요
```

가능하면 생성·갱신된 memory fact 수를 상세 보기에서 확인할 수 있게 한다.

---

## 11. 리포트 상태 표시

`리포트` 열에는 아래를 표시한다.

```text
미생성
생성 중
생성 완료 · v1
갱신 완료 · v2
건너뜀
실패
```

동일 `child_id + report_date + report_type`은 UPSERT 정책을 유지한다.

실패한 재실행이 기존 정상 리포트를 덮어쓰지 않게 한다.

## 13. 상태 판정 규칙

### 대기

- 아직 실행 기록이 없음
- 또는 해당 회차 실행 시각이 도래하지 않음

### 완료

- 대상 세션 처리 완료
- 실패 0건
- 신규 수집이 0건이어도 기존 데이터 확인이 정상 완료되면 완료로 표시 가능

### 부분 성공

- 일부 세션 성공
- 일부 세션 실패

### 실패

- 실행 자체 실패
- 또는 모든 대상 세션 실패

### 건너뜀

- 대상 세션 없음
- 이미 수집 완료되어 신규 처리 없음
- 정책상 실행 대상 아님

`신규 0건`을 자동으로 실패로 판단하지 않는다.

## 14. 세션 수와 수집 건수 관계

`세션(미션/자유)` 열은 대상 날짜의 원천 세션 수를 표시한다.

예시:

```text
2 / 0
```

이는 아래 의미다.

```text
미션 세션 2개
자유대화 세션 0개
```

수집 건수는 세션 수가 아니라 메시지 또는 대화 턴 수이므로 값이 더 클 수 있다.

예시:

```text
세션 2 / 0
1차 수집 신규 18건
```

관리자에게 오해가 없도록 열 제목 또는 툴팁에 정의를 명시한다.

---

## 15. 조회 기간 및 KST 정합성

아래 모든 단계가 동일한 날짜 기준을 사용해야 한다.

```text
대상 날짜
세션 수
1차 수집
2차 수집
보정
Memory Batch
리포트
```

기준:

```text
Asia/Seoul
00:00:00 ~ 23:59:59.999
```

UTC 저장값을 화면에 표시하거나 집계할 때 KST business date로 정확히 변환한다.

23:59:59 실행이 UTC 기준 다음 날짜로 잘못 분류되지 않게 E2E 테스트한다.

---

## 16. 기존 데이터 호환

기존 실행 이력에 `collection_slot`이 없는 경우 임의로 잘못 분류하지 않는다.

가능한 처리 방식:

1. 실행 시각이 명확한 경우
   - 18:00 회차 근처 → FIRST
   - 23:59:59 회차 근처 → SECOND
2. 실행 시각 또는 출처로 판단할 수 없는 경우
   - `기존 통합 기록`으로 표시
   - 관리자에게 확인 필요 상태 표시
3. 과거 데이터를 강제로 업데이트하지 않고 신규 실행부터 정확히 분리

기존 데이터 마이그레이션이 필요하면 적용 전 대상 건수와 판정 기준을 보고한다.

## 17. API 요구사항

프로젝트 구조에 맞춰 아래와 같은 조회·실행 API를 구성한다.

예시:

```text
GET /api/admin/reporting/status?date=YYYY-MM-DD
POST /api/admin/reporting/collection/first
POST /api/admin/reporting/collection/second
POST /api/admin/reporting/collection/all
GET /api/admin/reporting/jobs/:jobId
```

공통 요구사항:

- 관리자 인증 필수
- 관리자 권한 확인
- child_id 허용 여부 검증
- 대상 날짜 검증
- collection_slot 서버 고정
- 중복 실행 방지 또는 멱등 처리
- 실행 중인 동일 작업이 있으면 중복 실행 차단
- 클라이언트에서 Service Role Key 사용 금지

## 18. UI 디자인 기준

첨부 이미지와 동일한 정보 구조를 적용한다.

테이블 헤더:

```text
이름 | 세션(미션/자유) | 1차 수집 18:00 | 2차 수집 23:59:59 | 보정 | Memory Batch | 리포트
```

권장 상태 표시:

- 완료: 초록색 배지
- 대기: 회색 배지

- 건너뜀: 중립 회색 배지

색상만으로 상태를 구분하지 말고 텍스트를 함께 표시한다.

## 19. 테스트 요구사항

### 단위 테스트

- FIRST 회차 상태 저장
- SECOND 회차 상태 저장
- 두 회차 상태 독립 유지
- 동일 회차 재실행 멱등성
- 신규 수집 건수 계산
- 기존 메시지 중복 제외
- KST 날짜 변환
- 23:59:59 경계 처리
- 부분 성공 판정
- 수집 0건 완료 판정

### E2E 테스트

대표 아이 최소 2명으로 검증한다.

1. 대상 날짜 선택
2. 1차 수집 실행
3. 1차 열 상태·건수 표시 확인
4. 2차 열은 대기 상태 유지 확인
5. 2차 수집 실행
6. 2차 열 상태·건수 표시 확인
7. 1차 결과가 덮어써지지 않는지 확인
8. 전체 수집 재실행
9. 신규 0건·기존 데이터 확인 표시 확인
10. 보정 실행
11. Memory Batch 실행
12. 리포트 생성·버전 표시 확인

### Production 스모크 테스트

Production QA 아이인 TestA 또는 TestB만 사용한다.

실제 사용자 데이터를 임의 수정하거나 재수집하지 않는다.
