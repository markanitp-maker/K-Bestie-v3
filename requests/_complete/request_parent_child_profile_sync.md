# 부모 설정 자녀 정보 수정값 전체 화면 동기화

## 1. 작업 목적

부모가 `부모 설정 > 아이 정보 관리 > 수정하기`에서 자녀의 이름, 학년, 성별, 관심사 등 프로필 정보를 수정하고 저장하면, 부모 화면의 모든 관련 영역에 최신 정보가 즉시 동일하게 표시되도록 수정한다.

현재는 자녀 프로필 수정 화면과 아이 정보 관리 카드에는 변경된 학년이 표시되지만, `아이 승인 요청 현황`에는 가입 신청 당시 학년이 계속 표시되어 부모가 수정이 정상 반영되지 않은 것으로 오해할 수 있다.

---

## 2. 실제 발생 사례

### 박서동 재현 사례

1. 최초 가입 시 `5학년`으로 등록
2. 부모 설정의 아이 정보 관리에서 `6학년`으로 수정
3. 수정 팝업에는 `6학년` 표시
4. 아이 정보 관리 카드에도 `6학년` 표시
5. 아이 승인 요청 현황에는 계속 `5학년` 표시

### 안여원 실제 사례

실제 사용자 계정에서도 동일한 형태의 자녀 정보 불일치가 발생했다.

개인정보가 포함된 계정 정보, 내부 ID, 이메일, 인증정보는 로그와 결과 보고서에서 반드시 마스킹한다.

---

## 3. 확정 원인

현재 화면별 데이터 원천이 다르다.

- 자녀 프로필 수정 및 아이 정보 관리 카드
  - `child_profiles`의 최신 프로필 정보 사용
- 아이 승인 요청 현황
  - `child_approval_requests`의 가입 신청 당시 정보 사용

`child_approval_requests.grade`는 가입 당시 학년 스냅샷이므로, 이후 자녀 프로필을 수정해도 값이 자동 변경되지 않는다.

이번 문제는 다음 항목이 아니다.

- 자녀 프로필 저장 실패가 아님
- 캐시만 남아 있는 문제가 아님
- 미션이나 리포트가 과거 학년을 사용하는 문제가 아님

현재 확인된 핵심 문제는 승인 완료된 아이에게도 가입 당시 신청 정보를 사용자 화면에 계속 표시하는 것이다.

---

## 4. 제품 정책 확정

### 승인 완료된 아이

부모에게 노출되는 모든 화면은 `child_profiles`의 최신 정보를 기준으로 표시한다.

적용 대상은 최소 다음 항목을 포함한다.

- 이름
- 학년
- 성별
- 관심사
- 요금제 또는 자녀 프로필과 연결된 현재 상태 정보

### 승인 대기 중인 아이

아직 `child_profiles`가 생성되지 않았거나 승인 완료된 자녀 계정과 연결되지 않은 경우에만 `child_approval_requests`의 신청 정보를 표시한다.

### 가입 당시 신청 정보

가입 당시 값은 감사 및 이력 관리 목적으로 내부 DB에 보존할 수 있으나, 승인 완료 후 부모 화면의 현재 자녀 정보로 사용하거나 노출하지 않는다.

## 5. 핵심 요구사항

### 5.1 최신 자녀 정보 단일 기준 적용

승인 완료된 자녀는 `child_profiles`를 부모 노출 정보의 단일 기준으로 사용한다.

`아이 승인 요청 현황`도 승인 완료 상태라면 다음처럼 현재 프로필을 표시해야 한다.

- 수정 전: `박서동 · 5학년`
- 수정 후: `박서동 · 6학년`

부모가 이름을 수정한 경우에도 같은 원칙을 적용한다.

### 5.2 이름 기반 매칭 금지

다음 방식으로 자녀와 승인 요청을 연결하지 않는다.

- 이름 문자열 비교
- 성과 이름 조합 비교
- `family_id + 이름` 비교
- 배열 순서 또는 화면 순서 기반 매칭

반드시 실제 스키마의 안정적인 관계를 사용한다.

우선 확인 대상:

- `child_id`
- `child_profile_id`
- `user_id`
- `family_member_id`
- `approval_request_id`
- 승인 처리 시 생성·연결되는 기존 FK

기존 스키마에 안정적인 FK가 없다면 임의로 이름 매칭을 추가하지 말고, 승인 요청과 생성된 자녀 프로필을 연결하는 명시적인 FK를 추가한다.

### 5.3 저장 직후 즉시 동기화

부모가 자녀 정보를 수정하고 저장 성공 응답을 받은 직후 다음 영역이 모두 최신 값으로 변경되어야 한다.

- 자녀 프로필 수정 팝업
- 아이 정보 관리 카드
- 아이 승인 요청 현황
- 같은 화면에서 자녀 이름 또는 학년을 표시하는 다른 컴포넌트

다음 행동이 없어도 변경되어야 한다.

- 수동 새로고침
- 로그아웃 후 재로그인
- 앱 재실행
- 다른 메뉴 이동 후 복귀

현재 상태 관리 방식에 맞춰 다음 중 적절한 방법을 사용한다.

- React Query invalidate/refetch
- SWR mutate
- 서버 데이터 재조회
- 로컬 상태의 일관된 갱신
- `router.refresh()`가 필요한 구조라면 저장 성공 후 최소 범위로 적용

불필요하게 전체 페이지를 강제 리로드하지 않는다.

## 6. API 및 조회 구조 변경

### 6.1 승인 요청 현황 API

대상 후보:

`app/api/families/[id]/child-approval-requests/route.ts`

현재 승인 요청 데이터만 반환하고 있다면 승인 상태에 따라 현재 자녀 프로필 정보를 함께 반환하도록 변경한다.

권장 응답 구조 예시:

```ts
{
  id: string;
  status: "pending" | "approved" | "rejected";
  requestedProfile: {
    familyName: string;
    givenName: string;
    grade: number | string;
  };
  currentProfile: {
    childProfileId: string;
    name: string;
    grade: number | string;
    gender?: string | null;
    interests?: string[];
  } | null;
}
```

프런트엔드 표시 규칙:

```ts
const displayProfile =
  request.status === "approved" && request.currentProfile
    ? request.currentProfile
    : request.requestedProfile;
```

기존 API 필드를 사용하는 다른 화면이 있다면 하위 호환성을 확인한 뒤 변경한다.

### 6.2 프로필 수정 API

대상 후보:

`PATCH /api/child/[id]`

확인 사항:

- 저장 대상이 `child_profiles`인지 확인
- 수정 가능한 모든 필드가 실제로 업데이트되는지 확인
- 성공 응답에 최신 자녀 프로필 전체를 반환하는지 확인
- 업데이트 후 잘못된 캐시가 남지 않는지 확인
- 승인 요청 이력 테이블을 현재 값으로 덮어쓰는 방식은 사용하지 않음

## 7. 데이터 모델 및 마이그레이션

### 7.1 기존 FK가 있는 경우

기존 관계를 사용해 승인 요청과 현재 자녀 프로필을 연결한다.

추가 컬럼이나 마이그레이션을 만들지 않는다.

### 7.2 기존 FK가 없는 경우

`child_approval_requests`와 승인 완료 후 생성된 `child_profiles`를 안정적으로 연결할 수 있는 명시적 FK를 추가한다.

권장 후보:

```sql
child_approval_requests.child_profile_id
```

요구사항:

- 승인 완료 처리 시 생성 또는 연결된 `child_profiles.id` 저장
- 승인 완료 요청에만 값 설정
- 승인 대기 중에는 `NULL` 허용
- FK 제약조건 적용
- 필요한 인덱스 추가
- 기존 승인 완료 데이터에 대한 안전한 백필 계획 수립
- 이름 기반 자동 백필 금지
- 사용자 ID, 가족 관계, 승인 처리 이력 등 확실한 식별 관계가 있는 데이터만 백필
- 확실하지 않은 데이터는 자동 연결하지 않고 별도 보고

---

## 8. 기존 데이터 처리

이미 승인 완료된 사용자 중 현재 프로필과 가입 당시 정보가 다른 계정을 점검한다.

최소 점검 대상:

- 박서동
- 안여원
- 동일한 패턴의 다른 승인 완료 계정

수정 원칙:

- `child_profiles`의 현재 값을 정답으로 사용
- `child_approval_requests`의 과거 신청 정보는 삭제하거나 덮어쓰지 않음
- 승인 완료 화면에서는 현재 프로필만 표시
- 잘못 연결된 자녀가 없는지 가족별 복수 자녀 관계 검증

---

## 9. 서비스 로직 영향 확인

이번 수정은 부모 설정 화면 표시 문제 해결이 목적이다.

다음 기능이 계속 `child_profiles.grade`의 최신 값을 사용하는지 회귀 확인한다.

- 미션 질문 학년 선택
- 일반 미션 응답 프롬프트
- 학년별 질문지
- 퀴즈마스터 학년
- 학년별 놀이 콘텐츠
- 일일·주간·월간 리포트
- 부모-케이 질의에서 사용하는 자녀 프로필
- LLM Wiki 또는 메모리 컨텍스트의 자녀 기본 정보

이 기능들의 기존 데이터 원천을 불필요하게 변경하지 않는다.

## 10. UI 표시 규칙

### 승인 대기

```text
박서동 · 5학년
승인 대기
```

신청 당시 정보를 표시한다.

### 승인 완료

```text
박서동 · 6학년
승인 완료
```

현재 `child_profiles`의 최신 정보를 표시한다.

### 프로필 조회 실패

승인 완료 상태인데 현재 프로필을 찾지 못한 경우 과거 값을 조용히 대신 표시하지 않는다.

다음 중 서비스의 기존 오류 처리 규칙에 맞춰 명확히 처리한다.

- `정보 확인 필요`
- 재조회
- 오류 로그 및 관리자 점검 대상 등록

승인 완료 상태에서 프로필 연결이 끊어진 데이터 무결성 문제를 숨기지 않는다.

## 11. 테스트 시나리오

### 11.1 기본 재현 테스트

1. 아이를 5학년으로 가입
2. 관리자 승인 완료
3. 부모 설정에서 6학년으로 수정
4. 저장 성공 확인
5. 다음 영역이 모두 6학년인지 확인
   - 수정 팝업
   - 아이 정보 관리 카드
   - 아이 승인 요청 현황
6. 새로고침 후에도 6학년 유지
7. 로그아웃 후 재로그인해도 6학년 유지

### 11.2 이름 수정 테스트

1. 승인 완료된 자녀 이름 수정
2. 모든 부모 화면에 수정된 이름 즉시 표시
3. 승인 요청 당시 이름이 다시 노출되지 않는지 확인

### 11.3 복수 자녀 테스트

1. 같은 부모 계정에 자녀 2명 이상 등록
2. 한 명의 학년만 수정
3. 수정한 아이만 변경되는지 확인
4. 다른 아이의 이름·학년과 교차 매핑되지 않는지 확인

### 11.4 승인 대기 테스트

1. 아직 승인되지 않은 아이 생성
2. 승인 요청 현황에 신청 당시 정보 표시
3. 승인 전에는 존재하지 않는 `child_profiles`를 잘못 참조하지 않는지 확인

### 11.5 승인 완료 연결 오류 테스트

1. 승인 완료인데 `currentProfile` 연결이 없는 비정상 데이터 구성
2. 과거 신청값으로 조용히 대체하지 않는지 확인
3. 오류가 로그 또는 관리자 점검 대상으로 남는지 확인

### 11.6 서비스 로직 회귀 테스트

학년을 5학년에서 6학년으로 수정한 뒤 다음 기능이 6학년 기준으로 동작하는지 확인한다.

- 미션 질문
- 퀴즈
- 학년별 콘텐츠
- 리포트 생성
- 부모-케이 대화의 자녀 프로필 참조

## 12. 완료 조건

다음 조건을 모두 충족해야 완료로 판단한다.

- 승인 완료된 아이는 모든 부모 화면에서 `child_profiles` 최신 정보 표시
- 승인 대기 아이만 신청 당시 정보 표시
- 부모가 수정한 이름·학년·성별·관심사가 저장 직후 모든 관련 영역에 즉시 반영
- 새로고침 및 재로그인 후에도 최신 값 유지
- 이름 기반 매칭 없음
- 복수 자녀 간 오매핑 없음
- 가입 당시 승인 요청 이력은 내부에 보존
- 기존 미션·퀴즈·리포트 로직에 회귀 오류 없음
- Dev 검증 완료
- Dev 통과 후 Production 반영 및 동일 시나리오 검증 완료
- 개인정보와 비밀정보가 로그, 임시파일, 커밋에 포함되지 않음

## 13. 보안 및 작업 제한

- Production service role key, API key, 비밀번호, 토큰 평문 출력 금지
- 비밀정보 하드코딩 금지
- 임시 스크립트에 비밀정보 저장 금지
- 개인정보 전체 출력 금지
- 로그의 사용자 ID, 이메일, 이름 등은 필요한 최소 범위만 마스킹
- 기존 Vercel/Supabase Secrets 또는 환경변수를 런타임에만 사용
- 진단용 임시 파일과 사용자 데이터 출력 로그는 커밋 전 제거
- 승인 요청 이력 일괄 삭제 금지
- 이름 기준 데이터 일괄 매칭 및 백필 금지

## 14. 작업 순서

1. 현재 승인 요청과 자녀 프로필의 FK 관계 확인

3. API 응답 구조 설계
4. 승인 완료 시 현재 프로필을 반환하도록 서버 조회 수정
5. 승인 대기 시 신청 정보를 유지하도록 분기
6. 저장 성공 후 화면 전체 데이터 재조회 또는 상태 동기화
7. Dev DB 기준 재현 및 회귀 테스트
