핵심 정책은 **신규·기존 사용자 모두 알림 권한 획득 과정을 반드시 거치게 하되, 운영체제 권한창은 사용자 클릭 직후 호출**하는 것입니다. 브라우저 정책상 PWA 설치와 동시에 알림을 자동 승인시키거나 사용자 동작 없이 권한창을 강제로 띄울 수는 없습니다. 특히 iPhone·iPad의 홈 화면 웹앱도 직접적인 사용자 터치에 응답해 권한을 요청해야 합니다. 

아래 내용을 `Request.md`로 사용하면 됩니다.

````md
# Request: 부모·아이 PWA 알림 온보딩 및 정기 푸시 알림 구현

## 1. 작업 목적

현재 부모용·아이용 PWA 홈 화면 하단에 사용자가 직접 눌러야 하는 `알림 켜기` 버튼이 존재한다.

이 구조는 사용자가 기능을 발견하고 직접 활성화해야 하므로 알림 허용률이 낮고, 부모 리포트 및 아이 미션 시작 알림을 놓칠 가능성이 크다.

알림을 선택적 부가 기능처럼 하단에 배치하지 말고, 신규 사용자와 기존 사용자 모두가 PWA를 처음 사용하는 흐름에서 알림 허용 여부를 명확하게 결정하도록 온보딩 구조를 변경한다.

---

## 2. 핵심 요구사항

### 2.1 적용 대상

다음 사용자에게 모두 동일하게 적용한다.

- 신규 부모 사용자
- 신규 아이 사용자
- 기존 부모 사용자
- 기존 아이 사용자
- 현재 운영 중인 기존 사용자 전체
- 이후 추가되는 모든 사용자

알림 권한과 푸시 구독은 다음 단위로 분리한다.

- 사용자 계정
- 부모 또는 아이 역할
- 아이 프로필
- 사용 기기
- 브라우저 또는 PWA 설치 인스턴스

부모와 아이의 구독 정보가 서로 섞이지 않아야 한다.

---

## 3. 브라우저 정책 전제

PWA 설치만으로 알림 권한을 자동 승인할 수 있다고 가정하지 않는다.

알림 권한 요청은 브라우저 정책에 맞게 반드시 사용자의 명시적인 터치 또는 클릭 직후 실행한다.

따라서 설치 과정 또는 첫 실행 과정에서 자체 안내 화면을 먼저 보여주고, 사용자가 `알림 받기`를 누르면 즉시 운영체제 또는 브라우저의 알림 권한창을 호출한다.

설치 버튼 클릭과 알림 권한 요청을 기술적으로 하나의 이벤트로 무리하게 결합하지 말고, 플랫폼별 제약에 맞춰 아래 흐름을 구현한다.

1. PWA 설치 또는 홈 화면 추가
2. 설치된 PWA 첫 실행
3. 알림 안내 온보딩 표시
4. 사용자가 `알림 받기` 선택
5. 브라우저 알림 권한 요청
6. 권한 승인 시 Push Subscription 생성 및 서버 저장
7. 권한 거부 시 재활성화 안내 상태 저장

---

## 4. 신규 사용자 온보딩

### 4.1 기본 흐름

신규 사용자가 부모용 또는 아이용 PWA를 처음 실행하면 알림 온보딩을 표시한다.

알림 온보딩은 홈 화면 하단의 작은 버튼이 아니라, 사용자가 반드시 인지할 수 있는 모달 또는 전용 온보딩 단계로 제공한다.

### 4.2 부모용 안내 문구

제목:

`매일 아침 아이의 하루를 확인하세요`

설명:

`아이의 활동 리포트가 준비되면 오전 7시에 알려드려요. 출근 준비 중에도 아이의 어제 활동과 변화를 바로 확인할 수 있어요.`

주요 버튼:

`아침 리포트 알림 받기`

보조 버튼:

`나중에 설정하기`

### 4.3 아이용 안내 문구

제목:

`미션이 시작되면 알려줄게요`

설명:

`오늘 할 수 있는 미션이 시작되면 케이가 알려줘요. 중요한 미션을 놓치지 않도록 알림을 켜주세요.`

주요 버튼:

`미션 알림 받기`

보조 버튼:

`나중에 설정하기`

### 4.4 권한 요청 시점

운영체제 또는 브라우저의 `Notification.requestPermission()` 호출은 사용자가 주요 버튼을 누른 이벤트 핸들러 안에서 즉시 실행한다.

페이지 로드, 앱 시작, 타이머, 비동기 초기화 완료 이벤트만으로 권한창을 자동 호출하지 않는다.

---

## 5. 기존 사용자 전환

현재 사용 중인 기존 사용자도 앱 업데이트 후 알림 권한 획득 흐름을 거쳐야 한다.

### 5.1 표시 조건

다음 조건을 모두 만족하면 업데이트 후 첫 실행 시 알림 온보딩을 표시한다.

- 현재 알림 권한이 `default` 상태
- 해당 기기에 유효한 Push Subscription이 없음
- 해당 버전의 알림 온보딩을 완료하지 않음

### 5.2 기존 사용자 안내

제목:

`새로운 알림 기능이 추가됐어요`

부모 설명:

`매일 오전 7시, 아이의 리포트가 준비되면 알려드려요.`

아이 설명:

`미션을 시작할 시간이 되면 케이가 알려줘요.`

주요 버튼:

`알림 받기`

보조 버튼:

`나중에`

### 5.3 중복 방지

이미 알림 권한이 승인되어 있고 유효한 구독이 존재하는 사용자에게 온보딩을 다시 표시하지 않는다.

기존 구독이 서버에는 있지만 브라우저에서 사라진 경우에는 구독을 재생성한다.

브라우저에는 구독이 있지만 서버에 없는 경우에는 서버에 다시 등록한다.

---

## 6. 권한 상태별 처리

### 6.1 `granted`

- Service Worker 등록 상태 확인
- 기존 Push Subscription 조회
- 없으면 신규 구독 생성
- 구독 정보를 서버에 저장
- UI 상태를 `알림 켜짐`으로 표시
- 알림 온보딩 완료 처리
- 테스트 알림 또는 등록 완료 메시지 제공

### 6.2 `default`

- 알림 온보딩 표시 가능
- 사용자 클릭 전에는 권한 요청 금지
- 사용자가 `나중에`를 선택한 경우 일정한 재안내 정책 적용
- 매번 강제 팝업으로 앱 사용을 방해하지 않도록 노출 빈도를 관리

### 6.3 `denied`

브라우저가 이미 거부 상태이면 권한 요청 API를 반복 호출하지 않는다.

다음 내용을 안내한다.

- 현재 알림이 차단되어 있다는 사실
- 운영체제 또는 브라우저 설정에서 직접 허용해야 한다는 사실
- 현재 기기와 브라우저에 맞는 설정 경로
- 설정 변경 후 앱으로 돌아와 상태를 다시 확인하는 버튼

버튼 예시:

`알림 설정 방법 보기`

`권한 다시 확인`

### 6.4 브라우저 미지원

- 알림 기능 미지원 여부를 명확하게 안내
- 앱의 다른 기능은 정상적으로 사용할 수 있어야 함
- 로그인 해제 또는 앱 오류로 처리하지 않음
- 지원 브라우저 또는 설치 방법을 안내

---

## 7. 알림을 허용하지 않은 사용자 재안내

사용자가 알림을 허용하지 않았다고 해서 로그인할 때마다 운영체제 권한창을 강제로 호출하지 않는다.

대신 앱 내부 안내를 지속적으로 제공한다.

### 7.1 `default` 상태

홈 화면 또는 주요 진입 화면에 알림 활성화 배너를 표시한다.

부모 문구:

`아침 리포트 알림이 꺼져 있어요. 아이의 리포트가 준비되면 알려드릴까요?`

아이 문구:

`미션 알림이 꺼져 있어요. 시작 시간을 놓치지 않도록 알림을 켜주세요.`

버튼:

`알림 켜기`

사용자가 버튼을 눌렀을 때만 권한창을 호출한다.

### 7.2 `denied` 상태

홈 화면에 다음 상태를 표시한다.

`알림이 차단되어 있어요`

버튼:

`설정에서 허용하기`

버튼 선택 시 기기별 설정 방법을 안내한다.

### 7.3 노출 정책

다음 원칙을 적용한다.

- 운영체제 권한창을 반복 호출하지 않음
- 자체 안내 배너는 앱 실행 시 확인할 수 있도록 유지
- 전체 화면 모달은 매 로그인마다 강제로 표시하지 않음
- 사용자의 거부 의사를 존중하면서 설정 복구 경로는 계속 제공
- 온보딩 버전과 마지막 안내 시각을 저장해 과도한 반복 노출 방지

권장 기준:

- 첫 실행: 온보딩 모달
- `나중에` 선택 후 다음 실행: 홈 배너
- 이후: 홈 배너 상시 표시
- 중요한 알림 기능 업데이트가 있을 때만 모달 재노출 검토

---

## 8. 알림 해제 정책

사용자가 운영체제 설정에서 알림을 끄거나 앱 내 알림 해제를 선택한 경우 다음과 같이 처리한다.

- 해당 기기로 푸시 발송 중단
- 사용자 계정과 앱 기능은 그대로 유지
- 로그인 상태를 해제하지 않음
- 다른 기기의 구독은 유지
- 앱 화면에 `알림 꺼짐` 상태 표시
- 다시 활성화할 수 있는 설정 경로 제공
- 서버 구독 상태와 브라우저 권한 상태를 주기적으로 동기화

앱 내에서 알림 끄기 기능을 제공할 경우 해당 기기의 Push Subscription을 서버에서 비활성화하거나 삭제한다.

## 9. 부모용 리포트 알림

### 9.1 리포트 생성

부모용 일일 리포트 생성 작업은 매일 새벽 4시경 수행한다.

리포트 생성과 알림 발송을 분리한다.

### 9.2 발송 시각

부모 알림은 매일 오전 7시에 발송한다.

기본 시간대는 사용자 또는 가족 계정의 시간대를 사용하며, 현재 서비스 기본 시간대는 `Asia/Seoul`로 처리한다.

### 9.3 발송 조건

다음 조건을 모두 만족할 때만 발송한다.

- 해당 날짜의 리포트 생성 완료
- 리포트 상태가 열람 가능한 상태
- 부모 계정에 활성화된 기기 구독이 존재
- 부모가 리포트 알림을 활성화
- 해당 날짜와 부모 계정에 아직 동일 알림을 발송하지 않음

리포트 생성 실패, 지연 또는 데이터 없음 상태에서는 정상 리포트가 생성된 것처럼 알림을 보내지 않는다.

### 9.4 알림 문구 예시

제목:

`오늘의 아이 리포트가 준비됐어요`

본문:

`어제 아이가 케이와 나눈 활동과 변화를 확인해보세요.`

알림 클릭 시 해당 날짜의 부모 리포트 상세 화면으로 이동한다.

### 9.5 중복 방지 키

다음과 같은 멱등성 키를 적용한다.

`parent_id + report_date + notification_type`

다중 기기 정책은 명확하게 정의한다.

- 부모의 모든 활성 기기에 발송하거나
- 최근 사용 기기만 발송

현재 단계에서는 부모가 사용하는 모든 활성 기기에 발송하되, 동일 기기에는 한 번만 발송한다.

## 10. 아이용 미션 알림

아이 알림은 부모 리포트 알림과 별도로 관리한다.

발송 조건:

- 해당 아이에게 활성 미션 존재
- 미션 시작 가능 시간 도달
- 아이 계정 또는 아이 전용 기기에 활성 구독 존재
- 해당 미션 알림 미발송
- 부모의 알림 정책 또는 제한 설정을 위반하지 않음

알림 문구 예시:

제목:

`오늘의 미션이 시작됐어`

본문:

`케이와 함께 오늘의 미션을 시작해볼까?`

알림 클릭 시 해당 아이의 미션 시작 화면으로 이동한다.

중복 방지 키:

`child_id + mission_id + scheduled_at + notification_type`

## 11. 데이터 구조

현재 데이터 모델을 우선 분석하고, 기존 구조가 부족하면 다음 정보를 저장할 수 있도록 확장한다.

### 11.1 Push Subscription

필수 필드 예시:

- `id`
- `user_id`
- `child_id` nullable
- `role`
- `device_id`
- `installation_id`
- `endpoint`
- `p256dh`
- `auth`
- `platform`
- `browser`
- `user_agent`
- `permission_status`
- `is_active`
- `last_seen_at`
- `created_at`
- `updated_at`
- `revoked_at`

### 11.2 Notification Preference

필수 필드 예시:

- `user_id`
- `child_id` nullable
- `parent_report_enabled`
- `mission_start_enabled`
- `timezone`
- `parent_report_time`
- `onboarding_version`
- `onboarding_completed_at`
- `last_prompted_at`
- `created_at`
- `updated_at`

민감한 구독 정보는 로그에 원문으로 출력하지 않는다.

RLS 또는 접근 제어 정책을 적용하여 다른 가족이나 사용자 구독 정보를 조회하거나 변경할 수 없도록 한다.

## 12. Service Worker 및 푸시 처리

다음을 구현 또는 점검한다.

- Service Worker 정상 등록
- `push` 이벤트 처리
- `notificationclick` 이벤트 처리
- 앱이 닫혀 있거나 백그라운드인 경우에도 알림 표시
- 알림 클릭 시 정확한 화면으로 이동
- 이미 열린 PWA 창이 있으면 기존 창 활성화
- 필요한 경우 새 창 생성
- 만료되거나 해지된 구독 자동 비활성화
- 푸시 제공자가 구독 만료 응답을 반환하면 서버 데이터 정리
- 앱 업데이트 시 기존 구독 유지
- Service Worker 교체 과정에서 알림 구독이 불필요하게 삭제되지 않도록 처리

---

## 13. 발송 스케줄러

부모 리포트 생성 작업과 오전 7시 알림 발송 작업을 분리한다.

예시 흐름:

1. 새벽 4시 리포트 생성 작업 시작
2. 부모·아이별 리포트 생성
3. 생성 상태와 완료 시각 저장
4. 오전 7시 알림 대상 조회
5. 생성 완료된 리포트만 발송 큐에 등록
6. 기기별 푸시 발송
7. 성공·실패·만료 결과 기록
8. 재시도 가능한 오류만 제한적으로 재시도
9. 멱등성 키로 중복 발송 방지

서버 시간대가 UTC이더라도 사용자 기준 오전 7시가 정확히 계산되어야 한다.

## 14. 오류 및 재시도 정책

다음을 서로 다른 오류로 구분한다.

- 알림 권한 거부
- 브라우저 미지원
- PWA 미설치
- Service Worker 등록 실패
- Push Subscription 생성 실패
- 서버 구독 저장 실패
- 네트워크 일시 오류
- 푸시 제공자 오류
- 만료된 구독
- 리포트 미생성
- 스케줄러 지연
- 중복 발송 차단

일시적인 네트워크 실패는 사용자 로그아웃으로 처리하지 않는다.

서버 발송 실패는 지수 백오프 또는 현재 프로젝트 표준 재시도 정책을 적용하되, 오전 리포트 알림이 지나치게 늦게 발송되지 않도록 최대 재시도 시간과 만료 시간을 둔다.

## 16. 보안 및 개인정보

- VAPID 개인키 또는 푸시 발송 자격 증명을 클라이언트에 포함하지 않음
- 서버 환경변수 또는 Secret Manager 사용
- Push Subscription은 인증된 사용자만 등록·갱신·해제 가능
- 부모와 아이 데이터 접근 권한 분리
- 다른 가족의 구독 endpoint 조회 차단
- endpoint와 암호화 키 로그 마스킹
- 로그아웃 시 현재 기기 구독 유지 또는 해제 정책을 명확히 구현
- 공용 기기 또는 계정 전환 시 이전 사용자의 알림이 전달되지 않도록 처리
- 아이 계정에서 부모 리포트 알림이 노출되지 않도록 역할 검증
- 알림 본문에 과도한 개인정보나 민감한 대화 내용을 포함하지 않음

공용 기기 또는 계정 변경이 감지되면 기존 사용자와 기기의 연결을 해제하고 새 로그인 계정으로 재등록한다.
````
