# Request: 관리자 통합 분석 대시보드 — 아이별·부모별 분석 고도화

## 0. 작업 목적

현재 `내친구 케이` 관리자 페이지에는 `통합 분석 대시보드`와 별도의 아이 리텐션 상세 화면이 이미 존재한다.

현재 통합 분석 대시보드는 다음과 같은 전체 집계 데이터를 잘 보여주고 있다.

- 전체 활성 사용자
- 활성 가족
- 미션 완료율
- 리포트 생성률
- D1 / D3 / D7 리텐션
- 부모 동시 활성 가족
- 행동 퍼널 / 리포트 생성 흐름
- 기간 필터
- 테스트 계정 포함/제외
- CSV / XLSX 다운로드

그러나 현재 화면만으로는 운영자가 다음 질문에 빠르게 답하기 어렵다.

> 어떤 아이가 실제로 잘 사용하고 있는가?

> 어떤 아이가 이탈하고 있는가?

> 아이는 들어왔지만 아무 행동도 하지 않은 것은 아닌가?

> 어떤 부모가 아이의 리포트를 실제로 보고 있는가?

> 아이는 사용하는데 부모는 서비스를 사용하지 않는 가정은 어디인가?

> 부모 참여가 높은 가정과 낮은 가정의 차이는 무엇인가?

이번 작업의 목표는 기존 통합 분석 기능을 제거하거나 새 분석 시스템을 만드는 것이 아니다.

기존 통합 분석 대시보드를 유지하면서,

**아이별 분석과 부모별 분석을 추가하여 베타 가정의 실제 사용 상태를 운영자가 5분 안에 파악할 수 있도록 한다.**

---

# 1. 중요 개발 원칙

## 반드시 지킬 것

1. 기존 통합 분석 대시보드의 기능을 삭제하지 않는다.
2. 기존 KPI 계산 로직을 임의로 변경하지 않는다.
3. 이미 구현된 리텐션 계산 로직을 재작성하지 않는다.
4. `lib/admin/retentionChildMetrics.ts`의 기존 계산 함수를 최대한 재사용한다.
5. 기존 행동 이벤트의 의미를 변경하지 않는다.
6. DB Schema 변경을 기본적으로 하지 않는다.
7. 현재 필요한 원천 데이터는 이미 DB에 존재하므로 신규 테이블 설계를 하지 않는다.
8. 기존 RLS 및 관리자 권한 체계를 유지한다.
9. 관리자 API는 반드시 `requireAdmin` 등의 기존 관리자 인증 방식을 그대로 따른다.
10. 테스트 계정 포함/제외 옵션은 기존 동작과 동일하게 적용한다.
11. 시간 기준은 기존과 동일하게 KST / `Asia/Seoul`을 사용한다.
12. 실제 대화 원문은 이번 분석 화면에 노출하지 않는다.
13. 아동 개인 데이터가 CSV/XLSX로 과도하게 노출되지 않도록 기존 export 정책을 따른다.
14. 기존 URL이나 API를 불필요하게 깨지 않는다.
15. 구현 전에 현재 `통합 분석 대시보드` 소스 파일과 사용 API를 코드에서 검색하여 정확히 파악한다.

# 10. 앱 실제 체류시간

`chat_sessions.started_at ~ ended_at`을 기본 체류시간으로 사용하지 않는다.

보고서 조사 결과 브라우저 비정상 종료 시 `ended_at IS NULL` 문제가 있다.

대신:

```text
app_sessions.foreground_duration_sec
```

를 사용한다.

최소 표시:

```text
최근 7일 총 체류시간
최근 30일 총 체류시간
```

가능하면:

```text
최근 7일 평균 일일 체류시간
```

도 계산한다.

표시는 사람이 이해하기 쉬운 형태로 한다.

예:

```text
42분
1시간 12분
```

# 11. 부모 연계 지표

아이별 분석에서 부모 행동도 같이 보여준다.

다음 항목을 표시한다.

```text
일간 리포트 생성 수
부모 리포트 열람 수
부모 리포트 열람률
부모 질문 등록 수
부모 질문 전달 수
```

리포트 조회는 다음을 기준으로 한다.

```text
report_views
```

현재 다음 컬럼은 신뢰하지 않는다.

```text
daily_reports.viewed_at
```

조사 결과 해당 값은 과거 이슈로 NULL이 유지될 수 있다.

따라서 조회 여부는 반드시 `report_views`를 기준으로 계산한다.

# 12. 아이 상태 배지

운영자가 테이블 전체를 보면서 문제 사용자를 바로 찾을 수 있도록 상태 배지를 제공한다.

복잡한 AI 판단은 사용하지 않는다.

단순하고 설명 가능한 Rule 기반으로 구현한다.

최소 상태:

```text
정상 사용
초기 사용자
사용 저조
이탈 위험
부모 미열람
```

정확한 Rule은 기존 데이터와 충돌하지 않는 범위에서 구현하되 다음 기준을 권장한다.

## 초기 사용자

첫 의미 사용 이후 아직 D3가 도래하지 않은 사용자.

## 정상 사용

최근 7일 내 활동이 있으며 장기 미접속 상태가 아닌 사용자.

## 사용 저조

최근 7일 활성일수가 1일 이하인 경우.

단, 가입 직후 사용자는 제외한다.

## 이탈 위험

최근 사용 이후 일정 기간 활동이 없는 사용자.

기준은 코드에 매직넘버로 흩뿌리지 말고 상수로 관리한다.

예:

```ts
INACTIVE_RISK_DAYS
```

초기 권장값은 3일이다.

단, 기존 서비스에 동일 정의가 존재하면 그것을 우선 사용한다.

## 부모 미열람

일간 리포트가 생성되었으나 최근 일정 기간 동안 부모 열람이 0건인 경우.

# 17. 부모별 분석

## 목적

운영자가

> "부모도 이 서비스를 실제로 사용하고 있는가?"

를 확인할 수 있어야 한다.

특히 내친구 케이는 아이만 사용하는 앱이 아니므로 다음 흐름을 확인하는 것이 중요하다.

```text
아이 사용
↓
리포트 생성
↓
부모 열람
↓
부모 질문 / 실제 대화 연결
```

## 부모 활동

현재 DB에서 신뢰할 수 있는 부모 행동 데이터를 기준으로 표시한다.

최소:


부모의 정확한 `로그인 횟수`가 별도 이벤트로 안정적으로 기록되지 않는다면 추정하지 않는다.

데이터가 실제로 존재하는 경우에만 표시한다.

# 19. 부모 리포트 지표

부모별로:

```text
생성된 리포트 수
열람한 리포트 수
열람률
```

계산:

```text
열람률 = 열람된 고유 report_id / 생성된 daily_reports
```

동일 리포트를 부모가 여러 번 열어도 리포트 열람률에서는 1건으로 계산한다.

필요하면 별도로 총 조회 횟수를 표시할 수 있다.

예:

```text
리포트 12건
10건 열람
83%
```

# 21. 부모 상태 배지

단순 Rule 기반으로:

```text
활성 부모
낮은 참여
리포트 미열람
```

예:

## 활성 부모

최근 리포트를 지속적으로 열람하고 있는 사용자.

## 낮은 참여

리포트는 생성되지만 최근 일정 기간 열람 비율이 낮은 사용자.

## 리포트 미열람

# 26. API 구현 방향

기존 API를 무분별하게 확장하여 하나의 거대한 Route로 만들지 않는다.

현재 구조를 먼저 확인하고 가장 자연스러운 방식으로 구현한다.


또는 기존 통합 분석 API 내부에 명확한 mode를 추가할 수도 있다.

중요한 것은 URL명이 아니라:

- 서버에서 집계
- 관리자 인증
- 테스트 계정 처리
- KST 기준
- 페이지네이션
- 정렬
- 검색
- 필터

를 지원하는 것이다.

# 27. N+1 Query 방지

30가정 수준에서는 성능 문제가 작아 보일 수 있으나 향후 사용자를 고려한다.

아이 한 명마다 DB Query를 여러 번 호출하는 구조를 만들지 않는다.

가능한 경우:

- child_id 목록으로 batch query
- SQL aggregation
- Map 기반 server-side join

등을 사용한다.

특히 아래 데이터를 아이별 반복 요청하지 않는다.

```text
report_views
app_sessions
gold_key_ledger
parent_questions
```

# 48. 가장 중요한 제품 원칙

이번 관리자 분석 화면은 예쁜 통계 화면을 만드는 작업이 아니다.

현재 베타 운영의 목적은 다음 질문에 빠르게 답하는 것이다.

> 아이가 부모의 강요 없이 내친구 케이를 실제로 반복 사용하고 있는가?

그리고 그 다음 질문은:

> 아이의 사용 결과를 부모가 실제로 확인하고 있는가?

따라서 모든 UI와 데이터 우선순위는 이 두 질문을 중심으로 결정한다.

최종적으로 운영자가 매일 30~100가정을 빠르게 훑으면서

```text
잘 사용하는 아이
사용이 줄어드는 아이
이탈한 아이
아이만 사용하고 부모는 보지 않는 가정
아이와 부모 모두 활성인 가정
```

을 즉시 구분할 수 있어야 한다.
