# 관리자 리텐션 내부 테스트 계정 포함·제외 기능 수정

## 1. 작업 목적

관리자 페이지 `/admin/retention`의 `내부 테스트 계정 포함` 체크박스가 Production 테스트 가족을 기준으로 정확하게 동작하도록 수정한다.

체크박스 OFF 상태에서는 아래 테스트 가족 전체와 해당 가족에서 발생한 모든 활동 데이터를 모든 리텐션 지표에서 제외한다.

체크박스 ON 상태에서는 동일 테스트 가족과 활동 데이터를 모든 리텐션 지표에 다시 포함한다.

화면 일부 카드만 필터링하지 말고, 서버 API·SQL·RPC·집계 함수·상세 조회·내보내기까지 하나의 공통 기준을 사용한다.

## 3. 확정 동작

### 기본값

- `내부 테스트 계정 포함` 체크박스의 기본값은 OFF로 한다.
- 관리자 리텐션 페이지 최초 진입 시 내부 테스트 계정은 제외된 상태여야 한다.
- 새로고침 후에도 기본값은 OFF로 유지한다.
- 별도 URL 파라미터 또는 저장 상태가 명시되지 않은 경우 OFF를 사용한다.

### 체크박스 OFF

다음 항목에서 위 두 테스트 가족의 부모·아이·활동 데이터를 모두 제외한다.

- 승인 부모 수
- 기간 내 활성 부모 수
- 활성 아이 수
- 가족 동시 활성 수
- D1 리텐션
- D3 리텐션
- D7 리텐션
- D14 리텐션이 존재하는 경우 해당 지표
- 2주차 지속률 또는 W2
- 미션 시작 수
- 미션 완료 수
- 미션 완료율
- 자유대화 사용 지표
- 리포트 조회 지표
- 놀이 시작·완료 지표
- DAU
- 신규 사용자
- 재방문 사용자
- 코호트 표
- 차트
- 사용자 목록
- 부모 상세 드릴다운
- 아이 상세 드릴다운
- CSV 또는 기타 내보내기
- API 응답의 합계와 상세 목록

### 체크박스 ON

- 위 테스트 가족의 부모·아이·활동 데이터를 모두 포함한다.
- 모든 카드·차트·표·상세 목록·내보내기 결과가 동일한 조건으로 다시 계산되어야 한다.

## 4. 구현 원칙

### 4.1 클라이언트 전용 필터 금지

UI에서 이메일 문자열이나 사용자 행만 숨기는 방식으로 구현하지 않는다.

필터는 반드시 다음 서버 영역에 적용한다.

- 관리자 리텐션 API
- Server Action
- SQL
- RPC
- View
- 집계 함수
- 상세 조회
- 내보내기 API

클라이언트는 `includeInternal` 또는 프로젝트 기존 명명 규칙에 맞는 파라미터만 전달한다.

실제 포함·제외 판단은 서버에서 수행한다.

---

### 4.2 내부 계정 플래그 우선

기존 사용자·프로필·아이 테이블에 다음과 같은 내부 계정 플래그가 있는지 먼저 확인한다.

```text
is_internal_test
is_test_account
account_type
user_category
```

기존 플래그가 있으면 재사용한다.

기존 플래그가 없다면 최소 변경으로 내부 계정 식별 구조를 추가한다.

권장:

```text
is_internal_test BOOLEAN NOT NULL DEFAULT FALSE
```

부모와 아이를 각각 식별할 수 있어야 한다.

이메일 목록은 최초 계정 식별 또는 migration에서만 사용하고, 관리자 리텐션 React 컴포넌트나 브라우저 번들에 하드코딩하지 않는다.

---

### 4.3 가족 단위 처리

다음 기준을 적용한다.

- 내부 테스트 부모는 리텐션 부모 집계에서 제외한다.
- 내부 테스트 부모에 연결된 테스트 아이도 아이 집계에서 제외한다.
- 아이가 직접 내부 테스트 계정으로 지정된 경우 해당 아이의 활동을 제외한다.
- 부모 한 명에게 여러 아이가 연결되어 있어도 테스트 가족 전체가 일관되게 제외 또는 포함되어야 한다.
- 가족 동시 활성 지표에서는 부모 또는 아이 한쪽만 제외되어 잘못된 가족 수가 만들어지지 않도록 한다.

---

## 5. 공통 필터 설계

리텐션 관련 모든 쿼리에서 같은 필터를 재사용한다.

권장 구조 예시:

```text
includeInternal = false
→ parent.is_internal_test = false
→ child.is_internal_test = false
→ 테스트 부모 또는 테스트 아이에 연결된 activity/event 제외
```

또는 공통 SQL 함수·View·서버 유틸리티로 구현한다.

다음 코드가 서로 다른 기준을 사용하지 않도록 한다.

- KPI 카드 집계
- DAU
- 리텐션 코호트
- 미션 완료율
- 가족 동시 활성
- 사용자 리스트
- 상세 드릴다운
- 내보내기

한 화면에서 카드 수치와 상세 사용자 수가 서로 달라지지 않아야 한다.

---

## 6. 활동 데이터 필터

테스트 계정 자체만 제외하고 활동 이벤트는 남는 오류가 없도록 한다.

아래 데이터 소스와 실제 프로젝트의 관련 테이블을 확인한다.

- `behavior_events`
- `mission_progress`
- `chat_sessions`
- `k_play_sessions`
- `gold_key_ledger`
- 로그인 또는 방문 기록 테이블
- 리포트 조회 기록
- 부모·아이 연결 테이블
- 사용자 승인 테이블
- 기타 관리자 리텐션 집계 데이터

각 이벤트가 다음 중 어떤 식별자를 가지고 있는지 추적한다.

- `user_id`
- `parent_id`
- `child_id`
- `session_id`
- 가족 연결 ID

내부 테스트 계정과 연결된 이벤트가 집계에 남지 않도록 한다.

## 7. UI 동작

### 체크박스

- 라벨: `내부 테스트 계정 포함`
- 기본값: OFF
- OFF에서 ON으로 변경하면 전체 데이터를 다시 조회한다.
- ON에서 OFF로 변경하면 전체 데이터를 다시 조회한다.
- 단순 화면 숫자만 변경하지 않고 서버 API를 재호출한다.
- 로딩 중 중복 클릭을 방지한다.
- 실패 시 기존 수치를 조용히 유지하지 말고 오류 상태를 표시한다.

### 상태 전달

다음 중 프로젝트 기존 패턴에 맞는 방식을 사용한다.

```text
?includeInternal=true
?includeInternal=false
```

또는 API request parameter.

Boolean 문자열 처리 오류가 없도록 한다.

예:

```text
"false"를 truthy로 오인하지 않음
```

## 9. 내부 계정 등록

위 두 테스트 가족의 실제 Production 레코드를 안전하게 찾아 내부 테스트 플래그를 설정한다.

### 부모

```text
qa-parent@kbestie.local
markanitp@gmail.com
```

### 아이

```text
testa@kbestie.local
testb@kbestie.local
psa160202@kbestie.local
psh160202@kbestie.local
psd160202@kbestie.local
```

주의:

- 동일 이름이 아니라 로그인 아이디 또는 불변 ID로 식별한다.
- 계정이 존재하지 않거나 중복이면 임의로 생성·선택하지 말고 BLOCKED로 보고한다.
- 이메일 대소문자와 앞뒤 공백을 정규화한다.
- 부모와 아이의 실제 연결 관계를 확인한다.
- 일반 사용자에게 내부 테스트 플래그를 잘못 설정하지 않는다.

Production DB 변경이 필요하면 먼저 Dev 또는 안전한 검증 환경에서 migration과 쿼리를 검증하고, 대표 승인 전 Production 적용은 하지 않는다.

## 10. 보안

- Service Role Key를 클라이언트에 노출하지 않는다.
- Production API Key, 비밀번호, 토큰을 평문 출력하지 않는다.
- 비밀정보를 로그 또는 임시파일에 저장하지 않는다.
- 기존 환경변수, Vercel Secrets, Supabase Secrets를 런타임에서만 사용한다.
- 관리자 권한은 서버에서 검증한다.
- 일반 사용자가 `includeInternal=true` API를 직접 호출해 관리자 데이터를 조회할 수 없어야 한다.
- 보고서에는 사용자 ID와 이메일을 필요한 수준으로 마스킹한다.

## 12. 테스트 시나리오

### 12.1 기본 상태

1. Dev 관리자 리텐션 페이지 진입
2. 체크박스가 OFF인지 확인
3. 테스트 가족이 모든 카드와 목록에서 제외되는지 확인
4. 새로고침 후에도 OFF인지 확인

### 12.2 OFF 검증

OFF 상태에서 다음 두 가족이 포함되지 않아야 한다.

- QA 부모-TestA-TestB 가족
- Mark An 테스트 가족

확인 대상:

- 승인 부모
- 활성 부모
- 활성 아이
- 가족 동시 활성
- D1
- D3
- D7
- W2
- 미션 완료율
- DAU
- 코호트
- 상세 사용자 목록
- CSV

화면 수치, API 응답, DB 재계산값을 대조한다.

### 12.3 ON 검증

1. 체크박스를 ON으로 변경
2. API 재호출 확인
3. 위 두 테스트 가족이 모든 집계에 포함되는지 확인
4. 카드와 상세 목록의 증가분이 실제 테스트 가족 데이터와 일치하는지 확인
5. CSV에도 포함되는지 확인

### 12.4 재토글

1. ON 상태에서 OFF로 변경
2. 테스트 가족이 다시 제외되는지 확인
3. 카드·차트·표·드릴다운·CSV가 모두 같은 조건으로 갱신되는지 확인

### 12.5 기간별 검증

각각 OFF와 ON을 검증한다.

- 최근 7일
- 최근 14일
- 최근 30일
- 이번 달
- 전체

### 12.6 가족 관계 검증

- 부모만 제외되고 아이가 남는 오류가 없는지 확인
- 아이만 제외되고 가족 동시 활성 수가 남는 오류가 없는지 확인
- 한 부모의 여러 아이가 모두 정확히 처리되는지 확인

### 12.7 일반 사용자 회귀

- 일반 부모 수치가 변경되지 않는지 확인
- 일반 아이 활동이 누락되지 않는지 확인
- 일반 가족의 D1/D3/D7/W2가 동일한지 확인

### 12.8 권한

- 일반 부모 계정의 관리자 API 접근 차단
- 아이 계정의 관리자 API 접근 차단
- 관리자만 체크박스 포함 조회 가능

## 15. 작업 금지 사항

- 체크박스 UI만 변경하고 서버 집계를 그대로 두지 않는다.
- 특정 카드에만 필터를 적용하지 않는다.
- 이메일을 브라우저 코드에 하드코딩하지 않는다.
- 부모만 제외하고 연결된 테스트 아이를 남기지 않는다.
- 아이 이벤트만 제외하고 가족 동시 활성 수를 남기지 않는다.
- `"false"` 문자열을 true로 처리하지 않는다.
- 테스트 가족이 아닌 일반 사용자를 제외하지 않는다.
- Production에 임의 배포하지 않는다.
- Production DB를 검증 없이 수정하지 않는다.
- 비밀정보를 출력하거나 저장하지 않는다.
