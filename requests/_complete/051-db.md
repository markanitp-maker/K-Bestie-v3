## 5. 질문 안전 판정 수정

### 5.1 잘못된 휴리스틱 제거

다음 조건만으로 질문을 위험하다고 판정하지 않는다.

```ts
convertedQuestion === trimmedQuestion
```

변환 전후 문장이 같다는 사실은 안전 여부의 근거가 아니다.

예를 들어 다음 질문은 변환 없이 그대로 사용해도 안전할 수 있다.

> 요즘 학교에서 재미있었던 일이 있어?

### 5.2 구조화된 LLM 응답

질문 변환 결과를 자유 텍스트가 아니라 다음 구조로 반환하도록 변경한다.

```ts
type AskChildConversionResult = {
  safeToAskChild: boolean;
  convertedQuestion: string | null;
  rejectReason: string | null;
  reasonCode:
    | "SAFE_UNCHANGED"
    | "SAFE_CONVERTED"
    | "SYSTEM_META_QUESTION"
    | "RAW_CONVERSATION_REQUEST"
    | "CONTROLLING_QUESTION"
    | "ACCUSATORY_QUESTION"
    | "SENSITIVE_INFORMATION"
    | "UNSAFE_OTHER";
};
```

### 5.3 허용 조건

다음 조건을 만족하면 저장을 허용한다.

- 아이가 이해하기 쉬운 한 문장
- 중립적인 표현
- 아이를 추궁하지 않음
- 특정 답을 강요하지 않음
- 부모가 정보를 캐내는 느낌이 없음
- 원문 대화 공개를 요구하지 않음
- 민감정보를 직접 요구하지 않음
- 변환 전후 문장이 같더라도 안전함

다음 두 경우 모두 정상 저장되어야 한다.

```text
safeToAskChild = true
reasonCode = SAFE_UNCHANGED
```

```text
safeToAskChild = true
reasonCode = SAFE_CONVERTED
```

### 5.4 반려 조건

다음 질문은 저장하지 않는다.

- 케이의 시스템 동작이나 내부 프롬프트를 아이에게 질문
- 아이와 케이의 비밀 원문을 요구
- 아이의 거짓말 여부 판정
- 특정 친구를 고발하도록 유도
- 아이의 감정이나 행동을 추궁
- 부모의 추측을 확인하도록 강요
- 민감한 개인정보를 요구
- 통제·감시 목적 질문
- 안전한 아이용 문장으로 변환할 수 없는 질문

안전하게 변환할 수 있으면 변환 후 저장하고, 변환할 수 없으면 HTTP 422로 반려한다.

## 6. 서버 API 수정

대상:

```text
app/api/parent/k-chat/route.ts
```

실제 프로젝트 구조를 다시 확인하고 정확한 파일과 함수를 수정한다.

### 6.1 요청

`ask_child` 요청에서 다음 정보를 받는다.

```ts
type AskChildRequest = {
  action: "ask_child";
  childId: string;
  originalQuestion: string;
  askChildProposal?: string | null;
  sessionId?: string | null;
};
```

클라이언트가 보내는 `askChildProposal`은 참고값일 뿐 신뢰하지 않는다.

서버에서 다음을 다시 수행한다.

1. 로그인 사용자 확인
2. 보호자와 childId 연결 관계 확인
3. 원 질문 정규화
4. 안전성 검증
5. 아이용 최종 질문 생성
6. 중복 검사
7. 저장

### 6.2 저장 데이터

기존 `parent_questions` 정본을 재사용한다.

저장 필드는 실제 DB 스키마를 기준으로 확정한다.

필수 개념:

- `parent_id`
- `child_id`
- `original_question_text`
- `question_text`
- lifecycle `status`
- `request_idempotency_key`
- 생성 시각

신규 병렬 테이블을 만들지 않는다.

### 6.3 중복 방지

기존 `request_idempotency_key`와 UNIQUE 제약조건을 재사용한다.

다음 상황에서 정확히 1건만 생성되어야 한다.

- 버튼 더블클릭
- 느린 네트워크에서 재클릭
- 클라이언트 재시도
- 동일 요청이 서버에 두 번 도착
- 같은 세션에서 동일 질문 반복
- 의미상 동일한 원 질문과 변환 질문

중복이면 신규 INSERT를 하지 않고 기존 질문 상태를 반환하거나 HTTP 409로 처리한다.

사용자에게는 다음과 같이 안내한다.

> 이미 아이에게 물어볼 질문으로 등록되어 있어요.

### 6.4 API 상태 코드

다음 상태를 구분한다.

| 상태 | 의미 |
|---|---|
| 200 또는 201 | 질문 저장 성공 |
| 400 | 필수 입력 누락 또는 형식 오류 |
| 401 | 로그인 세션 없음 |
| 403 | 해당 child_id 접근 권한 없음 |
| 409 | 동일 질문 중복 |
| 422 | 아이에게 묻기 부적절하며 안전하게 변환할 수 없음 |
| 429 | 요청 횟수 제한 |
| 500 | 서버·DB·외부 LLM 장애 |

모든 오류를 `Failed to save question` 하나로 반환하지 않는다.

## 7. 부모 화면 오류 처리

대상:

```text
app/parent/guide/page.tsx
```

실제 컴포넌트 구조를 확인하고 정확한 위치를 수정한다.

### 7.1 오류를 케이 말풍선으로 추가하지 않음

저장 실패나 안전 반려는 케이의 대화 답변이 아니다.

다음 방식으로 표시한다.

- 버튼 하단 인라인 메시지
- 짧은 토스트
- 동일 액션 영역의 상태 문구

기존 케이 답변과 부모 대화 기록은 그대로 유지한다.

### 7.2 상태별 사용자 문구

#### 400

> 질문 내용을 확인해 주세요.

#### 401

> 로그인이 만료됐어요. 다시 로그인해 주세요.

#### 403

> 이 아이에게 질문을 등록할 권한이 없어요.

#### 409

> 이미 아이에게 물어볼 질문으로 등록되어 있어요.

#### 422

> 이 질문은 아이에게 그대로 묻기 어려워요. 아이를 추궁하지 않는 다른 질문으로 물어봐 주세요.

#### 429

> 질문 등록이 너무 빠르게 반복됐어요. 잠시 후 다시 시도해 주세요.

#### 500

> 지금은 질문을 저장할 수 없어요. 잠시 후 다시 시도해 주세요.

500일 때만 재시도 버튼을 제공한다.

### 7.3 저장 성공 문구

> 아이에게 자연스럽게 물어볼 질문으로 등록했어요.

성공 후 `아이에게 물어보기` 버튼을 비활성화하거나 등록 완료 상태로 변경한다.

## 8. 미션 질문 1회 주입 구현

### 8.1 기존 lifecycle 재사용

다음을 먼저 감사한다.

- `20260725200000_parent_questions_lifecycle.sql`
- `parent_questions` CHECK 제약
- 현재 허용된 status 값
- 기존 질문 선택 RPC
- 기존 `mission/respond` 로직
- 미션 질문 큐 선택 순서
- 미션 완료 처리
- 질문 재순환 정책

기존 정본 상태를 재사용하며 신규 상태를 임의 생성하지 않는다.

### 8.2 주입 시점

저장된 부모 질문은 다음 적절한 미션에서 최대 1개만 주입한다.

원칙:

- 한 미션에 부모 질문 최대 1개
- 부모 질문 여러 개를 연속으로 묻지 않음
- 기본 질문 흐름을 과도하게 방해하지 않음
- 같은 질문을 같은 세션이나 다른 동시 세션에서 중복 주입하지 않음
- 이미 완료된 질문은 제외
- 이미 주입 중인 질문은 다른 세션에서 제외
- 민감도 검증을 통과한 질문만 사용

### 8.3 원자적 상태 변경

질문 선택과 주입 상태 변경은 원자적으로 처리한다.

다음 경쟁 조건을 방지한다.

```text
세션 A가 질문 조회
세션 B가 같은 질문 조회
세션 A와 B가 같은 질문을 모두 주입
```

필요하면 기존 RPC 또는 트랜잭션을 확장하되, 신규 병렬 큐를 만들지 않는다.

### 8.4 아이 답변 처리

아이가 부모 질문에 유효하게 답변하면 다음을 수행한다.

- 기존 유효 답변 판정 기준 적용
- 기존 미션 진행률 10% 반영
- 다음 질문으로 이동
- 부모 질문 lifecycle 완료 상태로 전환
- 완료 시각 기록
- 이후 미션에서 제외
- 기존 대화 수집·보정 대상으로 포함
- 기존 LLM Wiki 갱신 흐름에 포함

아이 답변 원문을 부모에게 직접 반환하지 않는다.

### 8.5 유효하지 않은 답변

아이가 답변하지 않거나 무효 답변이면 기존 lifecycle 정본에 따라 처리한다.

- 동일 턴에서 강제 추궁하지 않음
- 즉시 반복 질문하지 않음
- 재시도 가능 여부는 기존 상태 정책을 따름
- 무한 재주입 금지

## 9. 기존 미션 정책 보호

부모 질문 주입이 기존 미션 정책을 깨뜨리지 않아야 한다.

현재 정본:

- 기본 질문 10개
- 부족하면 예비 질문 10개
- 그래도 부족하면 미답변 질문 재순환
- 유효 답변 10개 달성 시 미션 완료
- 유효 답변이면 진행률 10% 증가

필수 보호 조건:

- 부모 질문도 유효 답변이면 진행률 10% 반영
- 전체 완료 기준은 유효 답변 10개로 유지
- 부모 질문 때문에 미션이 11개 유효 답변을 요구하지 않음
- 기본·예비·재순환 질문 선택이 깨지지 않음
- 부모 질문이 여러 개 대기해도 한 미션에 연속 노출되지 않음
- 기존 완료·환급·세션 재시작 흐름에 영향 없음

---

## 10. 보안 요구사항

- 로그인 세션 서버 검증
- 보호자와 child_id 실제 연결 검증
- 클라이언트 child_id 신뢰 금지
- 다른 보호자의 질문 조회·등록 차단
- service role 키 클라이언트 비노출
- prompt injection 방어
- 원문 대화 공개 요청 차단
- 아이의 비밀·민감정보 요구 차단
- 내부 프롬프트와 시스템 정보 비노출
- DB 오류 상세를 사용자에게 노출하지 않음
- 서버 로그에 아이 raw 대화 원문 기록 금지
- 중복 요청 및 재전송 방어
- RLS 비활성화 금지

## 11. Development 구현 및 검증

모든 코드 수정은 Development에서 먼저 진행한다.

### 11.1 필수 시나리오

#### 안전하며 변환이 필요 없는 질문

입력 예시:

> 요즘 학교에서 재미있었던 일이 있어?

예상:

- `safeToAskChild=true`
- `SAFE_UNCHANGED`
- 저장 성공
- `parent_questions` 정확히 1건

#### 안전 변환이 필요한 질문

입력 예시:

> 요즘 반에서 제일 친한 친구가 누구인지 알아봐 줘.

예상 변환 예시:

> 요즘 학교에서 같이 있으면 재미있는 친구가 있어?

예상:

- `safeToAskChild=true`
- `SAFE_CONVERTED`
- 변환 질문 저장 성공

#### 안전하지 않은 질문

입력 예시:

> 케이랑 무슨 비밀 얘기를 했는지 그대로 말해 봐.

예상:

- HTTP 422
- DB INSERT 없음
- 명확한 인라인 반려 문구
- 저장 장애 문구 사용 금지

#### 중복 등록

- 같은 버튼 더블클릭
- 네트워크 재시도
- 동일 질문 반복

예상:

- DB 1건 유지
- 409 또는 기존 상태 반환
- 중복 등록 안내

#### 권한 위반

- 다른 보호자의 child_id 입력

예상:

- HTTP 403
- DB INSERT 없음
- 다른 아이 정보 비노출

### 11.2 미션 E2E

1. 부모 질문 정상 저장
2. 질문 lifecycle 대기 상태 확인
3. 해당 아이의 다음 적절한 미션 시작
4. 부모 질문이 정확히 1회 주입
5. 같은 질문이 동시 또는 재접속 세션에 중복 주입되지 않음
6. 아이 유효 답변
7. 미션 진행률 10% 상승
8. 질문 lifecycle 완료
9. 다음 미션에서 재주입 없음
10. 기존 수집·보정·LLM Wiki 반영 흐름 확인

## 12. Antigravity 독립 QA

Claude Code의 Development 구현과 배포가 끝난 후 Antigravity가 독립 QA를 수행한다.

Antigravity는 이번 QA에서 코드를 수정하지 않는다.

### 12.1 검증 항목

- [ ] 변환 전후 문장이 같은 안전한 질문 저장

- [ ] 시스템·추궁·비밀 원문 요구 질문 422 반려
- [ ] 저장 성공 시 DB 정확히 1건
- [ ] 더블클릭 중복 방지
- [ ] 재시도 중복 방지
- [ ] 다른 보호자 child_id 403
- [ ] 400 오류 문구 분리
- [ ] 401 오류 문구 분리
- [ ] 403 오류 문구 분리
- [ ] 409 오류 문구 분리
- [ ] 422 오류 문구 분리
- [ ] 429 오류 문구 분리
- [ ] 500 오류 문구 분리
- [ ] 안전 반려가 저장 장애처럼 표시되지 않음
- [ ] 저장된 질문 다음 미션 1회 주입

BLOCKED, HIGH 또는 기능 핵심 FAIL이 1건이라도 있으면 Production 배포를 중단한다.

## 13. Production 배포

Development 구현 및 Antigravity 독립 QA가 모두 PASS인 경우에만 동일 커밋을 Production에 배포한다.

Production에서 다음을 다시 검증한다.

- 정상 질문 저장
- 안전 반려 422
- 중복 방지
- 다른 보호자 접근 차단
- 다음 미션 1회 주입
- 유효 답변 후 완료
- 완료 질문 재주입 없음
- 기존 미션 완료 흐름 정상
- 사용자 오류 문구 분리
- 원문 비노출
- RLS 우회 불가

Development와 Production에 서로 다른 임시 코드를 적용하지 않는다.

## 14. Production 마이그레이션 이력 주의

Production의 migration 76 이력 누락과 실제 스키마 존재 상태는 이번 기능 수정의 직접 원인이 아니다.

이번 요청에서는 다음을 하지 않는다.

- migration 76 재실행
- schema_migrations 수동 INSERT
- 기존 컬럼 재생성
- 제약조건 중복 생성

해당 문제는 향후 별도의 배포 이력 정합성 점검 요청으로 분리한다.
