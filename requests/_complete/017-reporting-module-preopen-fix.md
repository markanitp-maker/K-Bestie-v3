# REQUEST 017 — 리포팅 모듈 오픈 전 수정·배포·검증

## 1. 작업 목적

내친구 케이 개발 서버에서 아이의 미션 대화와 자유 대화를 수집해 일일 리포트를 생성하고, 부모 대시보드의 아이 상태 8개 항목까지 정상 갱신되도록 수정한다.

현재 진단 결과 다음 문제가 확인되었다.

1. 자유대화 세션이 일일 리포트 생성 대상에서 제외되고 있다.
2. 최신 리포팅 Edge Function 코드가 개발 서버에 배포되지 않았다.
3. 부모 대시보드 신규 8개 항목이 최신 리포트에서 모두 `null`로 저장되고 있다.
4. 현재 스케줄이 확정 운영 시간과 다르다.
5. 코드 존재 여부가 아니라 실제 개발 서버의 DB·API·부모 화면까지 연결된 E2E 검증이 필요하다.

이번 요청은 문서 검토가 아니라 코드 수정, 개발 서버 배포, 스케줄 적용, 실제 E2E 검증까지 완료하는 작업이다.

---

## 2. 확정 운영 스케줄

모든 시간 기준은 `Asia/Seoul`이다.

| 작업        |     한국시간 |      UTC |
| --------- | -------: | -------: |
| 1차 대화 수집  | 매일 18:00 |    09:00 |
| 2차 대화 수집  | 매일 00:00 | 전날 15:00 |
| 일일 리포트 생성 | 매일 03:00 | 전날 18:00 |

### 날짜 처리 기준

* 00:00 수집은 방금 종료된 직전 날짜의 `business_date`를 대상으로 한다.
* 대표님이 요청한 `23:59:59` 마감 수집은 운영상 `00:00` 실행으로 구현한다.
* 03:00 리포트는 직전 날짜의 미션 대화와 자유대화를 합산해 생성한다.
* 기존 02:00 수집과 04:00 리포트 작업은 새 스케줄 적용 후 중복 실행되지 않아야 한다.

---

## 3. 현재 확인된 문제

### 3.1 자유대화 리포트 누락

리포트 생성 코드에서 다음과 유사한 조건으로 세션을 제외하고 있다.

```ts
if (progress?.status !== "COMPLETED")
```

자유대화에는 `mission_progress`가 존재하지 않으므로 자유대화 세션이 무조건 제외된다.

미완료 미션 역시 실제 아이 발화가 존재하더라도 전체 세션이 제외될 가능성이 있다.

### 3.2 최신 Edge Function 미배포

로컬 코드와 DB 마이그레이션에는 부모 대시보드 아이 상태 8개 항목이 추가되어 있으나, Supabase Edge Function 클라우드 환경에는 최신 `_shared/batch.ts` 관련 코드가 배포되지 않았다.

그 결과 최신 자동·수동 리포트에서 신규 8개 필드가 모두 `null`로 저장되고 있다.

### 3.3 부모 대시보드 8개 상태 미갱신

현재 최신 리포트 기준 정상 갱신 항목은 `0/8`이다.

확인해야 하는 전체 흐름은 다음과 같다.

```text
미션·자유 대화
→ 수집 및 집계
→ LLM 리포트 생성
→ daily_reports 저장
→ 부모 리포트 API
→ 부모 대시보드 아이 상태 8개 표시
```

### 3.4 스케줄 미반영

현재 개발 DB에 실제 등록된 스케줄은 다음과 같이 진단되었다.

* 수집: 18:00 / 02:00 KST
* 리포트: 04:00 KST

확정 스케줄인 18:00 / 00:00 / 03:00 KST로 변경해야 한다.

## 4. 구현 요구사항

### 4.1 대화 수집 대상

다음 대화를 모두 일일 리포트 분석 입력으로 포함한다.

* 완료된 미션 대화
* 진행 중 또는 중단된 미션 중 실제 아이 발화가 존재하는 대화
* 자유대화
* 이어하기로 재개된 세션의 실제 발화

다음 데이터는 분석 입력에서 제외한다.

* 빈 발화
* 시스템 메시지
* 에러 메시지
* 상태 안내 메시지
* 테스트용 더미 문구
* 케이의 발화만 존재하고 아이 발화가 없는 세션

미션 완료 여부만으로 세션 전체를 제외하지 않는다.

---

### 4.2 자유대화와 미션 대화 통합

같은 `child_id`와 `business_date`에 존재하는 모든 유효 대화를 통합하여 하나의 일일 리포트를 생성한다.

세션별로 별도 리포트를 생성하지 않는다.

```text
child_id + business_date = 일일 리포트 1개
```

다음 기준으로 중복을 방지한다.

* `session_id`
* `message_id`
* 원본 이벤트 ID 또는 이에 준하는 고유 키

배치를 여러 번 실행해도 동일 대화가 중복 반영되거나 리포트가 중복 생성되지 않아야 한다.

---

### 4.3 부모 대시보드 아이 상태 8개 항목

부모 대시보드 코드, API 타입, DB 마이그레이션을 기준으로 실제 8개 항목명을 확정한다.

각 항목에 대해 다음 연결을 검증하고 수정한다.

| 구간   | 확인 내용                                |
| ---- | ------------------------------------ |
| 프롬프트 | LLM 출력 스키마에 항목이 정의되어 있는가             |
| 파싱   | LLM 응답을 안전하게 파싱하는가                   |
| 저장   | `daily_reports` 컬럼 또는 JSON 필드에 저장하는가 |
| API  | 부모 리포트 API가 동일 필드를 반환하는가             |
| UI   | 부모 대시보드가 반환값을 표시하는가                  |
| 다자녀  | 현재 선택된 `child_id` 값만 표시하는가           |

프롬프트 필드명, TypeScript 타입, 배치 파싱 키, DB 컬럼, API 응답 필드명이 완전히 일치해야 한다.

---

### 4.4 데이터 부족 처리

특정 항목을 판단할 대화가 부족한 경우 다음 원칙을 적용한다.

* 전날 값을 최신 값인 것처럼 재사용하지 않는다.
* 임의의 감정이나 상태를 생성하지 않는다.
* 의미 없는 더미 문자열을 저장하지 않는다.
* 부모 화면이 깨지지 않는 명확한 데이터 부족 상태를 사용한다.
* `null`, `undefined`, 빈 문자열로 인해 화면 오류가 발생하지 않게 한다.

기존 UI 계약에 명확한 데이터 부족 표현이 있다면 이를 사용하고, 없다면 최소한의 안전한 표시값을 적용한다.

예:

```text
오늘은 확인할 대화가 충분하지 않아요.
```

이 문구는 실제 분석값처럼 취급하지 않고 데이터 부족 상태로 구분한다.

---

### 4.5 리포트 저장 방식

동일한 `child_id`와 `business_date`에는 최종 일일 리포트가 하나만 존재해야 한다.

다음 중 현재 스키마와 가장 안전한 방식을 사용한다.

* DB unique constraint
* `upsert`
* 기존 레코드 업데이트

리포트 생성 도중 실패한 경우 8개 항목이 모두 빈 상태인 레코드를 정상 완료 리포트로 확정 저장하지 않는다.

가능하면 다음 상태를 구분한다.

* `processing`
* `completed`
* `failed`

기존 스키마에 상태 필드가 없다면 불필요한 대규모 변경은 하지 말고 현재 구조 내에서 실패 레코드 저장을 방지한다.

---

### 4.6 부모 대시보드 조회

부모 대시보드는 현재 선택된 아이의 최신 정상 리포트를 조회해야 한다.

확인 항목:

* 다른 자녀의 `child_id` 리포트가 섞이지 않는가
* 최신 리포트보다 이전 리포트를 가져오지 않는가
* 빈 최신 레코드 때문에 이전 정상 리포트가 잘못 가려지지 않는가
* React Query, SWR, Next.js 캐시로 전날 값이 유지되지 않는가
* 새로고침 이후에도 최신 값이 유지되는가
* 8개 중 일부 값이 없어도 화면 전체가 깨지지 않는가

## 5. Edge Function 배포

리포팅과 수집에 관련된 최신 코드가 실제 개발 Supabase Edge Function에 포함되도록 배포한다.

주요 확인 대상:

* `_shared/batch.ts`
* `generateDailyReports.ts`
* `prompts.ts`
* `reportSafetyGuard.ts`
* 관련 타입 및 공통 유틸리티
* 리포트 생성 Edge Function 진입점
* 대화 수집 Edge Function 진입점

배포 전 확인:

* import 경로
* TypeScript 오류
* Deno 런타임 호환성
* 환경변수 이름
* LLM 출력 파싱
* DB insert/upsert 필드
* 신규 8개 DB 컬럼 존재 여부

배포 범위는 개발 서버만이다.

Production Supabase 및 Production Vercel 프로젝트는 변경하지 않는다.

## 6. pg_cron 적용

확정된 한국시간 기준으로 개발 DB에 실제 스케줄을 적용한다.

### 필수 조건

* 기존 동일 작업을 안전하게 `unschedule`
* 새 작업은 각각 한 번만 등록
* 기존 02:00 수집 제거
* 기존 04:00 리포트 제거
* 동일 목적의 중복 작업 제거
* 각 작업 `active = true` 확인

마이그레이션 파일 작성으로 끝내지 않고 개발 Supabase DB에 실제 적용한다.

적용 후 `cron.job` 조회 결과로 다음을 확인한다.

| 작업     |   UTC |   KST | 활성 상태 |
| ------ | ----: | ----: | ----- |
| 1차 수집  | 09:00 | 18:00 | true  |
| 2차 수집  | 15:00 | 00:00 | true  |
| 일일 리포트 | 18:00 | 03:00 | true  |

## 7. 개발 서버 E2E 검증

자동 스케줄 시각까지 기다리지 말고 개발 환경에서 관리자 방식으로 동일 배치를 1회 수동 실행해 검증한다.

### 테스트 입력 조건

실제 테스트 아이 계정 하나에 다음 데이터가 모두 존재해야 한다.

* 유효한 미션 아이 발화 1개 이상
* 유효한 자유대화 아이 발화 1개 이상

실제 대화 원문과 개인정보는 보고서에 노출하지 않는다.

### 검증 순서

1. 미션 대화 DB 저장 확인
2. 자유대화 DB 저장 확인
3. 대화 수집 배치 실행
4. 수집 데이터에 두 대화 유형 모두 포함됐는지 확인
5. 리포트 생성 배치 실행
6. `daily_reports` 저장 확인
7. 부모 상태 8개 필드 확인
8. 부모 리포트 API 응답 확인
9. 부모 대시보드 표시 확인
10. 브라우저 새로고침 후 유지 확인
11. 다른 자녀 화면에 값이 섞이지 않는지 확인
12. 동일 배치 재실행 후 중복 여부 확인

* `mission_progress`가 없어도 리포트 생성

### 시나리오 C — 미완료 미션에 아이 발화 존재

* 완료되지 않았다는 이유만으로 전체 제외하지 않음

* 렌더링 오류 없음

### 시나리오 E — 동일 배치 재실행

예상 결과:

* 대화 중복 집계 없음
* 동일 날짜 리포트 중복 없음
* 기존 레코드 안전하게 갱신

### 시나리오 F — 다자녀 계정

예상 결과:

* 선택한 아이의 리포트만 표시
* 형제·자매의 상태와 리포트가 섞이지 않음

## 9. 오픈 승인 기준

다음 조건을 모두 충족해야 `GO`로 판정한다.

* [ ] 미션 대화가 일일 리포트에 포함된다.
* [ ] 자유대화가 일일 리포트에 포함된다.
* [ ] 미완료 미션의 실제 아이 발화도 포함된다.
* [ ] 부모 대시보드 아이 상태 8개가 DB에 정상 저장된다.
* [ ] API에서 8개 항목이 정상 반환된다.
* [ ] 부모 대시보드에서 8개 항목이 정상 표시된다.
* [ ] 최신 E2E 검증 결과가 `8/8`이다.
* [ ] 최신 Edge Function이 개발 서버에 배포됐다.
* [ ] 스케줄이 18:00 / 00:00 / 03:00 KST로 실제 등록됐다.
* [ ] 기존 02:00 / 04:00 중복 작업이 제거됐다.
* [ ] 동일 아이·날짜 리포트가 중복 생성되지 않는다.
* [ ] 부모 대시보드 렌더링 오류가 없다.
* [ ] 다자녀 계정에서 아이 데이터가 섞이지 않는다.
* [ ] 배치 재실행 시 멱등성이 유지된다.
* [ ] BLOCKER, HIGH 문제가 0건이다.

하나라도 충족하지 못하면 `CONDITIONAL GO` 또는 `NO-GO`로 판정하고 미충족 항목을 정확히 보고한다.

## 10. 작업 범위 제외

이번 요청에서 다음 항목은 제외한다.

## 12. 실행 원칙

* 기존 구현을 먼저 분석하고 필요한 부분만 최소 수정한다.
* 추측으로 완료 처리하지 않는다.
* 코드 수정 후 반드시 개발 서버 배포와 E2E 검증까지 수행한다.
* 마이그레이션 파일만 작성하고 실제 DB에 적용하지 않은 상태는 미완료다.
* 로컬 코드만 수정하고 Edge Function을 배포하지 않은 상태는 미완료다.
* DB 값만 확인하고 부모 대시보드 화면을 확인하지 않은 상태는 미완료다.
* `8/8` 결과는 DB·API·화면의 값이 모두 일치할 때만 인정한다.
* Production 환경은 절대 변경하지 않는다.


## 13. 관리자 화면 수동 리포팅 실행 기능

### 13.1 목적

자동 수집 또는 자동 리포트 배치를 기다리지 않고, 관리자가 개발 서버 관리자 화면에서 특정 날짜와 아이를 대상으로 다음 작업을 즉시 실행할 수 있어야 한다.

1. 즉시 대화 수집
2. 즉시 일일 리포트 생성
3. 부모 대시보드 아이 상태 8개 항목 갱신

리포트 생성과 부모 대시보드 갱신은 별도의 수동 작업으로 분리하지 않는다.

```text
즉시 대화 수집
→ 즉시 리포트 생성
→ daily_reports 저장
→ 부모 API 최신 데이터 반환
→ 부모 대시보드 8개 상태 및 일일 리포트 반영
```

---

### 13.2 관리자 화면 구성

기존 관리자 페이지에 `리포팅 수동 실행` 영역을 추가한다.

#### 입력 항목

| 항목    | 요구사항                        |
| ----- | --------------------------- |
| 실행 환경 | 개발 서버로 고정 표시                |
| 대상 날짜 | `business_date` 선택, 기본값은 오늘 |
| 대상 아이 | 특정 아이 선택 또는 전체 아이 선택        |
| 아이 검색 | 아이 이름 또는 마스킹된 ID로 검색        |
| 현재 상태 | 최근 수집 및 리포트 생성 상태 표시        |

Production에서는 이 기능을 노출하거나 실행하지 않는다.

관리자 권한이 없는 사용자는 화면과 API 모두 접근할 수 없어야 한다.

---

### 13.3 버튼 1 — 즉시 대화 수집

버튼명:

```text
즉시 대화 수집
```

선택한 아이와 `business_date`를 기준으로 현재까지 저장된 유효한 대화를 즉시 수집한다.

#### 수집 대상

* 완료된 미션 대화
* 진행 중 또는 중단된 미션의 유효한 아이 발화
* 자유대화
* 이어하기 세션의 유효한 아이 발화

#### 제외 대상

* 빈 발화
* 시스템 메시지
* 오류 메시지
* 상태 안내 문구
* 테스트용 더미 메시지
* 아이 발화가 전혀 없는 세션

#### 실행 원칙

* 기존 자동 수집 배치와 동일한 핵심 로직을 재사용한다.
* 관리자 전용 별도 수집 로직을 중복 구현하지 않는다.
* 동일 작업을 반복 실행해도 같은 메시지가 중복 수집되지 않아야 한다.
* 특정 아이 실행 시 다른 아이 데이터는 처리하지 않는다.
* 전체 아이 실행 시 대상 날짜에 유효 대화가 존재하는 아이만 처리한다.
* 오늘 날짜를 선택하면 버튼을 누른 시점까지 저장된 대화만 수집한다.

#### 완료 결과 표시

```text
수집 완료
- 대상 날짜:
- 대상 아이:
- 미션 세션:
- 자유대화 세션:
- 유효 아이 발화:
- 신규 수집:
- 중복 제외:
- 실패:
- 실행 시간:
```

수집된 실제 대화 원문은 관리자 결과창에 표시하지 않는다.

---

### 13.4 버튼 2 — 즉시 리포트 생성

버튼명:

```text
즉시 리포트 생성
```

선택한 아이와 `business_date`를 기준으로 수집된 미션·자유대화 데이터를 이용해 일일 리포트를 즉시 생성한다.

#### 실행 전 확인

* 해당 날짜의 수집 데이터 존재 여부
* 미션 대화 포함 여부
* 자유대화 포함 여부
* 기존 일일 리포트 존재 여부
* 현재 실행 중인 동일 작업 존재 여부

수집 데이터가 없으면 빈 리포트를 만들지 않고 다음과 같이 안내한다.

```text
해당 날짜에 수집된 유효 대화가 없습니다.
먼저 ‘즉시 대화 수집’을 실행해 주세요.
```

#### 생성 원칙

* 미션과 자유대화를 통합해 아이별·날짜별 리포트 하나를 생성한다.
* 동일 `child_id + business_date` 리포트가 존재하면 중복 생성하지 않고 안전하게 갱신한다.
* 신규 부모 대시보드 8개 항목을 모두 생성하고 저장한다.
* 기존 일일 리포트 항목도 함께 저장한다.
* 일부 항목 생성 실패 시 전체가 성공한 것으로 표시하지 않는다.
* LLM 파싱 또는 DB 저장 실패 시 실패 상태와 원인을 관리자 화면에 표시한다.
* 이전 날짜 값을 최신 분석값처럼 재사용하지 않는다.

---

### 13.5 부모 대시보드 자동 갱신

`즉시 리포트 생성`이 성공하면 다음 데이터가 동시에 갱신되어야 한다.

* 부모용 일일 리포트
* 부모 대시보드 아이 상태 8개 항목
* 오늘의 대화거리
* 부모 전달 메시지
* 기존 리포트 요약 및 관련 인사이트 필드

대시보드 갱신용 별도 DB 데이터를 중복 생성하지 않는다.

부모 대시보드는 최신 `daily_reports` 결과를 조회하도록 연결한다.

#### 성공 판정 기준

다음 세 구간의 값이 일치해야 성공이다.

```text
daily_reports DB 값
= 부모 리포트 API 반환값
= 부모 대시보드 표시값
```

리포트 생성 완료 후 다음 캐시 처리도 수행한다.

* Next.js 서버 캐시 무효화
* React Query 또는 SWR 데이터 재검증
* 선택된 아이의 최신 리포트 재조회
* 전날 데이터 잔존 방지

부모가 이미 대시보드 화면을 열어둔 경우 다음 중 현재 구조에 적합한 방식을 적용한다.

* 일정 시간 내 자동 재조회
* 화면 재진입 시 최신 데이터 조회
* 새로고침 시 즉시 최신 데이터 조회

실시간 WebSocket 갱신을 위해 불필요하게 범위를 확대하지 않는다.

---

### 13.6 한 번에 실행 기능

관리자 편의를 위해 다음 통합 버튼도 함께 제공한다.

버튼명:

```text
수집 후 리포트 즉시 생성
```

실행 순서:

1. 선택한 날짜와 아이의 대화 수집
2. 수집 성공 확인
3. 리포트 생성
4. DB 저장 확인
5. 부모 API 반환값 확인
6. 부모 대시보드 8개 필드 반영 확인

수집 단계가 실패하면 리포트 생성을 실행하지 않는다.

일부 아이만 실패한 전체 실행에서는 성공·실패 대상을 분리해서 보고한다.

### 13.7 실행 상태 UI

버튼 실행 중에는 중복 클릭을 막는다.

```text
대시보드 반영 확인 중
```

실행 중 화면을 새로고침해도 서버 작업 자체가 중복 실행되지 않도록 한다.

장시간 작업은 프런트엔드 요청을 계속 열린 상태로 유지하기보다 현재 프로젝트 구조에 맞는 작업 ID 기반 상태 조회 방식을 우선 검토한다.

단, 베타 오픈 전 과도한 신규 작업 큐 시스템을 만들 필요는 없으며 현재 인프라에서 안전하게 완료 가능한 최소 구조를 사용한다.

#### 보안 조건

* 임의 Edge Function URL 호출 방지
* 동일 작업 중복 실행 잠금
* 실행자와 실행 결과 감사 기록

프런트엔드에서 직접 Supabase `service_role` 키나 Edge Function 관리자 비밀값을 사용하지 않는다.

전체 아이 실행:


전체 아이 실행은 실수 방지를 위해 한 번의 확인 절차를 거친다.

### 13.11 실패 및 재실행 처리

* 실패한 아이만 선택해 다시 실행할 수 있어야 한다.
* 성공한 아이의 리포트를 불필요하게 다시 생성하지 않는다.
* 동일 실행을 반복해도 중복 데이터가 생기지 않는다.
* LLM 호출 실패와 DB 저장 실패를 구분한다.
* 일부 항목만 저장된 불완전한 리포트는 완료로 표시하지 않는다.
* 이전 정상 리포트를 삭제한 뒤 신규 생성에 실패하는 방식은 사용하지 않는다.
* 신규 리포트 저장 성공 후 기존 값을 대체하는 안전한 순서를 적용한다.

### 13.12 관리자 수동 실행 E2E 검증

#### 시나리오 A — 특정 아이 즉시 수집

1. 대상 날짜와 아이 선택
2. `즉시 대화 수집` 실행
3. 미션·자유대화 수집 건수 확인
4. 동일 버튼 재실행
5. 중복 수집 없음 확인

#### 시나리오 B — 즉시 리포트 생성

1. 수집 완료된 날짜와 아이 선택
2. `즉시 리포트 생성` 실행
3. `daily_reports` 저장 확인
4. 부모 상태 8개 필드 확인
5. API 응답값 확인
6. 부모 대시보드 표시 확인

#### 시나리오 C — 통합 실행

1. 대상 날짜와 아이 선택
2. `수집 후 리포트 즉시 생성` 실행
3. 수집부터 대시보드 반영까지 한 번에 완료 확인
4. 최종 결과 `8/8` 확인

#### 시나리오 D — 자유대화만 존재

1. 자유대화만 있는 아이와 날짜 선택
2. 통합 실행

## 13.15 리포트 생성 대상 선택

`즉시 리포트 생성`과 `수집 후 리포트 즉시 생성`을 실행할 때 관리자는 반드시 실행 대상을 먼저 선택해야 한다.

### 대상 선택 방식

```text
리포트 생성 대상

○ 특정 아이
○ 전체 아이
```

기본 선택값은 `특정 아이`로 설정한다.

관리자가 명시적으로 `전체 아이`를 선택하지 않는 한 전체 대상 리포트가 생성되어서는 안 된다.

### 13.16 특정 아이 리포트 생성

`특정 아이`를 선택하면 관리자 화면에 아이 검색 및 선택 영역을 표시한다.

#### 검색 조건

다음 조건으로 아이를 검색할 수 있어야 한다.

* 아이 이름
* 보호자 이름
* 보호자 이메일
* 보호자 연락처 일부
* `child_id`
* 보호자 계정 ID
* 가입 상태
* 최근 대화 여부

개인정보는 관리자 권한 사용자에게만 표시하며, 검색 결과 목록에서는 필요한 범위만 노출한다.

#### 아이 목록 표시 항목

| 항목      | 표시 내용                    |
| ------- | ------------------------ |
| 선택      | 라디오 버튼 또는 체크박스           |
| 아이 이름   | 등록된 아이 이름                |
| 보호자     | 보호자 이름 또는 마스킹된 계정 정보     |
| 아이 ID   | 일부 마스킹된 `child_id`       |
| 최근 대화   | 마지막 유효 대화 시각             |
| 미션 대화   | 선택 날짜의 세션 또는 발화 건수       |
| 자유대화    | 선택 날짜의 세션 또는 발화 건수       |
| 수집 상태   | 미수집 / 수집 완료 / 일부 실패      |
| 리포트 상태  | 미생성 / 생성 완료 / 실패 / 갱신 필요 |
| 최근 리포트  | 마지막 생성 시각                |
| 대시보드 상태 | 정상 항목 수 `N/8`            |

검색 결과에서 아이를 선택하면 다음 요약을 먼저 표시한다.

```text
선택한 아이
- 아이 이름:
- 보호자:
- 대상 날짜:
- 미션 대화:
- 자유대화:
- 최근 수집:
- 최근 리포트:
- 부모 대시보드 상태:
```

특정 아이를 선택하지 않은 상태에서는 실행 버튼을 비활성화한다.

#### 특정 아이 실행 버튼

```text
선택한 아이 즉시 리포트 생성
```

또는 통합 실행 시:

```text
선택한 아이 수집 후 리포트 즉시 생성
```

특정 아이 실행에서는 선택한 `child_id`와 `business_date`만 처리한다.

다른 아이의 대화 수집, LLM 호출, 리포트 갱신은 발생하지 않아야 한다.

### 13.17 전체 아이 리포트 생성

`전체 아이`를 선택하면 특정 아이 검색 영역 대신 전체 실행 대상 요약을 표시한다.

#### 전체 실행 대상 기준

선택한 `business_date`에 다음 중 하나 이상이 존재하는 아이만 대상으로 한다.

* 유효한 미션 아이 발화
* 유효한 자유대화 아이 발화
* 아직 수집되지 않은 유효 대화
* 수집은 완료됐지만 리포트가 없는 데이터
* 리포트가 실패했거나 갱신이 필요한 데이터

대화가 없고 정상 리포트도 존재하지 않는 아이에게 빈 리포트를 생성하지 않는다.

이미 최신 정상 리포트가 존재하고 추가 대화가 없는 아이는 기본적으로 다시 생성하지 않는다.

관리자가 전체 강제 재생성을 선택한 경우에만 기존 정상 리포트도 다시 생성할 수 있다.

#### 전체 실행 요약

실행 전 다음 내용을 표시한다.

```text
전체 아이 리포트 생성 대상

- 대상 날짜:
- 전체 등록 아이:
- 유효 대화가 있는 아이:
- 리포트 미생성:
- 리포트 실패:
- 추가 대화로 갱신 필요:
- 이미 최신 상태:
- 실제 실행 예정:
```

#### 전체 실행 옵션

```text
□ 이미 최신 리포트가 있는 아이도 강제로 다시 생성
```

기본값은 선택하지 않은 상태로 둔다.

불필요한 LLM 호출과 비용 발생을 방지하기 위해, 기본 실행에서는 갱신이 필요한 아이만 처리한다.

#### 전체 실행 확인창

```text
[날짜] 기준으로 리포트 생성이 필요한 아이 [N]명을 처리합니다.

- 신규 생성: N명
- 실패 재처리: N명
- 추가 대화 반영: N명
- 최신 상태로 제외: N명

전체 실행은 여러 번의 LLM 호출과 DB 갱신을 발생시킵니다.
계속하시겠습니까?
```

확인 버튼명:

```text
전체 대상 리포트 생성
```

취소 버튼명:

```text
취소
```

### 13.20 실행별 API 요청 범위

관리자 API 요청에는 다음 대상 범위를 명시한다.

```ts
type ReportingTarget =
  | {
      scope: "single";
      childId: string;
    }
  | {
      scope: "selected";
      childIds: string[];
    }
  | {
      scope: "all";
      forceRegenerate: boolean;
    };
```

공통 요청값:

```ts
type ManualReportingRequest = {
  businessDate: string;
  action: "collect" | "generate" | "collect_and_generate";
  target: ReportingTarget;
};
```

서버는 클라이언트가 전달한 대상만 신뢰하지 말고 다음을 다시 검증한다.

* 요청자의 관리자 권한
* 전달된 `child_id`의 실제 존재 여부
* 대상 날짜 형식과 허용 범위
* 개발 환경 여부
* 실행 대상 아이 수
* 동일 작업 실행 중 여부
* 전체 실행 시 실제 처리 대상 재계산
