# 케이 챗봇 문의·건의·버그 신고 이미지 첨부 기능

- 상태: TODO
- 유형: 신규 기능
- 우선순위: HIGH
- 대상: 아이 화면, 부모 화면, 관리자 화면
- 요청 파일: `requests/022-feature-feedback-image-attachments.md`
- 선행 기능: 케이 챗봇 문의·건의·버그 접수 기능

---

## 1. 목적

현재 케이 챗봇의 `문의하기`, `건의하기`, `버그 신고하기`는 텍스트만 접수할 수 있다.

사용자가 문제 화면, 개선 요청 화면, 오류 상태를 이미지로 함께 전달할 수 있도록 세 메뉴 모두에 이미지 첨부 기능을 추가한다.

이미지 첨부는 선택 사항이며, 이미지를 첨부하지 않아도 기존 텍스트 접수는 정상 동작해야 한다.

---

## 2. 적용 범위

다음 세 메뉴에 동일한 이미지 첨부 기능을 제공한다.

1. 문의하기
2. 건의하기
3. 버그 신고하기

적용 화면:

- 아이 화면의 케이 챗봇 모달
- 부모 화면의 케이 챗봇 모달
- 관리자 화면의 문의·건의·버그 상세 화면

---

## 3. 사용자 관점

### 3.1 아이 관점

- 글로 설명하기 어려운 문제 화면을 사진으로 보여줄 수 있어야 한다.
- 첨부 방법은 복잡하지 않아야 한다.
- 첨부한 이미지를 바로 확인하고 잘못 고른 경우 쉽게 삭제할 수 있어야 한다.
- 사진 속에 이름, 얼굴, 학교명 등 개인정보가 보일 수 있음을 쉬운 문구로 안내한다.

### 3.2 부모 관점

- 버그가 발생한 화면을 캡처해 텍스트 설명과 함께 제출할 수 있어야 한다.
- 문의나 건의 내용과 관련된 화면도 첨부할 수 있어야 한다.
- 업로드 진행 상태와 성공·실패 여부를 명확하게 확인할 수 있어야 한다.

### 3.3 사업·운영 관점

- 텍스트만으로 재현하기 어려운 문제의 확인 시간을 단축한다.
- 실제 UI 오류, 잘림, 겹침, 빈 화면, 잘못된 상태 표시 등을 신속히 확인한다.
- 첨부 이미지는 접수 건과 정확히 연결되고 관리자만 조회할 수 있어야 한다.

---

## 4. 화면 요구사항

각 접수 메뉴의 입력 영역 하단, 제출 버튼 상단에 이미지 첨부 영역을 추가한다.

표시명:

`이미지 첨부 (선택)`

안내 문구:

아이 화면:

`문제 화면이나 보여주고 싶은 사진이 있으면 올려줘. 이름이나 얼굴 같은 개인정보가 보이지 않는지 먼저 확인해 줘.`

부모 화면:

`문제 화면이나 관련 이미지를 첨부할 수 있습니다. 개인정보가 포함되지 않았는지 확인해 주세요.`

버튼 문구:

- `사진 선택`
- 모바일에서 촬영 기능을 제공할 경우 `사진 촬영`
- 첨부 후 `이미지 추가`

모바일에서는 운영체제 기본 선택 UI를 사용하여 다음 경로를 제공한다.

- 사진 보관함에서 선택
- 카메라로 촬영
- 파일에서 선택 가능한 환경은 이미지 파일만 허용

---

## 5. 첨부 가능 조건

### 5.1 허용 파일 형식

다음 이미지 형식만 허용한다.

- JPEG / JPG
- PNG
- WebP
- HEIC / HEIF는 브라우저 및 서버 처리 가능 여부를 확인한다.
- HEIC / HEIF를 그대로 처리하기 어렵다면 업로드 전 또는 서버에서 JPEG/WebP로 변환한다.

다음 형식은 허용하지 않는다.

- PDF
- GIF
- SVG
- 동영상
- 실행 파일
- 압축 파일
- 확장자만 이미지로 변경한 비정상 파일

MIME type과 실제 파일 시그니처를 서버에서 모두 검증한다.

### 5.2 첨부 개수

- 접수 1건당 최대 3장
- 최소 0장
- 문의하기, 건의하기, 버그 신고하기 모두 동일 적용

### 5.3 파일 크기

- 원본 파일 1장당 최대 10MB
- 업로드 전 클라이언트에서 리사이즈 및 압축 수행
- 최종 업로드 파일은 1장당 최대 3MB를 목표로 한다.
- 긴 변 기준 최대 2,048px로 제한한다.
- 이미지 품질은 화면 오류 식별이 가능한 수준을 유지한다.

제한을 초과한 경우 다음 메시지를 표시한다.

`이미지는 한 장당 10MB 이하만 첨부할 수 있어요.`

최대 개수를 초과한 경우:

`이미지는 최대 3장까지 첨부할 수 있어요.`

## 6. 첨부 이미지 UX

### 6.1 미리보기

이미지 선택 즉시 다음 정보를 표시한다.

- 썸네일
- 파일 순서
- 업로드 준비 상태
- 삭제 버튼
- 업로드 실패 상태

### 6.2 삭제

- 제출 전 개별 이미지 삭제 가능
- 삭제 후 다른 이미지 재선택 가능
- 삭제 시 접수 내용과 다른 첨부 이미지에는 영향이 없어야 함

### 6.3 순서

- 사용자가 선택한 순서대로 저장
- 관리자 상세 화면에서도 동일한 순서로 표시
- 이번 범위에서 드래그 정렬은 필수 아님

### 6.4 제출 버튼

- 텍스트 필수값 검증을 먼저 수행
- 이미지 처리 중에는 제출 버튼 비활성화
- 제출 중 중복 클릭 방지
- 현재 상태를 다음과 같이 표시

예:

- `이미지 처리 중...`
- `제출 중...`
- `다시 시도`

## 7. 업로드 처리 방식

이미지 업로드와 접수 데이터 저장의 정합성을 보장해야 한다.

권장 처리 순서:

1. 접수 ID 또는 임시 업로드 세션 ID 생성
2. 이미지 리사이즈 및 압축
3. 저장소 업로드
4. 첨부 메타데이터 저장
5. 접수 본문 저장 또는 접수 상태 확정
6. 성공 응답 후 사용자에게 접수번호 표시

접수 본문 저장에 실패하면 이미 업로드된 고아 파일을 정리한다.

이미지 업로드 일부가 실패한 경우:

- 성공한 이미지만 몰래 제출하지 않는다.
- 어떤 이미지가 실패했는지 표시한다.
- 사용자가 재시도 또는 해당 이미지를 삭제한 후 제출할 수 있게 한다.

네트워크 재시도 시 동일 파일이 중복 저장되지 않도록 idempotency key 또는 고유 파일 키를 사용한다.

## 8. Supabase Storage

기존 피드백 첨부용 Storage Bucket이 있으면 재사용 가능성을 검토한다.

없으면 다음 전용 비공개 Bucket을 생성한다.

권장 Bucket:

`feedback-attachments`

설정:

- Public Bucket 금지
- 모든 파일은 비공개 저장
- 관리자 또는 권한이 검증된 서버 경로를 통해서만 조회
- Service Role Key를 브라우저에 노출하지 않음
- 장기 유효 Public URL 생성 금지
- 조회 시 짧은 만료시간의 Signed URL 사용

### 8.1 권장 저장 경로

```text
feedback-attachments/
  {environment}/
    {feedback_request_id}/
      {attachment_id}.{extension}
```

사용자 이메일, 이름, 아이 이름, 원본 파일명을 경로에 포함하지 않는다.

### 8.2 환경 분리

다음 환경의 파일이 섞이지 않아야 한다.

- development
- preview
- production

각 환경은 별도 Supabase 프로젝트 또는 저장 경로를 통해 명확히 분리한다.

## 9. 데이터베이스 구조

기존 `feedback_requests` 테이블을 유지하고 첨부 전용 테이블을 추가한다.

권장 테이블명:

`feedback_request_attachments`

### 9.1 권장 필드

| 필드 | 유형 | 설명 |
|---|---|---|
| id | uuid | Primary Key |
| feedback_request_id | uuid | `feedback_requests.id` 참조 |
| storage_bucket | text | Storage Bucket |
| storage_path | text | 비공개 저장 경로 |
| original_filename | text nullable | 표시가 꼭 필요한 경우만 저장 |
| stored_filename | text | 랜덤 또는 UUID 기반 파일명 |
| mime_type | text | 검증된 MIME type |
| file_size | bigint | 최종 업로드 크기 |
| width | integer nullable | 이미지 가로 크기 |
| height | integer nullable | 이미지 세로 크기 |
| display_order | integer | 표시 순서 |
| upload_status | text | pending, uploaded, failed, deleted |
| checksum | text nullable | 중복 및 무결성 확인용 |
| created_at | timestamptz | 생성 시각 |
| deleted_at | timestamptz nullable | 논리 삭제 시각 |

### 9.2 관계

- `feedback_requests` 1건에 첨부 최대 3개
- 접수 삭제 또는 보존기간 만료 시 연결된 Storage 파일도 함께 정리
- DB 레코드와 Storage 파일의 불일치 여부를 점검할 수 있어야 함

## 10. 보안 및 개인정보 보호

### 10.1 접근 권한

- 일반 사용자는 자신의 접수에 첨부할 이미지만 업로드 가능
- 일반 사용자는 다른 사용자의 첨부 이미지 조회 불가
- 일반 사용자는 다른 사용자의 Storage 경로를 추측해도 접근 불가
- 관리자만 전체 접수 첨부 이미지 조회 가능
- 관리자 조회도 Signed URL 또는 서버 인증 경로 사용

### 10.2 RLS 및 Storage 정책

다음을 검증한다.

- `feedback_request_attachments` RLS 적용
- 현재 인증 세션과 접수 소유권 일치 확인
- `feedback_request_id`를 클라이언트가 임의 조작해 타인 접수에 파일을 연결하지 못하도록 서버 검증
- 관리자 권한 판정은 기존 관리자 권한 구조 재사용
- Storage INSERT, SELECT, DELETE 정책을 최소 권한으로 구성

### 10.3 EXIF 및 메타데이터 제거

업로드 전에 다음 메타데이터를 제거한다.

- GPS 위치
- 촬영 기기 정보
- 촬영 일시
- 카메라 설정
- 기타 EXIF 메타데이터

이미지 방향 정보가 필요한 경우 회전 적용 후 EXIF를 제거한다.

### 10.4 민감정보 안내

이미지 선택 영역에 다음 경고를 표시한다.

아이 화면:

`사진에 이름, 얼굴, 학교 이름, 전화번호가 보이지 않는지 확인해 줘.`

부모 화면:

`이름, 얼굴, 학교명, 주소, 연락처 등 개인정보가 포함된 이미지는 첨부하지 마세요.`

이번 범위에서 자동 얼굴 블러나 OCR 기반 개인정보 탐지는 필수 구현 범위에 포함하지 않는다.

### 10.5 악성 파일 방지

- 클라이언트 확장자 검증만 신뢰하지 않음
- 서버에서 MIME type과 파일 시그니처 검증
- SVG 업로드 금지
- 이미지 디코딩 실패 파일 거부
- 파일명 Sanitization
- 저장 파일명은 UUID 기반으로 재생성
- 이미지 처리 라이브러리의 알려진 취약점 확인

## 11. 제출 실패 및 복구

### 11.1 이미지 업로드 실패

메시지:

`이미지를 올리지 못했습니다. 다시 시도하거나 해당 이미지를 삭제해 주세요.`

동작:

- 텍스트 입력 내용 유지
- 성공한 첨부와 실패한 첨부 상태 구분
- 재시도 가능
- 중복 업로드 금지

### 11.2 접수 저장 실패

메시지:

`접수하지 못했습니다. 작성한 내용과 선택한 이미지는 유지되니 다시 시도해 주세요.`

동작:

- 사용자 입력 유지
- 가능하면 이미지 선택 상태 유지
- 이미 업로드된 파일은 일정 시간 동안 임시 상태로 관리
- 재시도 성공 시 동일 접수에 연결
- 일정 시간 내 접수되지 않은 임시 파일은 자동 정리

### 11.3 모달 종료

이미지가 선택된 상태에서 모달을 닫을 경우 확인한다.

`작성 중인 내용과 첨부 이미지가 삭제됩니다. 닫을까요?`

확인 후 닫으면:

- 로컬 미리보기 URL 해제
- 임시 업로드 파일이 있다면 정리 대상 등록
- 입력 상태 초기화

## 12. 관리자 화면

기존 관리자 메뉴 `문의·건의·버그 접수`의 상세 화면에 첨부 이미지 영역을 추가한다.

### 12.1 목록 화면

첨부 이미지가 있는 접수는 다음 표시를 추가한다.

- 이미지 아이콘
- 첨부 개수

예:

`이미지 2장`

### 12.2 상세 화면

다음 기능을 제공한다.

- 첨부 이미지 썸네일
- 선택 시 확대 보기
- 이미지 간 이전·다음 이동
- 원본 비율 보기
- 관리자 다운로드
- 파일 정보 확인
  - MIME type
  - 파일 크기
  - 이미지 크기
  - 업로드 시각

원본 Storage 경로와 Bucket 내부 구조는 일반 관리자 UI에 불필요하게 노출하지 않는다.

### 12.3 이미지 열람

- 짧은 만료시간의 Signed URL 사용
- 새 탭 또는 보안된 이미지 뷰어 사용 가능
- URL 만료 후 재발급
- 브라우저 캐시 정책 검토
- 일반 사용자에게 관리자용 이미지 URL 노출 금지

### 12.4 다운로드

- 관리자만 다운로드 가능
- 원본 파일명에 개인정보가 포함될 수 있으므로 다운로드 파일명은 접수번호 기반으로 재구성

예:

```text
FB-20260802-000123-01.jpg
```

## 13. 보존 및 삭제

기존 문의·피드백 데이터 보존 정책이 있으면 동일 정책을 따른다.

정책이 없다면 다음 원칙으로 구현한다.

- 접수 데이터가 유지되는 동안 첨부 이미지도 유지
- 접수 영구 삭제 시 첨부 이미지도 Storage에서 삭제
- 논리 삭제를 사용하는 경우 즉시 조회 차단 후 정책에 따라 실제 파일 삭제
- 고아 파일 정리 Job 또는 관리자 점검 수단 마련
- 삭제 작업 실패 시 재시도 가능
- Production 파일을 Dev/Preview 정리 작업이 삭제하지 못하도록 환경 분리

## 17. 검증 시나리오

### 시나리오 1: 문의하기 이미지 1장

1. 아이 화면에서 케이 챗봇을 연다.
2. 문의하기를 선택한다.
3. 내용을 입력한다.
4. 이미지 1장을 선택한다.
5. 미리보기를 확인한다.
6. 제출한다.
7. 접수번호를 확인한다.
8. 관리자 상세 화면에서 이미지가 표시되는지 확인한다.

### 시나리오 2: 건의하기 이미지 3장

1. 부모 화면에서 건의하기를 선택한다.
2. 제목과 내용을 입력한다.
3. 이미지 3장을 선택한다.
4. 선택 순서대로 미리보기가 표시되는지 확인한다.
5. 가운데 이미지를 삭제하고 다른 이미지를 다시 추가한다.
6. 제출한다.
7. 관리자 화면의 첨부 순서와 개수를 확인한다.

### 시나리오 3: 버그 신고 카메라 촬영

1. 모바일에서 버그 신고하기를 연다.
2. 사진 촬영을 선택한다.
3. 촬영한 이미지 미리보기를 확인한다.
4. 제목과 내용을 입력하고 제출한다.
5. iOS Safari와 Android Chrome에서 각각 확인한다.

### 시나리오 4: 이미지 없이 제출

1. 세 메뉴 각각 이미지 없이 제출한다.
2. 기존 텍스트 접수가 정상 동작하는지 확인한다.

### 시나리오 5: 허용되지 않은 파일

1. PDF, GIF, SVG 또는 동영상 파일을 선택한다.
2. 업로드가 차단되는지 확인한다.
3. 사용자가 이해할 수 있는 오류 메시지가 표시되는지 확인한다.

### 시나리오 6: 용량 초과

1. 10MB 초과 이미지를 선택한다.
2. 업로드가 차단되거나 정책에 따라 안전하게 처리되는지 확인한다.
3. 앱이 멈추거나 종료되지 않는지 확인한다.

### 시나리오 7: 최대 개수 초과

1. 이미지 4장을 선택한다.
2. 최대 3장 제한 안내가 표시되는지 확인한다.
3. 기존 선택 3장이 유지되는지 확인한다.

### 시나리오 8: 업로드 일부 실패

1. 이미지 3장을 선택한다.
2. 네트워크 오류로 1장 업로드를 실패시킨다.
3. 실패 이미지가 명확히 표시되는지 확인한다.
4. 재시도 후 중복 없이 제출되는지 확인한다.

### 시나리오 9: 접수 저장 실패

1. 이미지 업로드 후 접수 저장을 실패시킨다.
2. 입력 내용과 이미지 상태가 유지되는지 확인한다.
3. 재시도 시 동일 파일이 중복 생성되지 않는지 확인한다.
4. 최종 실패 시 고아 파일 정리 여부를 확인한다.

### 시나리오 10: 권한

1. 일반 사용자가 다른 사용자 첨부 URL에 접근한다.
2. 접근이 거부되는지 확인한다.
3. 관리자만 전체 첨부를 열람하고 다운로드할 수 있는지 확인한다.
4. Signed URL 만료 후 접근이 차단되는지 확인한다.

### 시나리오 11: EXIF 제거

1. GPS 정보가 포함된 사진을 업로드한다.
2. 저장된 이미지에서 GPS와 촬영 메타데이터가 제거됐는지 확인한다.
3. 이미지 방향이 정상인지 확인한다.

### 시나리오 12: 회귀 테스트

1. 케이 챗봇 버튼을 드래그한다.
2. 문의 모달을 연다.
3. 이미지 없이 접수한다.
4. 이미지 포함 접수를 진행한다.
5. 음성대화, 하단 메뉴, 리포트 화면이 정상 동작하는지 확인한다.

## 19. 개발 및 리뷰 원칙

- 기존 업로드 컴포넌트와 Storage 구조를 먼저 조사한다.
- 관련 없는 리팩터링은 하지 않는다.
- 파일 업로드와 접수 저장의 정합성을 우선한다.
- Public Bucket 또는 영구 공개 URL 방식은 사용하지 않는다.
- Service Role Key, API Key, 토큰을 코드·로그·임시파일에 평문 저장하지 않는다.
- 비밀정보는 기존 환경변수, Secret Manager, Vercel/Supabase Secrets에서 런타임에만 불러온다.
- 로그에는 Storage 경로와 사용자 식별정보를 필요 이상 출력하지 않는다.
- 이미지 원문을 디버그 로그나 테스트 결과물에 복사하지 않는다.
- 실제 사용자 이미지를 테스트에 사용하지 않고 별도 테스트 이미지를 사용한다.
- DB Migration, RLS, Storage 정책은 보안 집중 리뷰를 수행한다.
- BLOCKED, HIGH, MEDIUM 이슈가 남아 있으면 완료 처리하지 않는다.
- 검증 완료 후 요청 파일을 `_done/`으로 이동하고 `_log.md`에 결과를 기록한다.
