# REQUEST 019 — 부모 대시보드 8개 카드 실제 분석 요약 표시 수정

## 1. 작업 목적

Production 부모 홈 대시보드의 8개 상태 카드에 실제 분석 내용 대신 다음과 같은 의미 없는 문구가 표시되고 있다.

- `새로운 이야기가 있어요`
- `분석을 준비 중이에요`

대표님이 확정한 요구사항은 각 카드에 해당 영역의 실제 분석 내용을 공백 포함 15자 이내, 한 줄로 요약하여 표시하는 것이다.

이번 작업에서는 개발 서버에서 원인을 수정하고 E2E 검증을 완료한 뒤 Production에 반영한다.

---

## 2. Production 원인 진단 결과

읽기 전용 진단에서 다음 원인이 확인됐다.

### 2.1 15자 요약 생성 기능 미구현

`lib/batch/dailyReportV3.ts`의 리포트 생성 프롬프트와 출력 스키마에는 대시보드 카드용 15자 요약 필드가 없다.

현재는 상세 분석 문장만 생성·저장되고 있다.

### 2.2 정상 분석값을 UI에서 임의 교체

`InsightGrid.tsx`는 상세 분석 문장이 일정 길이를 초과하면 실제 값을 표시하지 않고 다음 문구로 교체한다.

`새로운 이야기가 있어요`

이 문구는 AI 분석 결과가 아니라 UI에 하드코딩된 fallback이다.

### 2.3 선생님·어른 영역 미구현

선생님·어른 영역은 다음 구간이 완성되지 않았다.

- 리포트 생성 프롬프트
- 출력 스키마
- TypeScript 타입
- DB 저장 필드
- API 반환
- 부모 화면 매핑

현재 UI는 해당 항목을 지원하지 않는 영역으로 판단하여 다음 문구를 고정 표시한다.

`분석을 준비 중이에요`

### 2.4 카드별 날짜 혼합

부모 리포트 API는 선택한 아이의 최신 일일 리포트 한 건으로 모든 카드를 구성하지 않고, 과거 리포트를 조회하여 영역별 값이 존재하는 최근 날짜를 각각 선택한다.

이 때문에 같은 화면에서 다음 상태가 혼합된다.

- 2일 전
- 3일 전
- 4일 전
- 기록 없음

## 3. 확정 요구사항

부모 대시보드 8개 카드의 본문은 다음 기준을 모두 충족해야 한다.

1. 해당 영역의 실제 분석 내용이어야 한다.
2. 공백 포함 15자 이내여야 한다.
3. 한 줄로 표시해야 한다.
4. 상세 리포트 문장을 단순히 앞에서 잘라 표시하면 안 된다.
5. 각 영역별로 별도의 대시보드 요약을 생성해야 한다.
6. `새로운 이야기가 있어요`와 같은 범용 문구를 사용하면 안 된다.
7. 실제 대화 근거가 없는 항목만 데이터 부족 상태로 표시한다.
8. 8개 카드는 선택한 아이의 동일한 최신 정상 일일 리포트를 기준으로 표시한다.
9. DB 저장값, API 반환값, 화면 표시값이 동일해야 한다.

## 5. 데이터 구조 변경

상세 리포트 필드와 대시보드 요약 필드를 분리한다.

예시 구조:

| 학교·학원 생활 | `school_academy_life` | `school_academy_life_summary` |

| 공부 고민 | `study_concerns` | `study_concerns_summary` |

정확한 컬럼명은 기존 네이밍 규칙을 우선 확인하고 일관되게 결정한다.

대시보드 카드는 신규 단문 요약 필드만 사용한다.

## 6. 리포트 생성 프롬프트 변경

`lib/batch/dailyReportV3.ts` 또는 실제 Production 리포트 생성 경로의 프롬프트와 JSON 스키마에 8개 단문 요약 필드를 추가한다.

### 6.1 생성 규칙

각 요약에는 다음 규칙을 강제한다.

- 공백 포함 15자 이내
- 한 줄
- 해당 영역의 실제 대화 근거 사용
- 부모가 한눈에 이해할 수 있는 표현
- 구체적인 대상 또는 행동 우선
- 같은 문구를 여러 영역에서 반복하지 않음
- 범용적인 안내 문구 사용 금지
- 데이터가 없는데 내용을 임의 생성하지 않음
- 아이가 말하지 않은 사실을 추가하지 않음

### 6.2 금지 문구

다음 문구와 의미상 동일한 범용 문구를 생성하거나 저장하면 안 된다.

- 새로운 이야기가 있어요
- 새로운 소식이 있어요
- 분석을 준비 중이에요
- 관심이 있어 보여요
- 다양한 이야기를 했어요
- 특별한 이야기가 있어요

### 6.3 정상 예시

| 영역 | 허용 예시 |
|---|---|
| 학교·학원 생활 | `방학이라 쉬고 있어요` |
| 친구 관계 | `친구와 피구했어요` |
| 마음 흐름 | `오늘 기분이 좋아요` |
| 관심사·취향 | `그림 그리기를 좋아해요` |
| 공부 고민 | `수학 문제가 어려워요` |
| 디지털·콘텐츠 | `게임을 즐겨 해요` |
| 선생님·어른 | `담임 선생님을 말했어요` |
| 반복 이야기 | `피구 얘기를 자주 해요` |

예시 문구를 고정값으로 저장하지 말고 실제 대화 내용에 따라 생성해야 한다.

## 7. 15자 검증 로직

LLM이 반환한 단문 요약은 DB 저장 전에 서버에서 검증한다.

### 검증 항목

- 문자열 여부
- 공백 포함 글자 수
- 줄바꿈 포함 여부
- 금지 문구 여부
- 빈 문자열 여부
- 상세 분석과의 의미 관련성
- 해당 영역에 근거가 있는지

### 15자 초과 처리

15자를 넘는 문장을 `substring`, `slice` 또는 CSS로 잘라 저장하면 안 된다.

처리 순서:

1. 처음 생성된 요약 검증
2. 15자 초과 시 LLM 재요약 또는 안전한 압축 함수 실행
3. 다시 15자 검증
4. 기준을 통과한 값만 저장
5. 반복 실패 시 해당 항목을 데이터 부족으로 처리하고 오류 로그 기록

DB에는 검증을 통과한 전체 문장을 저장한다.

## 8. 데이터 부족 처리

실제 대화에서 특정 영역의 근거를 찾을 수 없는 경우에만 다음 상태를 사용한다.

권장 화면 문구:

`대화 정보 부족`

이 문구는 실제 분석 결과가 아니라 데이터 부족 상태임을 타입 또는 상태값으로 구분한다.

다음 행위는 금지한다.

- 이전 날짜 값을 오늘 분석값으로 재사용
- 근거 없이 일반적인 상태 생성
- 다른 영역의 분석을 복사
- `새로운 이야기가 있어요`로 대체
- 상세 분석의 임의 앞부분 표시

## 10. 부모 리포트 API 수정

부모 홈 대시보드는 선택한 `child_id`의 최신 정상 일일 리포트 한 건을 기준으로 8개 카드를 구성한다.

### 필수 조회 조건

- 선택된 `child_id`
- 정상 완료된 리포트
- 최신 `business_date`
- 동일한 리포트 ID

8개 카드의 요약값은 모두 같은 리포트 레코드에서 가져온다.

다음 방식은 사용하지 않는다.

- 최근 30일에서 영역별 마지막 값을 개별 검색
- 최신 값이 비어 있을 때 과거 값을 카드별로 혼합
- `child_memory`와 `daily_reports`를 임의로 조합
- 다른 아이의 캐시 데이터 재사용

### API 응답 예시

{
  "reportId": "masked-id",
  "childId": "masked-child-id",
  "businessDate": "2026-08-02",
  "summaryLine": "오늘 하루를 요약한 문장",
  "dashboardCards": {
    "schoolAcademyLife": {
      "summary": "방학이라 쉬고 있어요",
      "status": "available"
    },
    "peerFriendship": {
      "summary": "친구와 피구했어요",
      "status": "available"
    }
  }
}

실제 필드명은 기존 API 계약과 타입 규칙에 맞게 결정한다.

## 11. 부모 홈 UI 수정

`InsightGrid.tsx`와 관련 컴포넌트에서 다음 코드를 제거한다.

- 문자열 길이에 따라 `새로운 이야기가 있어요`로 교체하는 fallback
- 선생님·어른 영역을 강제로 미지원 처리하는 조건
- `분석을 준비 중이에요` 하드코딩
- 상세 분석을 임의로 분리하거나 자르는 로직
- 카드별 과거 리포트 조합

각 카드는 API에서 받은 단문 요약을 그대로 표시한다.

### UI 표시 기준

- 한 줄 고정
- 자동 줄바꿈 금지
- 공백 포함 15자 이내 데이터 사용
- 예상치 못한 초과값에는 `text-overflow: ellipsis`를 최종 방어 수단으로만 적용
- ellipsis가 정상 처리 방식이 되어서는 안 됨
- 데이터 부족 상태는 실제 분석값과 시각적으로 구분

## 12. 기존 상세 리포트 영향 방지

대시보드 단문 요약 추가로 기존 상세 일일 리포트가 축소되거나 삭제되면 안 된다.

다음 데이터를 구분한다.

- 상세 리포트: 부모 리포트 메뉴에서 확인
- 15자 단문 요약: 부모 홈 대시보드 카드에서 확인

기존 상세 리포트의 내용, 보존 기간, 조회 방식은 유지한다.

## 13. 자동·수동 생성 경로 통합

다음 모든 리포트 생성 경로가 동일한 단문 요약 생성·검증 로직을 사용해야 한다.

- 새벽 자동 일일 리포트 배치
- 관리자 즉시 리포트 생성
- 관리자 수집 후 리포트 즉시 생성
- 특정 아이 리포트 생성
- 전체 아이 리포트 생성
- 실패한 아이 재생성

관리자 실행과 자동 배치에서 서로 다른 프롬프트나 저장 로직을 사용하지 않는다.

## 14. 기존 Production 데이터 처리

신규 필드 추가 후 기존 리포트 레코드에 단문 요약값이 없을 수 있다.

### 처리 원칙

- 기존 상세 분석을 UI에서 직접 잘라 사용하지 않는다.
- 신규 필드가 없는 과거 리포트는 데이터 부족 상태로 처리한다.
- 필요한 경우 대표님이 관리자 수동 리포트 생성으로 특정 아이·날짜를 재생성할 수 있도록 한다.
- 모든 기존 리포트를 자동으로 강제 재생성하지 않는다.
- 기존 정상 상세 리포트를 삭제하지 않는다.

## 15. 개발 서버 검증

Production 수정 전에 개발 서버에서 다음 E2E를 완료한다.

### 대상

실제 대화가 존재하는 테스트 아이를 사용한다.

안서현 계정과 동일 증상을 재현할 수 있다면 해당 데이터 구조를 기준으로 검증하되 개인정보와 대화 원문은 보고서에 노출하지 않는다.

### 검증 순서

1. 미션·자유대화 데이터 확인
2. 보정 데이터 확인
3. 일일 리포트 생성
4. 상세 분석 8개 저장 확인
5. 단문 요약 8개 저장 확인
6. 각 요약의 공백 포함 글자 수 확인
7. API 응답 확인
8. 부모 홈 화면 확인
9. 새로고침 후 동일 값 유지 확인
10. 자녀 전환 후 데이터 혼선 확인

## 16. 필수 테스트 시나리오

### 시나리오 A — 8개 영역에 모두 근거 존재

예상 결과:

- 단문 요약 8개 생성
- 각 항목 15자 이하
- DB·API·화면 값 일치
- 범용 placeholder 없음

### 시나리오 B — 일부 영역에 근거 없음

예상 결과:

- 근거가 있는 영역은 실제 요약 표시
- 근거가 없는 영역만 `대화 정보 부족`
- 과거 데이터 혼합 없음

### 시나리오 C — 15자 초과 응답
