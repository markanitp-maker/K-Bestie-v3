# REQUEST #027 — 랜딩페이지 문의하기를 기존 앱 CS 접수 시스템과 통합

- 상태: TODO
- 유형: 신규 기능
- 우선순위: HIGH
- 대상: `app.k-bestie.com` 랜딩페이지 / 기존 관리자 CS
- 핵심 방향: 기존 `support_requests` 시스템 재사용

---

## 0. 완료 시 기대 결과 / 대표님 테스트 정상 프로세스

### 완료 시 기대 결과

랜딩페이지 하단의 `문의하기 준비중`이 실제 `문의하기` 기능으로 변경된다.

비로그인 방문자가 이메일과 문의 내용을 입력해 문의를 제출하면:

`랜딩페이지 → 문의 접수 → 기존 support_requests 저장 → 기존 관리자 CS 화면에서 확인`

흐름으로 동작한다.

별도의 랜딩 전용 CS 시스템이나 관리자 메뉴는 생성되지 않는다.

### 대표님 테스트 정상 프로세스

1. Dev 랜딩페이지에 비로그인 상태로 접속한다.
2. Footer의 `문의하기`를 클릭한다.
3. 문의 모달이 열리는지 확인한다.
4. 답변받을 이메일을 입력한다.
5. 문의 내용을 입력한다.
6. `제출하기`를 누른다.
7. `문의가 접수되었습니다.` 안내가 표시되는지 확인한다.
8. 관리자 `문의·건의·버그 접수` 화면으로 이동한다.
9. 방금 등록한 문의가 기존 목록에 표시되는지 확인한다.
10. 해당 문의를 열어 이메일, 문의 내용, `랜딩페이지` 출처, 상태가 정상 표시되는지 확인한다.

정상이라면:

- 로그인 없이 문의 가능
- 기존 CS 목록에 즉시 확인 가능
- 출처가 `랜딩페이지`로 구분
- 기존 부모/아이 앱 문의 기능은 그대로 동작

---

## 1. 목표

랜딩페이지 Footer의:

`문의하기 준비중`

을:

`문의하기`

로 변경하고 비로그인 방문자가 실제 문의를 접수할 수 있게 한다.

최종 흐름:

`랜딩페이지 → 문의 모달 → 기존 support_requests → 기존 관리자 문의·건의·버그 접수 화면`

별도의 랜딩 전용 CS 시스템은 만들지 않는다.

---

## 2. 요구사항

### 랜딩 문의

`문의하기` 클릭 시 페이지 이동 없이 문의 모달을 연다.

입력:

- 이메일: 필수 / 이메일 형식 검증
- 문의 내용: 필수 / 최대 2,000자 / 공백만 입력 금지
- 이미지: 선택 / 기존 문의 이미지 첨부 구조를 안전하게 재사용할 수 있을 때만 제공

버튼:

`제출하기`

기존 랜딩페이지 디자인·레이아웃·Footer 구성은 유지한다.

### 표시 문구

모달 제목:

`문의하기`

안내:

`내친구 케이 이용에 궁금한 점이 있으시면 남겨주세요.`  
`확인 후 입력하신 이메일로 안내드리겠습니다.`

이메일 placeholder:

`답변받을 이메일을 입력해 주세요.`

문의 내용 placeholder:

`궁금한 내용을 입력해 주세요.`

접수 성공:

`문의가 접수되었습니다.`  
`확인 후 입력하신 이메일로 안내드리겠습니다.`

접수 실패:

`문의를 접수하지 못했습니다.`  
`작성한 내용은 유지되니 잠시 후 다시 시도해 주세요.`

성공 시:

- 기존 접수번호 체계가 있으면 표시
- 입력값 초기화
- 모달 닫기 가능
- 페이지 새로고침 불필요

실패 시:

- 이메일과 문의 내용 유지
- 첨부 이미지도 가능한 범위에서 유지
- 내부 기술 오류 메시지는 사용자에게 노출하지 않음

### 접수 데이터

기존 `support_requests`를 사용한다.

랜딩 문의는:

- `request_type = inquiry`
- `source = landing`
- `contact_email` 저장
- `content` 저장
- 기존 `status` 체계 사용

비로그인 문의이므로 다음 사용자 식별값은 없어도 정상 처리한다.

- `user_id`
- `guardian_id`
- `child_id`

클라이언트가 임의의 사용자 ID를 전달하지 않도록 한다.

기존 source/origin/surface 계열 필드가 있으면 재사용한다.

해당 필드가 없을 경우에만 현재 schema를 확인한 후 최소 migration을 적용한다.

### 관리자

기존 `문의·건의·버그 접수` 관리자 화면에서 랜딩 문의를 함께 관리한다.

목록에서 최소 확인 가능:

- 유형
- 이메일
- 출처: `랜딩페이지`
- 접수일
- 상태

상세에서 최소 확인 가능:

- 접수번호
- 문의 유형
- 이메일
- 문의 내용
- 첨부 이미지
- 출처
- 접수일시
- 처리 상태
- 관리자 내부 메모

guardian/child 정보가 없는 랜딩 문의도 오류 없이 정상 처리한다.

### 비로그인 보안

서버 측에서 최소 다음을 검증한다.

- 이메일 형식
- 내용 길이
- 공백 입력
- HTML/script 안전 처리
- 동일 클라이언트의 과도한 연속 요청 제한

문의 제출을 위해 로그인이나 회원가입을 요구하지 않는다.

## 3. 기존 구조 확인

구현에 직접 필요한 범위만 확인하고 기존 구조를 우선 재사용한다.

확인 대상:

- 랜딩 Footer의 현재 문의 문구
- `support_requests` 실제 schema
- 기존 support 접수 API
- 기존 이미지 첨부 구조
- 기존 source/origin/surface 필드
- 기존 status 체계
- 비로그인 요청에 재사용 가능한 rate-limit 방식
- 관리자 CS 화면의 nullable 사용자 정보 처리 방식

코드에서 확인 가능한 내용은 추측하지 않는다.

관련 없는 CS 기능이나 프로젝트 전체로 조사 범위를 확대하지 않는다.

- `landing_inquiries` 등 별도 랜딩 문의 DB 생성
- 별도 랜딩 CS API 체계 구축
- 별도 관리자 메뉴 생성
- 신규 CS 아키텍처 설계
- 별도 Storage 구조 임의 생성
- 기존 구조에 없는 CAPTCHA 신규 도입
- 관리자 이메일 직접 발송 기능 신규 구현
- 랜딩에 건의하기/버그 신고하기 기능 추가
- 관련 없는 리팩터링

다음 기존 기능은 변경하지 않는다.

- 앱 케이 챗봇
- 부모/아이 앱 문의
- 앱 건의/버그 신고
- 기존 이미지 첨부
- 내 접수 확인
- 관리자 기존 CS 목록
- 관리자 상태 변경
- 관리자 내부 메모
- 랜딩 회원가입/시작하기 동선
- FAQ
- 랜딩 기존 디자인/레이아웃

## 5. 모호성 처리

Request와 현재 코드만으로 구현 판단이 가능하면 그대로 진행한다.

다음 경우에는 관련 코드와 필요한 Skill/Reference만 추가 확인한다.

- 기존 source 계열 필드가 여러 개 존재
- 현재 `support_requests`가 비로그인 문의를 직접 수용하지 못함
- 이미지 업로드가 로그인 사용자에 강하게 종속됨
- 관리자 화면이 nullable 사용자 정보를 처리하지 못함
- 기존 rate-limit 구조의 재사용 가능 여부가 불명확함

관련 Reference까지 확인해도 정책이나 데이터 구조 선택에 따라 실제 사용자 동작이 달라진다면 임의 구현하지 않는다.

다음만 보고하고 해당 판단 지점에서 중단한다.

1. 불명확한 지점
2. 가능한 선택지
3. 선택지별 실제 차이
4. 기존 정책과 구조 기준 권장 방향

## 6. QA

`qa-scope` Skill을 적용하여 실제 최종 diff의 위험도에 맞는 최소 충분 QA만 수행한다.

이번 Request의 필수 Gate:

- 비로그인 문의 접수 성공
- 기존 `support_requests`에 정상 저장
- `source = landing` 또는 기존 구조상 동등한 출처 구분 정상
- 기존 관리자 CS 화면에서 랜딩 문의 조회 가능
- 이메일 오류/빈 내용/공백 입력 차단
- 과도한 연속 요청 차단
- 기존 앱 CS에 직접 영향을 준 변경이 있는 경우 해당 범위만 회귀 검증
