# 일일 24시간 대화 QA 및 관리자 이슈 사항 v1

## 0. 완료 시 기대 결과 / 대표님 테스트 정상 프로세스

### 완료 시 기대 결과

내친구 케이가 매일 자동으로 지난 24시간 실제 아이의 미션·자유대화 전체를 전수 QA하고, 결과를 관리자 `운영 도구 > 이슈 사항` 탭에 누적 표시해야 한다.

최종 동작 흐름:

```text
매일 02:00 KST
→ 지난 24시간 실제 아이 대화 조회
→ Test/QA 계정 제외
→ 1차 규칙 기반 전수 탐지
→ 문맥 판단이 필요한 의심 사례만 Gemini 2.5 Flash로 2차 검증
→ 이슈 분류/심각도/발생 건수/영향 아이·세션 계산
→ 전일 결과와 비교하여 상태 계산
→ daily_conversation_qa_runs 저장
→ daily_conversation_qa_issues 저장
→ 관리자 > 운영 도구 > 이슈 사항 탭 표시
```

최상위 목적:

> 실제 아이들이 케이와 대화하면서 겪는 문제를 매일 자동으로 발견하고, 패치 이후 실제 운영 대화에서 문제가 줄었는지 또는 재발했는지 지속적으로 확인한다.

이번 기능은 단순 로그 화면이 아니다.

- 신규 문제 발견
- 기존 문제 지속
- 해결 후 재발
- 발생량 감소
- 해결 후보
- QA 실행 실패

를 매일 구분해서 대표님이 바로 판단할 수 있어야 한다.

### 대표님 테스트 정상 프로세스

#### 시나리오 A — 정상 일일 자동 QA

1. 매일 02:00 KST에 Cron이 실행된다.
2. 실행 시점 기준 직전 24시간 실제 아이 대화가 조회된다.
3. Test/QA 계정은 분석 대상에서 제외된다.
4. 모든 실제 미션·자유대화 세션을 누락 없이 스캔한다.
5. 규칙 기반 탐지기가 전체 대화를 1차 분석한다.
6. `MISSION_FORCED_QUESTION`, `MEMORY_REPEAT`, `RELATIONSHIP_RESPONSE_MISS` 등 문맥 검증이 필요한 후보만 LLM Judge로 전달한다.
7. QA Run과 Issue 결과가 DB에 저장된다.
8. 관리자 `운영 도구 > 이슈 사항`에서 최신 결과가 표시된다.

PASS 기준:
- 분석 대상 세션 수와 실제 조회 세션 수가 일치한다.
- QA 실행 성공 여부가 명확히 기록된다.
- 문제 0건과 QA 실행 실패가 구분된다.
- Test/QA 계정 결과는 운영 지표에 포함되지 않는다.

#### 시나리오 B — 신규 BLOCKER 발생

예:

```text
아이: 잘하기!
케이: 응, 듣고 있어. 더 얘기해줄래?
```

정상 결과:

```text
심각도: BLOCKER
상태: NEW
Taxonomy: LLM_FALLBACK
발생 건수: 1+
영향 아이 수: N
영향 세션 수: N
대표 사례: 익명화된 최소 발췌
관련 session/message reference 저장
```

PASS 기준:
- 관리자 상단 BLOCKER 카운트 증가
- 이슈 목록 최상단 표시
- 전일 0건 → 오늘 발생이면 `NEW`

#### 시나리오 C — 전날 문제 재발

과거 발생 후 0건 기간이 있었다가 다시 발생하면 `RECURRED`로 표시한다.

#### 시나리오 D — 기존 문제 감소

예:

```text
어제 10건
오늘 3건
```

설정된 감소 기준을 만족하면 `IMPROVED`로 표시한다.

#### 시나리오 E — 문제 미발생

어제까지 발생했으나 오늘 0건인 경우 즉시 FIXED로 확정하지 않고 `RESOLVED_CANDIDATE`로 표시한다.

운영 기준:
- 최소 2일 이상 연속 미발생을 확인할 수 있어야 한다.
- 하루 0건만으로 자동 해결 확정 금지.

#### 시나리오 F — QA 실행 실패

DB 오류 또는 LLM Judge 실패 등으로 전수분석이 완전히 끝나지 않은 경우:

```text
SUCCESS
PARTIAL
FAILED
```

중 정확한 상태를 기록한다.

PASS 기준:
- `FAILED`인데 문제 0건처럼 표시되지 않는다.
- `PARTIAL`이면 분석 성공 세션 수와 누락 세션 수가 표시된다.
- 관리자 화면에서 오류 요약을 확인할 수 있다.

#### 시나리오 G — 관리자 수동 재실행

1. 관리자 `이슈 사항` 탭에서 `지금 다시 점검`을 누른다.
2. 현재 시점 기준 직전 24시간을 다시 READ-ONLY 분석한다.
3. 같은 분석 기간 중복 Issue 저장을 방지한다.
4. 화면이 최신 결과로 갱신된다.

## 2. 목표

현재는 대표님 또는 Antigravity가 필요할 때 수동으로 최근 대화를 전수조사한다.

최근 READ-ONLY 점검 결과:

```text
최근 30일 실제 아이:
- 261 sessions
- 5,338 messages
- 일일 평균 11.9 sessions
- 일일 평균 242.6 messages
- 일일 최대 25 sessions
- 일일 최대 425 messages
```

현재 규모에서는 매일 전체 실제 아이 대화를 전수 분석하는 비용/처리량이 충분히 감당 가능하다.

기존:

```text
문제 제보
→ 대표님 요청
→ Antigravity 전수조사
→ 원인 분석
→ Request 작성
```

변경:

```text
매일 자동 QA
→ 관리자 이슈 사항 자동 누적
→ 대표님이 신규/재발/BLOCKER 확인
→ 필요한 이슈만 개발 Request로 전환
```

핵심 원칙:

> 코드가 수정되었다는 사실보다 실제 아이 대화에서 문제가 다시 발생했는지를 운영의 Source of Truth로 본다.

### 3-7. 하이브리드 탐지


### 3-11. Trend Status

자동 상태:

```text
NEW
RECURRED
ONGOING
IMPROVED
RESOLVED_CANDIDATE
```

기본 의미:

- NEW: 과거 이력 없이 오늘 처음 발생
- RECURRED: 과거 발생 후 0건 기간을 거쳐 다시 발생
- ONGOING: 전일과 오늘 모두 발생
- IMPROVED: 전일 대비 유의미하게 감소
- RESOLVED_CANDIDATE: 어제까지 발생했으나 오늘 0건

중요:
- `RESOLVED_CANDIDATE`는 FIXED가 아니다.
- 하루 0건만으로 해결 확정하지 않는다.
- 최소 2일 이상 연속 미발생 추적이 가능해야 한다.

### 3-12. 전일 대비 비교

가능하면 다음을 함께 계산한다.

```text
event count
affected sessions
affected children
issue rate per analyzed session
```

절대 건수만으로 악화/개선을 단정하지 않는다.

### 3-13. 대표 사례 저장

전체 대화 원문을 신규 테이블에 복제하지 않는다.

저장:

```text
session_id
message_id
익명화된 최소 excerpt
```

최대 1~3개 대표 사례만 저장하고 excerpt는 최대 약 200자 이내를 기본으로 한다.

### 3-14. 상세 원문 조회

관리자가 대표 사례를 클릭해 전체 맥락이 필요하면 기존 Source of Truth:

```text
chat_messages
chat_sessions
```

에서 관리자 API를 통해 실시간 조회한다.

### 3-15. 관리자 권한

기존:

```text
lib/admin/requireAdmin.ts
lib/admin/adminActor.ts
```

를 재사용한다.

일반 parent/child/authenticated 사용자는 QA Run/Issue를 읽을 수 없어야 한다.

### 3-16. RLS

신규 테이블은 RLS를 활성화한다.

원칙:

```text
service_role → batch INSERT/UPDATE/SELECT
admin API → server-side authorized SELECT
parent/child/anon → 직접 접근 차단
```

### 3-17. Vercel Cron

매일 02:00 KST 실행한다.

UTC 기준:

```text
0 17 * * *
```

실제 경로:

```text
/api/batch/daily-qa
```

최종 endpoint 이름은 기존 batch naming convention에 맞춰 조정 가능하다.

### 3-18. 24시간 Window

이번 정책은 전날 business_date 전체가 아니라 실행 시점 기준 직전 24시간이다.

예:

```text
2026-08-20 02:00 KST 실행
window:
2026-08-19 02:00:00 KST
~
2026-08-20 02:00:00 KST
```

DB에는 `window_start`, `window_end`를 반드시 기록한다.

### 3-19. 배치 인증

기존 batch worker 인증 패턴을 재사용한다.

인증 없는 public batch endpoint는 금지한다.

### 3-20. 수동 `지금 다시 점검`

관리자 탭에 `지금 다시 점검` 버튼을 추가한다.

동작:

```text
POST /api/admin/operations/issues/run
```

관리자 권한 필수.

### 3-21. Idempotency / 중복 Run 방지

자동 Cron과 관리자 수동 실행이 겹칠 수 있다.

동일 window 또는 동일 execution key 기준으로 중복 Issue 저장을 방지한다.

### 3-22. Run 실패 처리

Run 상태:

```text
RUNNING
SUCCESS
PARTIAL
FAILED
```

`PARTIAL`이면 분석 성공/실패 세션 수와 error summary를 기록한다.

### 3-23. 관리자 실패 UI

`FAILED` 또는 `PARTIAL` 시 상단 경고를 표시한다.

`FAILED` Run은 절대 문제 0건으로 보이면 안 된다.

### 3-24. 이슈 상세 UI

이슈 클릭 시 다음 정보를 확인할 수 있게 한다.

```text
Taxonomy
Severity
Trend Status
오늘 발생 건수
전일 발생 건수
영향 아이 수
영향 세션
최초/최근 발생
대표 사례
관련 session/message
root cause hint
```

### 3-25. 안전 이슈

`SAFETY_POTENTIAL_MISS`는 자동 탐지 결과만으로 실제 miss라고 확정하지 않는다.

높은 confidence LLM 판단 또는 관리자 검토가 필요하다.

### 3-26. 테스트 계정 별도 집계

운영 기본 결과에서는 Test/QA 제외.

향후 `실제 사용자 / 테스트 포함` 토글 확장이 가능하도록 데이터 구조는 test 여부를 식별 가능하게 유지한다.

### 3-27. 보존 정책

QA 이슈 결과는 운영 품질 metadata이므로 raw conversation 7일 보존 정책과 동일하게 자동 삭제하지 않는다.

대표 excerpt는 최소화한다.

Run/Issue 보존 기간은 기존 관리자 운영 로그 정책을 확인한 뒤 적용한다.

## 5. 금지사항

1. 전체 대화를 매일 전부 LLM에 전달하지 않는다.
2. Test/QA 계정을 운영 기본 문제 통계에 섞지 않는다.
3. 신규 QA 테이블에 전체 아동 대화 원문을 복제하지 않는다.
4. PII를 대표 사례에 그대로 저장하지 않는다.
5. 하루 0건만으로 FIXED 판정하지 않는다.
6. Git commit 존재만으로 문제 해결 판정하지 않는다.
7. QA 실행 실패를 문제 0건으로 표시하지 않는다.
8. 자동 QA가 코드를 수정하거나 배포하지 않는다.
9. 자동 QA가 기존 운영 대화 데이터를 수정하지 않는다.
10. Safety 기능을 자동 QA 때문에 변경하지 않는다.
11. Scratch 분석 script를 그대로 Production Cron에서 실행하지 않는다.
12. 인증 없는 batch endpoint를 만들지 않는다.
13. 수동 재실행으로 중복 Issue가 생성되지 않게 한다.
14. 기존 운영 도구 탭의 기능을 깨지 않는다.

## 6. 모호성 처리

### 6-1. 자정 기준 vs 직전 24시간

이번 정책은 직전 24시간이다.

Cron 02:00 기준:

```text
전일 02:00 ~ 당일 02:00
```

### 6-2. 세션이 Window 경계를 걸치는 경우

분석 대상 이벤트는 window 내 발생을 기준으로 하되 필요한 앞뒤 문맥은 최소 범위로 읽는다.

### 6-3. LLM Judge 실패

규칙 탐지 결과는 유지한다.

LLM 검증 필수 candidate가 실패하면 taxonomy별로 UNKNOWN 또는 Run PARTIAL 처리 기준을 명확히 정의한다.

### 6-4. 전일 데이터가 없는 첫 Run

모든 발견 Issue는 NEW 또는 baseline 상태로 처리하고 첫날임을 UI에 표시한다.

### 6-5. 세션 모수가 너무 작은 날

절대 건수 감소만으로 IMPROVED를 과장하지 않고 count/rate/affected children을 함께 본다.
