#CS 시스템 고도화: 관리자 답변·처리상태·사용자 알림·Discord 연동

- 상태: TODO
- 유형: 기능 고도화
- 우선순위: HIGH
- 개발 담당: Claude Code
- 대상: 아이 화면, 부모 화면, 관리자 화면, Discord 운영 채널
- 기반 기능:
  - 문의하기
  - 건의하기
  - 버그 신고하기
  - 이미지 첨부
  - 관리자 문의·건의·버그 접수 관리
  - 사용자 내 접수 확인 기능이 존재하면 재사용

---

## 0. 작업 목표

현재 문의·건의·버그 접수 시스템은 사용자가 요청을 등록하고 관리자가 이를 확인하는 구조까지 구현되어 있다.

이번 작업에서는 이를 실제 운영 가능한 CS 처리 시스템으로 고도화한다.

최종 흐름:

```text
사용자 문의/건의/버그 접수
→ Discord 운영 채널 신규 접수 알림
→ 관리자 접수 확인
→ 상태 변경
→ 관리자 답변 작성
→ 사용자에게 상태 변경/답변 알림
→ 사용자가 자신의 접수 상세에서 상태와 답변 확인
→ 처리 완료
```

핵심 목표:

1. 관리자가 새 접수를 빠르게 인지할 수 있어야 한다.
2. 관리자가 접수별 처리 상태를 변경할 수 있어야 한다.
3. 관리자가 사용자에게 공식 답변을 남길 수 있어야 한다.
4. 사용자는 자신의 접수 상태와 관리자 답변을 확인할 수 있어야 한다.
5. 관리자 답변 또는 주요 상태 변경 시 사용자에게 알림을 제공한다.
6. Discord에는 개인정보·문의 원문 전체를 보내지 않고 최소 정보만 전달한다.
7. 기존 문의·건의·버그 접수 구조를 재사용하고 별도 CS 시스템을 중복 구축하지 않는다.

---

# 1. 구현 전 사전 조사

Claude Code는 구현 전에 현재 구조를 반드시 먼저 확인한다.

확인 항목:

- 기존 `support_requests` 또는 동일 목적 테이블
- 문의·건의·버그 구분 필드
- 현재 접수 상태 필드
- 관리자 접수 목록/상세 화면
- 관리자 메모 기능
- 사용자 `내 접수 확인` 기능 존재 여부
- 이미지 첨부 테이블 및 Storage 구조
- 현재 사용자 알림 시스템
- PWA Push 또는 앱 알림 구조 존재 여부
- Discord 관련 기존 webhook 코드 존재 여부
- 기존 서버-side notification utility 존재 여부
- 아이/부모 인증 구조
- child / guardian 관계
- RLS 정책
- 기존 배포 환경변수 관리 방식

기존 구조가 있으면 반드시 재사용한다.

별도 문의 시스템, 별도 관리자 페이지, 별도 고객 DB를 임의 생성하지 않는다.

# 2. 접수 유형

기존 3개 유형 유지:

```text
inquiry
suggestion
bug
```

사용자 표시:

```text
문의
건의
버그
```

이번 작업에서 접수 유형을 새로 추가하지 않는다.

---

# 3. 처리 상태

기존 상태값이 있으면 재사용한다.

기본 권장 상태:

```text
received
reviewing
in_progress
resolved
closed
```

사용자 표시:

| DB 상태 | 아이 화면 | 부모 화면 |
|---|---|---|
| received | 접수됐어 | 접수 완료 |
| reviewing | 확인하고 있어 | 확인 중 |
| in_progress | 처리하고 있어 | 처리 중 |
| resolved | 처리가 끝났어 | 처리 완료 |
| closed | 확인이 끝났어 | 종료 |

관리자 화면에서는 실제 DB 상태값과 사용자 표시값을 명확히 매핑한다.

기존 상태 enum이 있으면 중복 enum 생성 금지.

---

# 4. 관리자 상태 변경

관리자 접수 상세 화면에서 상태 변경 가능해야 한다.

예:

```text
접수 완료
→ 확인 중
→ 처리 중
→ 처리 완료
→ 종료
```

관리자가 상태 변경 시 다음을 기록한다.

- 이전 상태
- 새 상태
- 변경 관리자
- 변경 시각

기존 audit/history 구조가 있다면 재사용한다.

없으면 다음 구조를 검토한다.

```text
support_request_status_history

id
support_request_id
previous_status
new_status
changed_by
created_at
```

---

# 5. 관리자 공식 답변 기능

관리자 접수 상세 화면에 사용자에게 보여줄 공식 답변 입력 영역을 추가한다.

관리자 내부 메모와 사용자 답변은 반드시 분리한다.

예:

```text
[관리자 내부 메모]
운영자끼리만 확인

[사용자 답변]
사용자가 직접 확인
```

사용자 답변 저장 필드 예:

```text
admin_response
responded_at
responded_by
```

기존 구조가 있다면 재사용한다.

---

# 6. 관리자 답변 UX

관리자 상세 화면:

```text
문의 내용

사용자가 작성한 원문
첨부 이미지

현재 상태
[처리 중 ▼]

관리자 내부 메모
[........................]

사용자에게 보내는 답변
[........................]

[답변 저장]
```

답변 저장 시:

- 사용자 답변 저장
- `responded_at` 갱신
- `responded_by` 기록
- 사용자 알림 생성
- 필요 시 상태 변경과 동시에 저장 가능

답변 저장과 내부 메모 저장이 서로 섞이지 않아야 한다.

---

# 7. 사용자 내 접수 확인 화면

아이와 부모가 본인이 작성한 접수만 확인할 수 있어야 한다.

목록:

- 접수 유형
- 제목
- 접수일
- 현재 상태
- 관리자 답변 여부

예:

```text
[버그]
마이크가 작동하지 않아요

2026.08.12
처리 중
새 답변 있음
```

---

# 8. 사용자 접수 상세 화면

표시 항목:

- 접수번호
- 유형
- 제목
- 내용
- 첨부 이미지
- 접수일
- 현재 상태
- 관리자 답변
- 관리자 답변 등록일

예:

```text
현재 상태
처리 중

관리자 답변

확인했습니다.
현재 iPhone 이미지 첨부 과정에서 발생하는 문제를 수정하고 있습니다.
수정 완료 후 다시 안내드리겠습니다.

2026.08.12
```

관리자 내부 메모는 절대 사용자에게 노출하지 않는다.

---

# 9. 아이 화면 문구

아이에게는 운영 용어를 그대로 노출하지 않는다.

예:

```text
접수됐어
확인하고 있어
처리하고 있어
처리가 끝났어
```

관리자 답변 제목:

```text
케이팀에서 답장이 왔어
```

부모 화면:

```text
관리자 답변
```

---

# 10. 사용자 알림

관리자가 다음 동작을 했을 때 사용자 알림을 생성한다.

필수 알림 조건:

1. 관리자 답변 등록
2. 상태가 `in_progress`로 변경
3. 상태가 `resolved`로 변경

불필요하게 모든 상태 변경마다 알림을 반복하지 않는다.

---

# 11. 앱 내 알림

기존 앱 알림 시스템이 있으면 우선 재사용한다.

알림 예:

아이:

```text
케이팀에서 답장이 왔어!
```

부모:

```text
문의하신 내용에 답변이 등록되었습니다.
```

상태 완료:

```text
접수하신 요청의 처리가 완료되었습니다.
```

알림 클릭 시 해당 접수 상세 화면으로 이동한다.

---

# 12. Push 알림

현재 PWA Push 또는 앱 Push 구조가 이미 존재하면 연결한다.

관리자 답변 등록:

```text
문의하신 내용에 새로운 답변이 등록되었습니다.
```

처리 완료:

```text
접수하신 요청의 처리가 완료되었습니다.
```

Push 클릭:

```text
해당 support_request 상세 화면
```

으로 deep-link 처리한다.

---

# 13. Push 미지원 환경

Push 권한이 없거나 Push 기능을 사용할 수 없는 사용자는:

- 앱 내 알림
- 내 접수 확인 화면

에서 최신 상태를 확인할 수 있어야 한다.

Push 알림 때문에 CS 상태 조회 기능이 의존적으로 동작하면 안 된다.

---

# 14. Discord 신규 접수 알림

새로운 문의·건의·버그 접수 발생 시 운영용 Discord 채널에 webhook 알림을 전송한다.

흐름:

```text
사용자 접수
→ DB 저장 성공
→ Discord webhook 호출
```

Discord 전송 실패가 사용자 접수 자체를 실패시키면 안 된다.

즉:

```text
DB 접수 성공
Discord 실패
```

인 경우 사용자 접수는 성공으로 처리한다.

Discord 실패는 서버 로그 또는 재시도 대상으로만 처리한다.

---

# 15. Discord 메시지 내용

Discord에는 민감정보와 문의 전체 내용을 보내지 않는다.

전송 허용 정보:

- 접수 유형
- 접수번호
- 제목
- 접수 출처
- 접수 시각
- 관리자 페이지 바로가기 URL

문의처럼 제목이 없는 경우:

- 내용 앞부분을 짧게 잘라 제목 대용으로 사용

예:

```text
🔔 새로운 버그 신고

유형: 버그
접수번호: KB-20260812-0012
제목: 사진 첨부가 실패해요
출처: 부모 앱
접수시각: 2026-08-12 18:22

관리자에서 확인:
https://...
```

---

# 16. Discord에 보내지 않는 정보

절대 전송 금지:

- 사용자 전체 문의 원문
- 이메일 주소
- 전화번호
- 아이 이름
- 부모 이름
- child_id
- guardian_id
- user_id
- 이미지 원본
- 이미지 URL
- 관리자 내부 메모
- 인증 토큰
- IP 주소
- 브라우저 fingerprint

Discord는 신규 접수 알림 수단으로만 사용한다.

상세 내용은 관리자 페이지에서 확인한다.

---

# 17. Discord Webhook 설정

Webhook URL은 코드에 하드코딩하지 않는다.

환경변수 예:

```text
DISCORD_SUPPORT_WEBHOOK_URL
```

규칙:

- server-side only
- `NEXT_PUBLIC_` 접두어 금지
- 클라이언트 bundle 노출 금지
- Git commit 금지
- 로그 출력 금지

Dev와 Production webhook은 분리 가능 구조로 유지한다.

---

# 18. Discord 메시지 유형 구분

메시지 첫 줄 또는 Embed 제목으로 구분:

문의:

```text
🔵 새로운 문의
```

건의:

```text
🟠 새로운 건의
```

버그:

```text
🔴 새로운 버그 신고
```

색상이나 Discord Embed를 사용할 경우 Discord 메시지 가독성 범위 내에서만 적용한다.

과도한 디자인 작업은 하지 않는다.

---

# 19. Discord 실패 처리

Webhook 전송 실패 시:

- 사용자 접수 성공 상태 유지
- 서버에서 실패 로그 기록
- webhook secret 로그 금지
- 운영 시스템을 blocking 하지 않음

가능하면 짧은 timeout 적용.

기존 retry infrastructure가 있으면 재사용한다.

없으면 이번 작업 때문에 복잡한 queue 시스템을 새로 구축하지 않는다.

---

# 20. 관리자 Discord 바로가기

Discord 알림에서 관리자 접수 상세로 바로 이동할 수 있게 한다.

예:

```text
https://{admin-domain}/admin/support-requests/{request_id}
```

실제 프로젝트 관리자 route를 확인하고 정확한 URL 사용.

사용자는 해당 URL에 접근할 수 없으며 관리자 인증을 거쳐야 한다.

---

# 21. 사용자 답변 알림 흐름

최종 흐름:

```text
관리자 답변 저장
→ DB 저장
→ 사용자 알림 생성
→ Push 가능 시 Push 전송
→ 사용자 클릭
→ 해당 접수 상세
```

Discord는 신규 사용자 접수 알림용이다.

관리자 답변을 Discord에 다시 알릴 필요는 없다.

---

# 22. 랜딩페이지 문의 연동

랜딩페이지 문의 기능이 동일 `support_requests` 시스템을 사용하게 되면 Discord 알림도 동일하게 적용한다.

출처:

```text
landing
parent_app
child_app
```

예:

```text
🔵 새로운 문의

출처: 랜딩페이지
```

랜딩 문의는 비로그인 사용자이므로 사용자 Push 대상이 없을 수 있다.

이 경우:

- Discord 운영 알림
- 관리자 처리

까지만 정상 수행한다.

---

# 23. 랜딩 문의 관리자 답변

랜딩페이지 비로그인 문의의 경우 이메일 주소를 받고 있다면 관리자 답변 표시와 앱 Push가 불가능할 수 있다.

이번 요청에서는 랜딩 문의에 대해 자동 이메일 발송을 새로 구현하지 않는다.

랜딩 문의 답변 전달 방식은 기존 이메일 운영 방식이 있으면 재사용한다.

없으면 별도 후속 Request로 분리한다.

---

# 24. 보안 및 권한

일반 사용자:

허용:

- 본인 접수 목록 조회
- 본인 접수 상세 조회
- 본인 접수 관리자 답변 조회
- 본인 접수 상태 조회

금지:

- 다른 사용자 접수 조회
- 상태 변경
- 관리자 메모 조회
- 다른 사용자 관리자 답변 조회

관리자:

허용:

- 전체 접수 조회
- 상태 변경
- 사용자 답변 작성
- 관리자 내부 메모 작성
- 첨부 이미지 조회

---

# 25. RLS

기존 RLS 구조를 유지하고 필요한 경우 최소 확장한다.

중요:

- 클라이언트 필터링만으로 권한을 처리하지 않는다.
- DB/RLS 또는 server-side ownership 검증 필수.
- admin_response를 다른 사용자 ID로 직접 API 호출해서 조회할 수 없어야 한다.

---

# 26. 감사 이력

관리자 상태 변경 및 사용자 답변 등록 시 추적 가능해야 한다.

기록 대상:

- 누가 변경했는지
- 언제 변경했는지
- 이전 상태
- 새 상태
- 답변 등록 시각

# 32. 중요 구현 원칙

- 이번 기능은 기존 CS 시스템 고도화다.
- 새 CS 시스템을 만들지 않는다.
- 새 Discord Bot을 만들지 않는다.
- Discord Webhook만 사용한다.
- Discord에 문의 원문 전체를 보내지 않는다.
- Discord Secret을 클라이언트에 노출하지 않는다.
- 기존 Push 시스템이 있으면 재사용한다.
- Push 때문에 새 대규모 인프라를 만들지 않는다.
- 관련 없는 리팩터링 금지.
- 현재 동작하는 문의 시스템을 깨뜨리지 않는다.
