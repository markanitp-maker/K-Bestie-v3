# REQUEST #027 — 랜딩페이지 문의하기를 기존 앱 CS 접수 시스템과 통합

- 상태: TODO
- 유형: 신규 기능
- 우선순위: HIGH
- 대상: `app.k-bestie.com` 랜딩페이지 / 기존 관리자 문의·건의·버그 접수
- 방향: 기존 앱 `support_requests` 시스템 재사용
- 별도 문의 DB 구축 금지

---

## 1. 목적

현재 랜딩페이지 하단에는 `문의하기 준비중` 문구가 표시되어 있다.

이를 실제 `문의하기` 기능으로 활성화하고, 앱 내부 케이 챗봇에서 사용하는 기존 문의 접수 백엔드와 관리자 처리 화면을 그대로 재사용한다.

목표 구조:

```text
랜딩페이지
→ 문의하기
→ 비로그인 문의 모달
→ 기존 support_requests
→ 기존 관리자 문의·건의·버그 접수 화면
```

별도의 랜딩 전용 CS 시스템이나 관리자 페이지는 만들지 않는다.

---

## 2. 랜딩페이지 UI 변경

현재 Footer:

```text
문의하기 준비중
```

변경:

```text
문의하기
```

클릭 시 페이지 이동 없이 문의 모달을 연다.

기존 랜딩페이지 디자인·레이아웃·Footer 구성은 유지한다.

---

## 3. 문의 모달

랜딩페이지 방문자는 로그인하지 않은 사용자가 대부분이므로 앱 내부 문의 모달과 입력 구조만 다르게 한다.

입력 항목:

### 이메일
- 필수
- 답변 연락용
- 이메일 형식 검증

### 문의 내용
- 필수
- 자유 형식
- 최대 2,000자

### 이미지 첨부
- 선택
- 기존 앱 문의 이미지 첨부 기능을 안전하게 재사용할 수 있으면 동일하게 제공
- 기존 업로드 구조 재사용이 어렵다면 이번 구현에서 임의의 별도 Storage 구조를 만들지 말고 기존 구조에 맞춰 구현

버튼:

```text
제출하기
```

## 4. 문구

모달 제목:


```text
문의 내용
```

placeholder:

```text
궁금한 내용을 입력해 주세요.
```

## 5. 기존 앱 CS 백엔드 재사용

기존:

```text
support_requests
```

및 기존 관련 API·관리자 UI를 우선 조사하고 재사용한다.

새로운 `landing_inquiries` 등 별도 문의 테이블 생성 금지.

---

## 6. 접수 출처 구분

랜딩 문의와 앱 문의를 관리자에서 구분할 수 있어야 한다.

기존 source/origin/surface 계열 컬럼이 있으면 재사용한다.

권장 값:

```text
landing
parent_app
child_app
```

이번 작업에서는 랜딩 문의에:

```text
source = landing
```

을 저장한다.

기존 컬럼이 없다면 최소한의 migration으로 source 컬럼을 추가하되 먼저 현재 DB 구조를 확인한다.

---

## 7. 비로그인 사용자 처리

랜딩 문의는 로그인 없이 접수 가능해야 한다.

랜딩 접수에서는 다음 값이 없어도 정상이다.

```text
user_id = null
guardian_id = null
child_id = null
```

대신 반드시 저장:

```text
contact_email
content
source = landing
created_at
status
```

클라이언트가 임의의 user_id, guardian_id, child_id를 전달하지 않도록 한다.

---

## 8. 문의 유형

랜딩페이지 Footer의 `문의하기`는 1차 버전에서 문의 유형 하나만 사용한다.

```text
request_type = inquiry
```

랜딩페이지에 별도의:

- 건의하기
- 버그 신고하기

탭을 추가하지 않는다.

앱 내부의 기존 문의·건의·버그 3종 구조는 그대로 유지한다.

---

## 9. 접수 상태

기존 앱 문의 상태 체계를 그대로 사용한다.

예:

```text
received
reviewing
in_progress
resolved
closed
```

랜딩 문의를 위해 새로운 상태 체계를 만들지 않는다.

---

## 10. 관리자 화면

기존 `문의·건의·버그 접수` 관리자 화면에서 랜딩 문의도 함께 조회한다.

목록에서 최소 다음을 구분 가능하게 한다.

- 유형
- 문의 이메일
- 출처
- 접수일
- 상태

출처 표시:

```text
랜딩페이지
```

기존 부모/아이 앱 문의와 같은 목록에서 관리한다.

별도 관리자 메뉴는 만들지 않는다.

---

## 11. 관리자 상세

랜딩 문의 상세에서 표시:

- 접수번호
- 문의 유형
- 이메일
- 문의 내용
- 첨부 이미지가 있으면 이미지
- 출처: 랜딩페이지
- 접수일시
- 처리 상태
- 관리자 내부 메모

앱 사용자 전용 guardian/child 정보는 랜딩 문의에서 표시하지 않거나 `-` 처리한다.

---

## 12. 스팸 및 보안

비로그인 접수이므로 서버 측 보호를 적용한다.

필수:

- IP 또는 기존 프로젝트 방식의 rate limit
- 동일 클라이언트의 과도한 연속 요청 차단
- 서버 측 이메일 형식 검증
- 내용 길이 검증
- 공백만 입력 차단
- HTML/script 안전 처리

로그인이나 회원가입을 문의 제출 조건으로 만들지 않는다.

CAPTCHA는 현재 프로젝트에 이미 사용 중인 구조가 없다면 이번 작업에서 임의 도입하지 않는다.

---

## 13. 성공 처리

접수 성공:

```text
문의가 접수되었습니다.
확인 후 입력하신 이메일로 안내드리겠습니다.
```

- 기존 접수번호 체계가 있으면 접수번호 표시
- 입력값 초기화
- 모달 닫기 가능
- 페이지 새로고침 불필요

---

## 14. 실패 처리

```text
문의를 접수하지 못했습니다.
작성한 내용은 유지되니 잠시 후 다시 시도해 주세요.
```

실패 시:

- 이메일 유지
- 문의 내용 유지
- 첨부 이미지가 있다면 가능한 범위에서 상태 유지
- 기술적인 내부 오류 메시지는 사용자에게 노출하지 않음

---

## 15. 이메일 답변

이번 작업 범위에서는:

- 문의 접수
- 관리자 확인 및 상태 관리

까지만 구현한다.

관리자가 시스템에서 직접 이메일 답변을 발송하는 신규 기능은 이번 범위에서 추가하지 않는다.

현재 운영 방식으로 입력된 이메일을 확인해 대응할 수 있도록 한다.

## 17. 구현 전 확인

Codex는 구현 전에 다음만 확인한다.

1. 현재 랜딩 Footer의 `문의하기 준비중` 위치
2. 기존 `support_requests` 실제 schema
3. 기존 `/api/support` 구조
4. 기존 이미지 첨부 API 재사용 가능 여부
5. 기존 관리자 CS 목록이 nullable 사용자 정보를 처리할 수 있는지
6. 기존 source/origin 컬럼 존재 여부

확인 후 기존 구조를 최대한 재사용한다.

불필요한 리팩터링이나 신규 CS 아키텍처 설계는 하지 않는다.
