# Request: 관리자 운영 요청 데이터 소프트 삭제 및 정식 서비스 전 일괄 정리 기능

## 1. 작업 목적

정식 서비스 준비 전에 관리자 페이지에 누적된 운영 요청 데이터를 안전하게 정리할 수 있도록, 관리자 운영 영역 전체에 소프트 삭제 기능을 추가한다.

이번 작업은 실제 사용자 계정과 핵심 서비스 데이터를 삭제하는 작업이 아니다. 관리자 운영 요청 데이터만 대상으로 하며, 삭제된 데이터는 일반 목록에서 즉시 숨기되 30일 동안 복구 가능하도록 한다.

---

## 2. 확정 정책

### 2.1 적용 대상

다음 관리자 운영 요청 데이터에 삭제 기능을 추가한다.

- 베타 신청
- 문의
- 건의
- 버그 신고
- 계정 복구 승인 요청
- 요금제 변경 요청
- 아이 승인 요청
- 이벤트 지급 처리 이력
- 상품권 지급 처리 이력
- 그 밖에 관리자 페이지에서 운영 요청·처리 이력 성격으로 관리되는 데이터

### 2.2 제외 대상

아래 데이터는 이번 작업에서 절대 삭제하지 않는다.

- 부모 계정
- 아이 계정
- 가족 계정
- 인증 계정
- 대화 원본
- 보정 대화
- 미션 데이터
- 자유대화 데이터
- 리포트 데이터
- 리텐션 원천 데이터
- LLM Wiki / Memory 데이터
- 황금열쇠 원장
- 결제 원장
- 서비스 핵심 이벤트 원장

제외 대상에는 삭제 버튼을 추가하지 않는다.

## 3. 삭제 방식

모든 삭제는 물리 삭제가 아니라 소프트 삭제로 구현한다.

각 대상 테이블에는 필요한 경우 아래 컬럼을 추가한다.

```sql
deleted_at timestamptz null
deleted_by uuid null
delete_reason text null
```

필요하면 아래 컬럼도 추가할 수 있다.

```sql
restored_at timestamptz null
restored_by uuid null
permanently_deleted_at timestamptz null
```

### 필수 동작

- 삭제 시 `deleted_at`, `deleted_by`, `delete_reason` 저장
- 일반 관리자 목록에서는 `deleted_at is null` 데이터만 표시
- 삭제 직후 화면에서 즉시 사라짐
- 삭제된 데이터는 관리자 휴지통에서 조회 가능
- 삭제 후 30일 이내 복구 가능
- 30일 이후 자동 영구 삭제
- 삭제·복구·영구 삭제 이력은 감사 로그에 기록
- 삭제된 데이터가 통계, 카운트, 배지, 검색 결과에 다시 포함되지 않도록 처리

## 4. 관리자 UI 요구사항

### 4.1 개별 삭제

각 적용 대상 목록과 상세 화면에 `삭제` 버튼을 추가한다.

삭제 버튼 클릭 시 확인 모달을 표시한다.

모달에는 아래 내용을 반드시 표시한다.

- 삭제 대상 유형
- 사용자 또는 요청 식별 정보
- 제목 또는 대표 내용
- 현재 상태
- 삭제 후 일반 목록에서 숨겨진다는 안내
- 30일 이내 복구 가능 안내
- 삭제 사유 입력란

삭제 사유는 필수 입력으로 한다.

확인 문구 예시:

```text
삭제 후 일반 목록에서는 보이지 않으며, 30일 동안 휴지통에서 복구할 수 있습니다.
```

### 4.2 일괄 삭제

정식 서비스 전 누적 운영 데이터를 한 번에 정리할 수 있도록 각 대상 목록에 다중 선택과 일괄 삭제 기능을 추가한다.

필수 기능:

- 행 체크박스
- 현재 페이지 전체 선택
- 필터된 전체 결과 선택
- 선택 건수 표시
- `선택 삭제` 버튼
- 대상 유형별 삭제 건수 표시
- 일괄 삭제 전 최종 확인 모달
- 확인 문구 직접 입력

확인 문구는 아래 문장을 정확히 입력해야 실행되도록 한다.

```text
운영 요청 데이터를 삭제합니다
```

일괄 삭제 모달에는 아래 정보를 표시한다.

- 전체 삭제 예정 건수
- 유형별 건수
- 현재 필터 조건
- 삭제 후 복구 가능 기간
- 제외 대상 데이터는 삭제되지 않는다는 안내

### 4.3 정식 서비스 전 전체 정리

관리자 설정 또는 운영 관리 영역에 `정식 서비스 전 운영 데이터 정리` 기능을 추가한다.

이 기능은 아래 범위만 대상으로 한다.

- 베타 신청
- 문의·건의·버그
- 계정 복구 요청
- 요금제 변경 요청
- 아이 승인 요청
- 이벤트·상품권 처리 이력

실행 전 반드시 미리보기 단계를 제공한다.

미리보기에는 다음을 표시한다.

- 대상 테이블
- 대상 건수
- 유형별 건수
- 가장 오래된 데이터 일자
- 가장 최근 데이터 일자
- 제외 대상 목록
- 실제 삭제가 아닌 소프트 삭제라는 안내

미리보기 확인 후에만 실행 가능하게 한다.

## 5. 관리자 휴지통

관리자 사이드바에 `휴지통` 메뉴를 추가한다.

휴지통에서는 다음 기능을 제공한다.

- 삭제된 전체 운영 요청 데이터 통합 조회
- 유형별 필터
- 삭제일 필터
- 삭제자 필터
- 삭제 사유 검색
- 원래 상태 표시
- 남은 복구 가능 일수 표시
- 개별 복구
- 선택 복구
- 영구 삭제 예정일 표시

### 복구 처리

복구 시:

- `deleted_at = null`
- `deleted_by = null`
- `delete_reason = null`
- 복구 감사 로그 기록
- 원래 목록과 통계에 다시 반영

이미 동일 데이터가 복구됐거나 중복 요청된 경우에도 멱등하게 처리한다.

## 6. 30일 후 자동 영구 삭제

매일 1회 실행되는 정리 작업을 구현한다.

기준:

```text
deleted_at < now() - interval '30 days'
```

자동 영구 삭제 전 확인 사항:

- 외래키 관계
- 첨부파일 존재 여부
- Storage 파일 존재 여부
- 감사 로그 보존 여부
- 법적·운영 보존 의무 여부

영구 삭제 시 감사 로그 자체는 삭제하지 않는다.

첨부파일이 존재하는 경우 DB 행과 Storage 파일이 불일치하지 않도록 순서를 보장한다.

권장 순서:

1. 대상 검증
2. 첨부파일 삭제
3. DB 물리 삭제
4. 감사 로그 기록
5. 실패 시 재시도 가능 상태 저장

Cron 또는 Supabase scheduled function을 사용할 수 있으나, 기존 운영 스케줄과 충돌하지 않게 한다.

## 7. API 요구사항

삭제·복구 API는 관리자 인증과 권한 검사를 필수로 한다.

예시:

```text
DELETE /api/admin/<resource>/:id
POST /api/admin/<resource>/:id/restore
POST /api/admin/<resource>/bulk-delete
POST /api/admin/<resource>/bulk-restore
GET /api/admin/trash
POST /api/admin/cleanup/preview
POST /api/admin/cleanup/execute
```

실제 프로젝트 구조에 맞춰 공통 서비스 레이어를 사용한다.

### 공통 검증

- 관리자 세션 확인
- 관리자 권한 확인
- 대상 리소스 허용 목록 검증
- 제외 대상 차단
- 이미 삭제된 데이터 재삭제 요청은 멱등 처리
- 삭제 사유 필수 검증
- bulk 요청 최대 건수 제한
- CSRF 및 비정상 요청 방어
- Service Role Key를 클라이언트에 노출하지 않음

## 8. 감사 로그

삭제 관련 모든 작업은 감사 로그에 남긴다.

필수 필드:

```text
action
resource_type
resource_id
performed_by
performed_at
reason
before_snapshot
after_snapshot
request_id
source
```

`action` 예시:

```text
SOFT_DELETE
BULK_SOFT_DELETE
RESTORE
BULK_RESTORE
PERMANENT_DELETE
CLEANUP_PREVIEW
CLEANUP_EXECUTE
```

감사 로그에는 비밀번호, 토큰, API 키, 서비스 역할 키, 민감한 원문 대화 내용을 저장하지 않는다.

## 9. 조회 및 통계 정합성

모든 기존 관리자 API, SQL, RPC, 통계 카드, 배지, 검색, 다운로드 기능에서 삭제된 데이터가 기본적으로 제외되도록 한다.

필수 점검 대상:

- 목록 건수
- 미처리 건수
- 승인 대기 건수
- 완료 건수
- 상태별 통계
- CSV/XLSX 다운로드
- 관리자 홈 KPI
- 최근 활동
- 검색 결과
- 필터 결과
- 상세 화면 이동
- 알림 배지

공통 쿼리 또는 repository 계층에서 `deleted_at is null` 조건을 적용해 누락을 방지한다.

## 10. DB 및 마이그레이션 안전 조건

- Development와 Production 스키마를 먼저 비교한다.
- 기존 pending migration 전체를 일괄 적용하지 않는다.
- 이번 작업에 필요한 migration만 별도로 작성한다.
- 기존 데이터는 보존한다.
- 기존 RLS 정책을 검토한다.
- 삭제·복구 API에 필요한 최소 권한만 추가한다.
- Production 적용 전 백업 또는 롤백 계획을 작성한다.
- migration은 재실행해도 실패하지 않게 작성한다.

## 11. UX 세부 기준

- 삭제 버튼은 위험 동작 스타일로 명확히 구분
- 실수 클릭 방지를 위해 목록에서는 아이콘 단독보다 텍스트 포함 버튼 권장
- 모바일에서도 삭제 모달과 다중 선택이 정상 동작
- 삭제 중 중복 클릭 방지
- 처리 중 로딩 상태 표시
- 성공·실패 결과 건수 표시
- 일부 실패 시 성공 건과 실패 건을 분리해 보여줌
- 실패한 항목만 재시도 가능
- 토스트만 표시하지 말고 일괄 작업 결과 화면 제공

## 12. 테스트 요구사항

### 단위 테스트

- 개별 소프트 삭제
- 중복 삭제
- 복구
- 중복 복구
- 삭제 사유 누락
- 제외 대상 삭제 차단
- 권한 없는 사용자 차단
- 30일 경과 대상 계산
- 통계 제외 조건

### E2E 테스트

각 운영 영역별로 최소 1건씩 검증한다.

1. 데이터 생성 또는 기존 테스트 데이터 선택
2. 일반 목록 노출 확인
3. 삭제 실행
4. 일반 목록에서 사라짐 확인
5. 통계·카운트 감소 확인
6. 휴지통 노출 확인
7. 복구 실행
8. 일반 목록 재노출 확인
9. 통계·카운트 복원 확인

일괄 삭제도 별도로 검증한다.

### Production 검증

Production에서는 실제 사용자 데이터가 아닌 QA 운영 요청 데이터로만 검증한다.

검증 대상:

- 베타 신청
- 문의 또는 버그
- 승인 요청
- 이벤트 또는 상품권 처리 이력

실제 부모·아이·가족·대화·미션·리포트가 삭제되지 않았는지 반드시 확인한다.

- 원문 대화 내용을 감사 로그에 저장 금지
