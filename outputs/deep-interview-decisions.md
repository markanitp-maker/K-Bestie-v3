# 내친구 케이 — Deep Interview 최종 결정 로그

## 부록: Phase1~3 구현 완료 후 2차 Deep Interview (실행 결정)

- 2차 Interview 목적: Phase1~3 구현·검증이 전부 끝난 상태에서, Production 반영/외부 인프라 생성/실제 결제/실제 메일 발송처럼 "승인 게이트"가 필요한 지점을 재점검
- 사실 확인(질문 없이 코드/DB로 해소): AI 프로바이더 그룹B는 `provider_switch_settings`에 `vertex/gemini-2.5-flash`로 유효하게 설정되어 있음(문제 없음). `lib/mail.ts`는 "소셜 로그인 전용 베타 전환"으로 **의도적으로 비활성화**되어 있고 SMTP 환경변수도 미설정 — 현재 계정 라이프사이클 알림은 시뮬레이션(로그)만 됨.

### 결정 사항 (6그룹)
1. **Production 반영 계획**: 마이그레이션 실행·cron 등록·과거 daily_reports 백필은 이번 범위에서 **금지**. KST 기준 실행 순서·멱등키·롤백 계획·예상 영향만 문서화.
2. **안전이벤트 알파**: child_id 2개 + 관리자 1개를 **환경변수 기반** allowlist 구조로 준비(실제 값은 배포 승인 시 입력). 외부 가족 등록(베타) 전 원문 전면 차단을 검증하는 자동테스트를 **필수**로 구현.
3. **케이 놀이 별도 프로젝트**: 로컬 스캐폴드·API 계약·환경변수 명세·현재 앱 모달 연동까지만. 원격 저장소·Vercel 프로젝트 생성/배포는 **금지**.
4. **자유대화 300개**: 이미 통과한 검증(그룹당10개/금칙어/질문형/중복/유사도/최근30개반복방지)에 더해 그룹별 대표문구 검수 보고서를 만들고, **현재 정적 문구를 그대로 사용**(재작성 없음).
5. **계정 알림 이메일**: SMTP 미설정 상태 유지. 발송 시뮬레이션·outbox·템플릿·재시도 상태까지 구현하되 실제 SMTP 연결/실제 발송은 **금지**.
6. **Care Insight 확장팩**: 기본3년+1년단위 최대9개, 최종 삭제 예정일, 동의 이력, 구매 UI+데이터모델까지 구현하되 실제 결제사 연동/상품 생성/과금은 **금지**.

각 항목은 로컬 구현+테스트까지 진행하고, Production·외부계정·실결제·실메일이 필요한 시점에 별도 승인을 받는다.

## 1. C1 — 미션·리포트 배치 파이프라인

### 확정 결정
- 미션 시간창: **1차 KST 13:00–17:00, 2차 19:00–23:59:59** (기존 코드 12–17시/19시–익일1시 → PRD01 기준으로 수정. GAP 결정#3 해결)
- 수집 배치: **18:00**(1차 마감 직후), **01:00**(2차 마감 직후)
- 최종 일일 리포트 배치: **03:00 KST** (기존 04:00 → 03:00으로 변경)
- 리포트 업데이트 인정 기준: **미션 게이지 100% 완료만 인정**, 0~99%는 미완료로 처리(부분 진행은 리포트에 반영하지 않음)
- 완료 미션이 하나도 없으면 리포트 문구는 정확히: **"아이가 미션을 완료하지 않아 업데이트가 없습니다"**
- 자유대화는 리포트의 **보조 자료**로만 사용(주 근거 아님)
- 새 일일 리포트는 **푸시하지 않는다** — 리포트 목록/카드에 **NEW만 표시**, 처음 열람 시 제거
- 부모 대시보드는 아래 **8개 항목으로 고정 노출** (신규/재설계):
  1. 학교·학원 생활
  2. 친구 관계와 또래 생활
  3. 감정 힌트
  4. 관심사와 개인 취향
  5. 공부 고민
  6. 디지털 관심사와 콘텐츠 취향
  7. 미래·진로·꿈
  8. 반복되는 이야기

### GAP 재해석
- "감정 힌트" 1개 필드가 기존 `mood_score`/`emotion_tags`/`emotion_level` 3개 필드를 통합 대체 → 기존 GAP 결정#4(감정칩 삭제범위) 문제는 **스키마 전면 재설계로 자동 해소**. 목록/상세의 감정 칩은 신규 8항목 스키마 적용 시 함께 제거.
- 기존 GAP 3.2/4.3("오늘의 대화거리"/"오늘 건네볼 한 문장" 전용 필드 부재)은 신규 8항목 스키마에는 명시적으로 없음 — PRD01의 8항목이 이 두 필드를 대체한 것으로 해석(별도 유지 안 함). *이 해석에 이견 있으면 구현 착수 전 알려주세요.*

### 변경 파일(예상)
- `supabase/migrations/`: `daily_reports` 8항목 스키마 마이그레이션(신규 컬럼 + 기존 mood_score/emotion_tags/emotion_level deprecate), 배치 크론 재등록(03:00/18:00/01:00 KST)

## 2. C2 — 자유대화 재설계

### 확정 결정
- 자유대화는 **생성형 LLM과 케이 음성(Gemini Live)을 사용하지 않는다**
- 아이의 음성·텍스트 입력에 **수백 개의 검수된 규칙·키워드 기반** 짧은 공감 반응을 **텍스트로만** 제공
- 질문·상세 답변·조언 금지
- 모든 분석과 안전 신호 처리는 **배치 리포트로만** 수행(자유대화 중 실시간 안전 이벤트 트리거 없음)
- **미션 대화는 영향받지 않음** — LLM 기반 미션 질문/꼬리질문/음성은 그대로 유지. 이 지시는 자유대화 채널에만 적용.

### 변경 파일(예상)
- 신규: 규칙·키워드 매칭 엔진 + 공감반응 데이터셋(콘텐츠 큐레이션 필요 — 초기 시드 데이터 협의 필요)
- `app/api/chat/messages/route.ts`: `session_type=free`일 때 LLM 호출 대신 규칙엔진 분기
- 자유대화 UI: 음성 입력 제거/텍스트 전용 전환 여부 확인 후 반영
- 기존 실시간 안전 이벤트 트리거가 있다면 배치 이동

### 리스크/순서
콘텐츠(수백 개 규칙) 준비가 선행 조건이라 구현 착수는 이르게, 완료는 늦게(병행 진행).

## 3. C3 — 부모 질문 라이프사이클

### 확정 결정
- 질문 기회: **아이 1명당 일 1회, 월요일 00시 초기화 기준 주 2회**
- 흐름: 부모가 질문 기회 사용 동의 → AI가 안전한 질문지 **1회만** 생성 → 이후 **부모 직접 수정 + 안전 재검사만** 허용(재생성 불가)
- **재생성/취소 시 질문 기회 복구하지 않음**
- 질문은 **미션에서만** 자연스럽게 **최대 2회** 확인 시도
- 부모에게는 **아이가 확인한 의미 요약**만 제공(원문/직접 답변 아님)
- 등록 직후 **"확인 중 · 최대 48시간 소요"** 표시
- 최종 상태 4종: **확인 완료 / 명확한 답변 거부 / 미션 미완료 / 최종 시스템 실패**
- 기술 실패는 **48시간 자동 재처리**, 그래도 실패한 경우에만 **"일시적인 문제로 확인을 완료하지 못했습니다. 질문 기회는 복구되었습니다"** 표시 — **이 케이스만 기회 복구**
- 동일/유사 질문도 각각 **신규 요청·신규 횟수로 정상 차감**하되, **하나의 요청에 대한 시스템 재처리는 중복 차감 금지**(요청 단위 멱등키 필요)
- 결과 배치 위치: **케이와 대화 화면의 "등록한 질문 목록"** — 새 결과는 해당 카드 + 하단 메뉴에 NEW 표시
- 일일 리포트에는 **답변을 중복 저장하지 않고**, 해당 질문 결과로 이동하는 **링크만** 제공

### GAP 재해석
기존 GAP 5.1/5.3("부모 질문 연동이 사실상 빈 껍데기")이 이 컴포넌트의 전체 구현 대상이 됨. 기존 `parentQuestionFilter.ts`(등록 시 필터)는 재사용, 그 위에 라이프사이클 전체를 신규 구축.

### 변경 파일(예상)
- `supabase/migrations/`: `parent_questions` 확장(주기 카운터, 상태머신, 요청단위 멱등키), RLS
- `app/api/parent/questions/*`: 동의→AI생성→부모수정→안전재검사 플로우
- `app/api/mission/respond/route.ts` 등: 미션 내 질문 주입(최대 2회 확인)
- 신규 배치: 48시간 상태 관리(자동 재처리, 타임아웃 처리+기회 복구)
- 케이 대화 화면: "등록한 질문 목록" UI + NEW 배지
- 리포트 ↔ 질문결과 연결 링크(중복 저장 금지)

### 의존성
C1의 미션 게이지/리포트 스키마 확정 후 진행(미션 내 확인·리포트 연결 때문). 병렬 착수는 가능.

## 4. C4 — 계정·구독·데이터프라이버시 (+ 안전이벤트 원문정책)

### 확정 결정 — 계정/구독
- 구독 취소: **결제기간 종료 후** 서비스 중지 + **30일 복구 보관** 시작 → 이후 완전 삭제
- 최종 결제 실패: **재시도 종료 후** 동일하게 서비스 중지 + 30일 복구 보관 → 완전 삭제
  - *(기존 `request_account_withdrawal` RPC + 30일 파기 흐름과 일치 — 이미 구현. GAP 결정#1은 "자녀 프로필 개별 삭제"가 아니라 "구독/계정 라이프사이클" 범위였음이 확인됨. **자녀 프로필 개별 하드삭제는 PRD01이 언급하지 않으므로 기존 구현 그대로 유지**, 변경 없음.)*
- 보존기간: **Care Start 6개월 고정**(변경 없음) / **Care Insight 기본 3년 + 1년 단위 확장팩 최대 9개**(신규) / **Care Premium 1·3·5년 선택 + 5년 권장**(신규 — 기존 `isPermanent` 상수 대체, GAP 결정#4 해결)
- 알림: 구독취소신청·복구보관시작·완전삭제 7일전/1일전·삭제완료 시 **앱 내부 + 소셜계정 이메일** 안내, **푸시 권한 있을 때만 푸시 병행**, 발송 결과 기록 (단, C1의 "일일 리포트는 푸시 안 함" 규칙과는 별개 채널)
- 아이 대화 원문: 암호화된 시스템 전용 공간에 **최대 7일 임시 보관 후 완전 파기**(기존 정책과 일치, retention-purge 크론 active 확인됨)
- 로그인: **부모는 카카오·구글만**(기존 소셜 전용과 일치 — GAP 결정#2 해결, 이메일/PIN 요구는 폐기), **아이는 부모가 생성한 아이디·해시 비밀번호로만**(기존과 일치)

### 확정 결정 — 안전이벤트 원문 정책 (알파 한정 예외, Deep Interview로 확정)
- **알파 단계**: 형진님이 지정한 **child_id 2개** + 지정된 **관리자 계정 1개**가 **모두** 허용목록과 일치할 때만, 발화·STT·배치분석 품질 확인 목적으로 원문을 **읽기 전용**으로 표시
- 검색·복사·다운로드·내보내기 **전부 금지**
- 모든 열람자·열람 시각·대상을 **감사 로그**로 기록
- 원문은 **최대 168시간 후 자동 파기**
- 일반 admin/safety_admin 역할만으로는 원문 접근 **불가** — env=alpha AND child_id 허용목록 AND 관리자 계정 허용목록, **3개 조건 서버 검증**, 하나라도 불일치 시 **fail-closed**
- **외부 가족이 참여하는 베타 배포 전**: 관리자 UI·API·DB view·RLS에서 `child_text` 반환을 **완전 제거**, 원문은 사람이 접근할 수 없는 암호화 시스템 전용 저장소에서 리포트 생성에만 사용 후 168시간 내 파기
- **자동 테스트 + 전환 체크리스트** 필수: 비허용 child_id 원문 노출 검사, 베타 환경 원문 API 응답 검사 — 하나라도 실패하면 배포 차단
- 프로덕션 데이터/배포 환경에는 **별도 승인 전까지 적용 금지**

## 5. C5 — 황금열쇠·케이놀이

### 확정 결정
- 수치(하루 최대 3개 = 출석1+미션2, 168시간 소멸, 최대 보유 22개, FIFO 소진)는 **기존 구현과 일치 — 변경 없음**
- 케이 놀이는 **동일 Supabase + 별도 코드 저장소·별도 Vercel 프로젝트**로 확정. 현재 **별도 프로젝트는 없음** — 이번 작업 범위에 **설계 + 생성 준비**까지 포함하되, **실제 원격 저장소/Vercel 프로젝트 생성·환경변수 등록·배포는 별도 승인 후에만 실행**
- 이번 저장소(K-Bestie-v3) 범위: 케이 놀이 **목록·전체화면 모달 실행·복귀 UI + 연동 계약(API 계약)만** 구현. **놀이 4종의 실제 코드는 별도 프로젝트**(이번 범위 밖)
- 두 프로젝트는 동일 Supabase의 인증·황금열쇠 원장·놀이 세션 API를 공유하되, **소모·예약·확정·복원은 서버의 단일 원자적 함수에서만** 처리. **service_role 키를 브라우저에 노출하지 않음**
- 시작 동의 시 열쇠 **임시 예약** → 놀이 정상 실행 시 **소모 확정** → 실행 실패 시 **원래 지급·소멸 시각 그대로 복원**
- 놀이별 진행상태 + 최초 정상 진입부터 **6시간 이어하기**를 독립 관리, 6시간 내 추가 차감 없이 이어감, 완료/6시간 만료 후 이어하기 미제공
- 진행 중 새로 시작 선택 시: **"기존 진행 기록이 초기화되고 황금열쇠 N개가 소모됩니다"** 최종 확인 → 새 놀이 **정상 실행됐을 때만** 기존 기록 초기화+소모 확정, 취소/실패 시 기존 기록·열쇠 유지

### GAP 재해석
기존 `consume_gold_keys`/`refund_gold_keys`는 **즉시 소모/환불형**이며 "예약(reserve)" 단계가 코드에 **존재하지 않음**(직접 확인). 예약→확정→복원 3단계 원자적 트랜잭션은 **신규 구현 필요**.

### 변경 파일(예상)
- `supabase/migrations/`: 황금열쇠 **예약(reserve) RPC** 신규(기존 consume/refund 확장), `k_play_sessions` 6시간 이어하기/새로시작 초기화 트랜잭션
- `app/child/play/page.tsx`: 플레이스홀더 → 실제 목록+전체화면 모달 셸(실제 게임 콘텐츠는 별도앱 연동)
- 신규: 별도 프로젝트와의 통합 계약 문서(세션 토큰 발급 API, 진행상태 동기화 API) — 구현은 계약 수준까지, 실제 별도 레포는 승인 후
- 신규: 별도 레포/Vercel 프로젝트 생성 체크리스트 문서(실행은 승인 후)
